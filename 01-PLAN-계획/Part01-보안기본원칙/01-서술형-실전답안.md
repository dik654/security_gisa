## 1. CIA Triad

### 문제 1-1: 정보보안의 3대 목표 (CIA Triad)를 설명하고, 각 목표를 위협하는 공격 사례와 대응 방안을 제시하시오 (15점) ★★★

#### ✅ 모범 답안:

**[CIA Triad 정의]**

```
정보보안의 3대 목표:
- Confidentiality (기밀성)
- Integrity (무결성)
- Availability (가용성)
```

---

**[1. Confidentiality (기밀성)] ★★★**

**정의:**
```
인가되지 않은 사용자가 정보에 접근하는 것을 방지
"허가된 사람만 정보에 접근"
```

**목표:**
```
- 민감 정보 보호
- 개인정보 보호
- 영업 기밀 보호
- 국가 기밀 보호
```

**위협 사례:**

**1. 도청 (Eavesdropping)**
```
공격:
- 네트워크 스니핑
- 평문 통신 가로채기
- 무선 네트워크 도청

예시:
- HTTP 트래픽 스니핑으로 패스워드 탈취
- 공개 Wi-Fi에서 패킷 캡처
- 암호화되지 않은 이메일 열람

도구:
- Wireshark
- tcpdump
- Aircrack-ng
```

**2. 사회공학 (Social Engineering)**
```
공격:
- 피싱 (Phishing)
- 스피어 피싱 (Spear Phishing)
- 프리텍스팅 (Pretexting)
- 테일게이팅 (Tailgating)

예시:
"IT 부서입니다. 시스템 점검을 위해
패스워드를 알려주세요."

"CEO입니다. 긴급히 100만원을
다음 계좌로 송금해주세요."
```

**3. 비인가 접근**
```
- SQL Injection으로 DB 접근
- 권한 상승 공격
- 계정 탈취
- 내부자 위협
```

**4. 데이터 유출 (Data Breach)**
```
대규모 사례:
- Equifax (2017): 1억 4천만 명 개인정보
- Yahoo (2013): 30억 계정
- Marriott (2018): 5억 명 고객 정보
```

**대응 방안:**

**A. 암호화 ★★★**
```
전송 중 (Data in Transit):
- TLS/SSL (HTTPS)
- VPN (IPSec, SSL VPN)
- SSH (암호화된 원격 접속)
- S/MIME (이메일 암호화)

저장 중 (Data at Rest):
- 디스크 암호화
  - Windows: BitLocker
  - Linux: LUKS, dm-crypt
  - macOS: FileVault
- 데이터베이스 암호화
  - TDE (Transparent Data Encryption)
  - 컬럼 암호화
- 파일 암호화
  - AES-256
  - 7-Zip, VeraCrypt

사용 중 (Data in Use):
- 메모리 암호화
- Secure Enclave
- Intel SGX
```

**B. 접근 통제 ★★★**
```
식별 (Identification):
- 사용자 ID, 계정

인증 (Authentication):
- 패스워드
- 다중 인증 (MFA)
  - OTP
  - 생체 인식
  - 하드웨어 토큰

인가 (Authorization):
- ACL (Access Control List)
- RBAC (Role-Based Access Control)
- 최소 권한 원칙

감사 (Auditing):
- 접근 로그 기록
- 정기 검토
```

**C. 데이터 분류 ★★**
```
등급:
1. Top Secret (극비)
   - 접근: 최소 인원만
   - 저장: 암호화 필수
   - 전송: 전용 망

2. Secret (비밀)
   - 접근: 권한자만
   - 저장: 암호화
   - 전송: VPN

3. Confidential (대외비)
   - 접근: 부서원
   - 암호화 권장

4. Public (공개)
   - 제한 없음

각 등급별 처리 절차 수립
```

**D. DLP (Data Loss Prevention) ★★**
```
기능:
- 민감 데이터 탐지
  - 주민번호, 카드번호 패턴
  - 기밀 문서
- 전송 차단
  - 이메일 첨부
  - USB 복사
  - 클라우드 업로드
- 알림 및 로그

예시:
주민번호 포함 파일을 외부 이메일로 발송 시도
→ DLP가 차단
→ 보안 담당자에게 알림
```

**E. 교육**
```
- 보안 인식 교육
- 피싱 메일 인식 훈련
- 청정 책상 정책 (Clear Desk)
- 문서 파기 절차
```

---

**[2. Integrity (무결성)] ★★★**

**정의:**
```
정보가 무단으로 변조되지 않음을 보장
"정보가 정확하고 완전함"
```

**목표:**
```
- 데이터 정확성
- 데이터 완전성
- 위변조 방지
```

**위협 사례:**

**1. 변조 (Modification)**
```
공격:
- SQL Injection으로 DB 수정
- 중간자 공격 (MITM)으로 데이터 변조
- 악성코드로 시스템 파일 변조
- 웹사이트 변조 (Defacement)

예시:
공격자가 SQL Injection으로
"UPDATE users SET balance=999999 WHERE id=1"
실행하여 계좌 잔액 변조
```

**2. 삭제 (Deletion)**
```
- 로그 파일 삭제 (흔적 제거)
- 백업 파일 삭제
- 중요 데이터 삭제
```

**3. 재전송 공격 (Replay Attack)**
```
공격:
1. 정상 트랜잭션 가로채기
   "계좌 A → B 10만원 송금"
2. 캡처한 패킷 재전송
3. 동일 거래 반복 실행

결과:
10만원이 여러 번 송금됨
```

**대응 방안:**

**A. 해시 함수 ★★★**
```
용도: 데이터 무결성 검증

알고리즘:
- SHA-256 (권장)
- SHA-3
- BLAKE2

사용:
# 파일 무결성 검증
sha256sum file.iso > checksum.txt

다운로드 후:
sha256sum -c checksum.txt
→ 일치: 무결성 OK
→ 불일치: 변조됨

응용:
- 소프트웨어 배포 시 해시 제공
- 로그 파일 해시 (위변조 탐지)
- 블록체인 (이전 블록 해시 포함)
```

**B. 전자서명 ★★★**
```
원리:
1. 송신자가 개인키로 서명
2. 수신자가 공개키로 검증

보장:
- 무결성: 변조 시 서명 검증 실패
- 부인 방지: 송신자만 서명 가능

사용:
- 계약서 전자서명
- 소프트웨어 코드 서명
  - Windows: Authenticode
  - macOS: Gatekeeper
- 이메일 서명 (S/MIME, PGP)
```

**C. MAC (Message Authentication Code) ★★**
```
HMAC (Hash-based MAC):
- 해시 + 비밀키
- 송수신자만 비밀키 공유
- 무결성 + 인증

예시:
메시지: "송금 100만원"
비밀키: "secret123"
HMAC = SHA256(비밀키 + 메시지)

수신자:
동일한 비밀키로 HMAC 계산
→ 일치하면 무결성 확인
```

**D. 버전 관리 ★★**
```
Git, SVN:
- 모든 변경 이력 추적
- 누가, 언제, 무엇을 변경
- 이전 버전 복구 가능
- 위변조 추적
```

**E. 트랜잭션 무결성**
```
ACID:
- Atomicity (원자성): 전부 또는 전무
- Consistency (일관성): 규칙 준수
- Isolation (격리성): 동시 실행 방지
- Durability (지속성): 영구 저장

타임스탬프:
- 거래 시간 기록
- 재전송 공격 방지
  - 5분 이내 트랜잭션만 유효

Nonce (Number used Once):
- 일회용 난수
- 동일 요청 재사용 방지
```

**F. 파일 무결성 모니터링 (FIM)**
```
도구:
- Tripwire
- AIDE (Advanced Intrusion Detection Environment)
- OSSEC

동작:
1. 초기 베이스라인 생성
   - 모든 파일의 해시 값 저장
2. 정기적 비교
   - 현재 해시 vs 베이스라인
3. 변경 탐지
   - /etc/passwd 변경 → 알림
   - 시스템 파일 변조 → 알림

예시:
```bash
# Tripwire 초기화
tripwire --init

# 무결성 검사
tripwire --check

# 변경 발견 시
File: /etc/passwd
Expected Hash: a1b2c3...
Current Hash: d4e5f6...
Status: MODIFIED
```
```

---

**[3. Availability (가용성)] ★★★**

**정의:**
```
필요할 때 정보와 시스템에 접근 가능
"서비스가 지속적으로 제공됨"
```

**목표:**
```
- 시스템 가동시간 유지
- 서비스 중단 최소화
- 빠른 복구
```

**측정:**
```
가용성 = (전체 시간 - 다운타임) / 전체 시간 × 100%

목표:
- 99.9% (Three Nines): 연간 8.76시간 다운타임
- 99.99% (Four Nines): 연간 52.56분
- 99.999% (Five Nines): 연간 5.26분
```

**위협 사례:**

**1. DoS/DDoS 공격 ★★★**
```
DoS (Denial of Service):
- 단일 출발지에서 공격
- 서버 리소스 고갈
- 네트워크 대역폭 소진

DDoS (Distributed DoS):
- 다수의 좀비 PC (봇넷)
- 대규모 트래픽
- 방어 어려움

공격 유형:
- SYN Flood
- UDP Flood
- HTTP Flood
- Slowloris
- Ping of Death

피해:
- 서비스 중단
- 고객 이탈
- 매출 손실
- 명성 손상
```

**2. 랜섬웨어**
```
- 파일 암호화
- 시스템 사용 불가
- 복구키 없으면 영구 손실
```

**3. 하드웨어 고장**
```
- 디스크 장애
- 서버 다운
- 네트워크 장비 고장
- 전원 장애
```

**4. 자연 재해**
```
- 화재, 홍수, 지진
- 데이터센터 파괴
- 장기 서비스 중단
```

**대응 방안:**

**A. 이중화 (Redundancy) ★★★**
```
서버 이중화:
- Active-Active: 모두 동시 운영
- Active-Standby: 주 서버 장애 시 예비 서버 가동
- 로드 밸런서
  - L4 (IP/Port)
  - L7 (Application)

네트워크 이중화:
- 이중 ISP
- 다중 경로
- VRRP, HSRP (가상 IP)

스토리지 이중화:
- RAID
  - RAID 1: 미러링
  - RAID 5: 패리티
  - RAID 10: 미러링 + 스트라이핑
- SAN 복제
- 클라우드 백업

전원 이중화:
- UPS (무정전 전원 장치)
- 이중 전원 공급
- 발전기
```

**B. DDoS 방어 ★★★**
```
1. 방화벽 Rate Limiting
   - 초당 요청 수 제한
   - 동일 IP 연결 수 제한

2. IPS/IDS
   - DDoS 패턴 탐지
   - 자동 차단

3. CDN (Content Delivery Network)
   - Cloudflare, Akamai
   - 트래픽 분산
   - DDoS 완화

4. Anycast
   - 다수 서버에 동일 IP
   - 트래픽 분산

5. Scrubbing Center
   - ISP 레벨 필터링
   - 악성 트래픽 제거
   - 정상 트래픽만 전달

6. 과잉 대역폭
   - 공격 흡수 여력
```

**C. 백업 및 복구 ★★★**
```
백업 전략:
- Full Backup (전체): 주간
- Incremental (증분): 일일
- Differential (차등): 필요시

3-2-1 규칙:
- 3개 복사본
- 2개 다른 매체
- 1개 오프사이트

백업 테스트:
- 정기 복구 훈련
- 복구 시간 측정 (RTO)
- 데이터 손실 점검 (RPO)

RTO (Recovery Time Objective):
- 목표 복구 시간
- 예: 4시간 이내

RPO (Recovery Point Objective):
- 허용 가능한 데이터 손실 시간
- 예: 1시간 이내 데이터
```

**D. 장애 조치 (Failover) ★★**
```
자동 장애 조치:
- Health Check
  - 주 서버 응답 확인
  - 3회 연속 실패 시
  - 예비 서버로 자동 전환

수동 장애 조치:
- 관리자 판단
- 계획된 유지보수
```

**E. 용량 계획**
```
- 성능 모니터링
- 트래픽 예측
- 피크 타임 대비
- 확장성 (Scalability)
  - Scale-Up: 서버 성능 향상
  - Scale-Out: 서버 수 증가
```

**F. 재해 복구 (DR) ★★★**
```
DR 사이트:
- Hot Site: 즉시 전환 가능
- Warm Site: 수 시간~일 내
- Cold Site: 수 일~주 소요

DR 훈련:
- 연 1~2회
- 시나리오 기반
- 복구 절차 검증
```

---

**[CIA 통합 사례]**

**온라인 뱅킹:**
```
Confidentiality (기밀성):
- 계좌 정보 암호화 (TLS)
- 로그인 인증 (ID/PW + OTP)
- 접근 통제

Integrity (무결성):
- 거래 내역 전자서명
- 트랜잭션 무결성 (ACID)
- 위변조 방지

Availability (가용성):
- 24/7 서비스
- 서버 이중화
- DDoS 방어
- 백업 시스템
```

**의료 시스템:**
```
Confidentiality:
- 환자 기록 암호화
- 의료진만 접근
- 개인정보 보호

Integrity:
- 의료 기록 무결성
- 처방전 위조 방지
- 진료 기록 변조 방지

Availability:
- 응급실 시스템 항상 가동
- 이중화
- 빠른 복구
```

---

**[확장된 보안 목표]**

**추가 3가지:**

**4. Authenticity (진정성)**
```
정의: 주체의 신원이 진짜임을 보장

방법:
- 전자서명
- 디지털 인증서
- 생체 인식
```

**5. Non-Repudiation (부인 방지)**
```
정의: 행위를 부인할 수 없음

방법:
- 전자서명
- 타임스탬프
- 로그 기록
- 블록체인

예시:
계약서 전자서명 후
"나는 서명 안 했다" 부인 불가
```

**6. Accountability (책임 추적성)**
```
정의: 행위를 특정 주체에 추적 가능

방법:
- 로그 기록
- 감사 추적 (Audit Trail)
- 사용자 활동 모니터링
```

**[채점 기준]**
- CIA 3가지 정의 (6점, 각 2점)
- 각 목표별 위협 사례 (3점)
- 각 목표별 대응 방안 (6점)

## 2. AAA

### 문제 2-1: AAA (Authentication, Authorization, Accounting)를 설명하고, 각 단계별 구현 방법과 프로토콜을 제시하시오 (12점) ★★★

#### ✅ 모범 답안:

**[AAA 정의]**

```
AAA 프레임워크:
- Authentication (인증): 누구인가?
- Authorization (인가): 무엇을 할 수 있는가?
- Accounting (계정 관리): 무엇을 했는가?
```

---

**[1. Authentication (인증)] ★★★**

**정의:**
```
사용자의 신원을 확인하는 과정
"당신이 주장하는 사람이 맞는가?"
```

**인증 요소 (3가지):**

**Something You Know (지식 기반)**
```
- 패스워드
- PIN
- 보안 질문

장점: 구현 쉬움
단점: 유출, 추측 가능
```

**Something You Have (소유 기반)**
```
- 스마트카드
- OTP 토큰
- 휴대폰 (SMS)
- USB 보안 토큰
- 인증서

장점: 물리적 소유 필요
단점: 분실, 도난 위험
```

**Something You Are (생체 기반)**
```
- 지문
- 홍채
- 얼굴 인식
- 음성 인식
- 정맥 인식

장점: 위조 어려움
단점: 오인식, 복제 위험
```

**다중 인증 (MFA) ★★★**
```
2개 이상 요소 조합:

2FA 예시:
1. 패스워드 (지식)
2. OTP (소유)

3FA 예시:
1. 패스워드
2. OTP
3. 지문

효과:
- 보안 강도 크게 향상
- 하나 뚫려도 다른 요소로 방어
```

**구현 방법:**

**로컬 인증:**
```
# Linux: /etc/passwd, /etc/shadow
username:x:1000:1000::/home/user:/bin/bash

# Windows: SAM (Security Account Manager)
HKLM\SAM\SAM\Domains\Account\Users
```

**중앙 집중식 인증:**

**LDAP (Lightweight Directory Access Protocol)**
```
용도: 디렉토리 서비스
포트: 389 (LDAP), 636 (LDAPS)

구조:
dc=company,dc=com
  ├─ ou=users
  │   ├─ cn=john
  │   └─ cn=jane
  └─ ou=groups
      └─ cn=admins

사용:
- Active Directory (MS)
- OpenLDAP
```

**Kerberos**
```
원리: 티켓 기반 인증

구성 요소:
- KDC (Key Distribution Center)
- TGT (Ticket Granting Ticket)
- Service Ticket

과정:
1. 클라이언트 → KDC: TGT 요청
2. KDC → 클라이언트: TGT 발급
3. 클라이언트 → KDC: 서비스 티켓 요청
4. KDC → 클라이언트: 서비스 티켓 발급
5. 클라이언트 → 서버: 서비스 티켓 제시
6. 서버: 티켓 검증 → 접근 허용

장점:
- 패스워드 네트워크 전송 안 함
- SSO (Single Sign-On)
- 상호 인증

사용:
- Windows Active Directory
- Linux MIT Kerberos
```

**RADIUS (Remote Authentication Dial-In User Service)**
```
용도: 원격 사용자 인증

포트: 1812 (인증), 1813 (계정)

구성:
[클라이언트] → [NAS] → [RADIUS 서버] → [사용자 DB]

과정:
1. 사용자 → NAS: 로그인 시도
2. NAS → RADIUS: Access-Request
3. RADIUS → DB: 사용자 확인
4. RADIUS → NAS: Access-Accept/Reject
5. NAS → 사용자: 접속 허용/거부

사용:
- VPN 인증
- Wi-Fi 인증 (WPA-Enterprise)
- 네트워크 장비 접속
```

**TACACS+ (Terminal Access Controller Access-Control System Plus)**
```
Cisco 개발

RADIUS vs TACACS+:
- RADIUS: UDP, 패킷 일부 암호화
- TACACS+: TCP, 전체 암호화

- RADIUS: AAA 통합
- TACACS+: AAA 분리 (세밀한 제어)

사용:
- 네트워크 장비 관리 (Cisco)
```

---

**[2. Authorization (인가)] ★★★**

**정의:**
```
인증된 사용자가 무엇을 할 수 있는지 결정
"어떤 권한이 있는가?"
```

**접근 통제 모델:**

**DAC (Discretionary Access Control)**
```
소유자가 권한 결정

예시:
- 파일 소유자가 다른 사용자에게 권한 부여
- chmod, chown (Linux)
- ACL (Access Control List)

장점: 유연함
단점: 보안 취약 (소유자 판단)
```

**MAC (Mandatory Access Control)**
```
시스템이 권한 결정

보안 등급:
- Top Secret > Secret > Confidential > Unclassified

규칙:
- No Read Up: 상위 등급 읽기 금지
- No Write Down: 하위 등급 쓰기 금지

예시:
- Secret 등급 사용자:
  - Secret 읽기/쓰기 ✓
  - Top Secret 읽기 ✗
  - Confidential 쓰기 ✗

사용:
- SELinux
- AppArmor
- 군사/정부 시스템
```

**RBAC (Role-Based Access Control) ★★★**
```
역할 기반 권한

구조:
사용자 → 역할 → 권한

예시:
```
역할: 관리자
권한:
- 사용자 생성/삭제
- 시스템 설정 변경
- 모든 파일 접근

역할: 일반 사용자
권한:
- 자신의 파일만 접근
- 읽기 전용

사용자 John → 관리자 역할 할당
→ 관리자 권한 자동 부여
```

장점:
- 관리 편리
- 직무 변경 시 역할만 변경

사용:
- Windows 그룹
- Linux sudo
- 대부분의 ERP, DB
```

**ABAC (Attribute-Based Access Control)**
```
속성 기반 권한

속성:
- 사용자 속성: 부서, 직급, 위치
- 리소스 속성: 분류, 소유자
- 환경 속성: 시간, 위치, IP

규칙:
```
IF (사용자.부서 == "HR") AND
   (문서.분류 == "인사") AND
   (시간 >= 09:00 AND 시간 <= 18:00)
THEN
   Allow
```

장점: 매우 세밀한 제어
단점: 복잡한 정책
```

**구현 예시:**

**Linux ACL**
```bash
# 특정 사용자에게 권한 부여
setfacl -m u:john:rwx /data/file.txt

# 그룹에 권한 부여
setfacl -m g:developers:rx /data/project/

# ACL 확인
getfacl /data/file.txt
```

**AWS IAM Policy**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::mybucket/*",
      "Condition": {
        "IpAddress": {
          "aws:SourceIp": "192.168.1.0/24"
        }
      }
    }
  ]
}
```

**[3. Accounting (계정 관리)] ★★★**

**정의:**
```
사용자 행위를 기록하고 추적
"누가, 언제, 무엇을 했는가?"
```

**목적:**
```
- 감사 (Audit)
- 과금 (Billing)
- 용량 관리
- 보안 모니터링
- 법적 증거
```

**기록 내용:**

**로그인 기록**
```
- 사용자 ID
- 로그인 시간
- 로그아웃 시간
- 접속 IP
- 성공/실패

Linux:
/var/log/auth.log
/var/log/secure

Windows:
Event ID 4624: 로그인 성공
Event ID 4625: 로그인 실패
```

**자원 사용 기록**
```
- 네트워크 사용량
- 디스크 사용량
- CPU 사용 시간
- 프린터 사용
```

**작업 기록**
```
- 파일 접근
- 명령어 실행
- 설정 변경
- 데이터 수정
```

**구현 방법:**

**Syslog**
```
표준 로그 프로토콜

포맷:
<Priority>Timestamp Hostname Application: Message

예시:
<134>Jan 10 10:23:45 server1 sshd[1234]: Accepted password for john from 192.168.1.100 port 50123 ssh2

전송:
UDP 514 (비암호화)
TCP 514, 6514 (TLS)

중앙 집중식:
모든 서버 → 중앙 Syslog 서버
```

**RADIUS Accounting**
```
메시지:
- Accounting-Request (Start)
  - 세션 시작 시
- Accounting-Request (Update)
  - 주기적 업데이트
- Accounting-Request (Stop)
  - 세션 종료 시

기록:
- 세션 ID
- 사용자
- 사용 시간
- 트래픽 양
```

**Database Audit**
```
Oracle:
- Audit Trail
- Fine-Grained Auditing

기록:
- SELECT 쿼리
- INSERT/UPDATE/DELETE
- 스키마 변경
- 권한 변경

예시:
```sql
-- 감사 활성화
AUDIT SELECT ON employees BY ACCESS;

-- 감사 로그 조회
SELECT username, timestamp, action_name, obj_name
FROM DBA_AUDIT_TRAIL
WHERE obj_name = 'EMPLOYEES';
```
```

**SIEM (Security Information and Event Management)**
```
종합 로그 관리:
- 수집
- 정규화
- 상관 분석
- 장기 보관
- 검색
- 리포팅

제품:
- Splunk
- IBM QRadar
- ArcSight
```

**[AAA 프로토콜 비교]**

| 프로토콜 | 전송 | 암호화 | AAA 분리 | 주 용도 |
|---------|------|--------|---------|---------|
| RADIUS | UDP | 패스워드만 | 통합 | VPN, Wi-Fi |
| TACACS+ | TCP | 전체 | 분리 | 네트워크 장비 |
| Diameter | TCP | 전체 | 분리 | 차세대 (4G/5G) |

**[AAA 실제 시나리오]**

**VPN 접속:**
```
1. Authentication (인증)
   사용자: ID + 패스워드 + OTP
   → RADIUS 서버 확인
   → 인증 성공

2. Authorization (인가)
   사용자 그룹 확인
   → 접근 가능한 네트워크 결정
   → VLAN 할당
   → ACL 적용

3. Accounting (계정)
   로그 기록:
   - 로그인 시간: 2024-01-10 09:00
   - IP: 10.1.1.100
   - 사용 트래픽: 500MB
   - 로그아웃 시간: 2024-01-10 18:00
```

**[채점 기준]**
- AAA 각 단계 정의 (6점, 각 2점)
- 구현 방법 및 프로토콜 (6점)

## ✅ 핵심 요약

### 가장 자주 출제되는 Top 5 ★★★

1. **CIA Triad**: 기밀성, 무결성, 가용성
2. **AAA**: 인증, 인가, 계정 관리
3. **MFA (다중 인증)**: 지식+소유+생체
4. **RBAC**: 역할 기반 접근 통제
5. **백업 3-2-1 규칙**: 3복사본, 2매체, 1오프사이트

### 서술형 답안 작성 팁

1. **CIA 각각**: 정의 → 위협 → 대응 순서
2. **실제 사례**: WannaCry, DDoS 등 언급
3. **구체적 방법**: 명령어, 설정 포함
4. **프로토콜**: RADIUS, TACACS+, Kerberos
5. **비교표**: 장단점 비교

### 실전 시험 전략

- CIA는 **각각 위협과 대응** 모두 작성
- AAA **순서 중요**: 인증 → 인가 → 계정
- MFA는 **3가지 요소** 명확히
- RADIUS vs TACACS+ **차이점** 암기
- 백업은 **3-2-1 규칙** 필수
