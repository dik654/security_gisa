# 접근 통제 모델 - 실기 필수 암기

## 🔴 필수 암기 접근 통제 모델

```
┌────────┬──────────────────────────────────────┐
│  모델  │              설명                    │
├────────┼──────────────────────────────────────┤
│  DAC   │ Discretionary Access Control         │
│        │ 임의적 접근 통제                     │
│        │ - 소유자가 권한 결정                 │
│        │ - Unix/Linux 파일 권한 (rwx)        │
├────────┼──────────────────────────────────────┤
│  MAC   │ Mandatory Access Control             │
│        │ 강제적 접근 통제                     │
│        │ - 시스템이 권한 결정                 │

├────────┼──────────────────────────────────────┤
│  RBAC  │ Role-Based Access Control            │
│        │ 역할 기반 접근 통제                  │
│        │ - 역할에 권한 부여                   │
│        │ - 사용자는 역할 할당받음             │
└────────┴──────────────────────────────────────┘
```

## 📝 기출 유형 1: DAC (Discretionary Access Control) ★★★

### 개념
```
임의적 접근 통제 (Discretionary Access Control)

특징:
- 객체(파일)의 소유자가 접근 권한 결정
- 사용자의 신원(Identity)과 자격(Credentials) 기반
- 유연성 높음, 보안성 상대적으로 낮음

대표 예시:
- Unix/Linux 파일 권한 (rwxrwxrwx)
- Windows NTFS ACL (Access Control List)

장점:
- 유연한 권한 관리
- 소유자가 직접 제어

단점:
- 트로이목마 공격 취약
- 권한 전파 위험 (사용자가 타인에게 권한 부여 가능)
```

### 문제 1-1 (2023년 실기)
```
다음은 Linux 파일의 권한이다. 설명하시오.

-rwxr-x--- 1 user01 group01 1024 Nov 5 14:30 data.txt
```

**✅ 답안:**
```
파일 권한 분석:
- (첫 번째 문자): 일반 파일
rwx (소유자 권한): 읽기, 쓰기, 실행 가능
r-x (그룹 권한): 읽기, 실행 가능 (쓰기 불가)
--- (기타 사용자 권한): 모든 권한 없음

세부 정보:
- 소유자: user01 (rwx = 7)
- 그룹: group01 (r-x = 5)
- 기타: 권한 없음 (--- = 0)
- 숫자 표현: 750

접근 통제 모델: DAC (Discretionary Access Control)
이유: 소유자(user01)가 파일 권한을 자유롭게 변경 가능
      chmod 750 data.txt (소유자가 직접 권한 변경)
```

### 문제 1-2 (DAC의 취약점)
```
DAC 모델의 보안 취약점과 공격 시나리오를 설명하시오.
```

**✅ 답안:**
```
취약점 1: 트로이목마 공격
시나리오:
1. 공격자가 악성 프로그램 작성 (game.exe)
2. 피해자가 game.exe 실행
3. game.exe는 피해자 권한으로 실행됨
4. 피해자의 중요 파일(secret.txt)을 공격자에게 전송
   cp /home/user/secret.txt /tmp/attacker/

문제점:
DAC는 주체(사용자)의 권한만 확인하고,
프로그램의 의도는 확인하지 않음

취약점 2: 권한 전파 (Discretionary)
시나리오:
1. user01이 중요 파일 소유
2. user01이 실수로 user02에게 읽기 권한 부여
   chmod o+r secret.txt
3. user02가 파일을 다른 곳에 복사
4. 정보 유출

문제점:
소유자가 임의로 권한을 부여할 수 있어 통제 어려움

대응 방안:
- MAC (강제적 접근 통제) 사용
- 최소 권한 원칙 (Least Privilege)
- 정기적인 권한 감사
```

## 📝 기출 유형 2: MAC (Mandatory Access Control) ★★★

### 개념
```
강제적 접근 통제 (Mandatory Access Control)

특징:
- 시스템이 접근 권한 결정 (사용자가 변경 불가)
- 보안 레이블(Security Label) 기반
  - 주체(사용자): Security Clearance
  - 객체(파일): Security Classification
- 높은 보안성, 낮은 유연성

보안 레이블 예시:
Top Secret > Secret > Confidential > Unclassified

대표 예시:
- SELinux (Security-Enhanced Linux)
- 군사, 정부 기관 시스템

장점:
- 강력한 보안 (시스템 강제)
- 정보 유출 방지

단점:
- 관리 복잡
- 유연성 낮음
```

### 문제 2-1 (2022년 실기)
```
MAC 모델과 DAC 모델의 차이점을 설명하시오.
```

**✅ 답안:**
```
┌─────────────┬──────────────────┬──────────────────┐
│    구분     │       DAC        │       MAC        │
├─────────────┼──────────────────┼──────────────────┤
│ 권한 결정자 │ 소유자 (사용자)  │ 시스템 (관리자)  │
├─────────────┼──────────────────┼──────────────────┤
│ 제어 방식   │ 임의적 (자유)    │ 강제적 (엄격)    │
├─────────────┼──────────────────┼──────────────────┤
│ 기반        │ 신원(Identity)   │ 보안 레이블      │
├─────────────┼──────────────────┼──────────────────┤
│ 유연성      │ 높음             │ 낮음             │
├─────────────┼──────────────────┼──────────────────┤
│ 보안성      │ 상대적으로 낮음  │ 높음             │
├─────────────┼──────────────────┼──────────────────┤
│ 사용 환경   │ 일반 시스템      │ 군사, 정부 기관  │
├─────────────┼──────────────────┼──────────────────┤
│ 예시        │ Linux 파일 권한  │ SELinux          │
│             │ Windows ACL      │ 보안 등급 시스템 │
└─────────────┴──────────────────┴──────────────────┘

DAC:
- user01이 파일 소유자이면 chmod로 권한 변경 가능
- 소유자의 재량으로 권한 부여/회수

MAC:
- user01도 보안 레이블을 변경할 수 없음
- 시스템 관리자만 보안 정책 설정 가능
- Top Secret 레이블 파일은 Secret 레벨 사용자 접근 불가
```

## 📝 기출 유형 3: RBAC (Role-Based Access Control) ★★★

### 개념
```
역할 기반 접근 통제 (Role-Based Access Control)

특징:
- 역할(Role)에 권한 부여
- 사용자는 역할을 할당받음
- 권한 관리 효율적

구조:
사용자 → 역할 → 권한 → 자원

예시:
김철수 → 영업팀장 역할 → 영업DB 읽기/쓰기 권한 → 고객정보

장점:
- 권한 관리 단순화
- 직무 분리 (Separation of Duties)
- 대규모 조직에 적합

단점:
- 역할 설계 복잡
- 역할 폭발 문제 (Role Explosion)
```

### 문제 3-1 (2023년 실기)
```
RBAC 모델의 동작 원리와 장점을 설명하시오.
```

**✅ 답안:**
```
동작 원리:

1. 역할 정의
   - 관리자 (Administrator)
   - 개발자 (Developer)
   - 일반 사용자 (User)

2. 역할에 권한 부여
   - 관리자: 시스템 설정, 사용자 관리, 모든 파일 접근
   - 개발자: 소스코드 읽기/쓰기, 개발 서버 접근
   - 일반 사용자: 공개 문서 읽기

3. 사용자에게 역할 할당
   - user01 → 관리자 역할
   - user02, user03 → 개발자 역할
   - user04 → 일반 사용자 역할

4. 접근 제어
   user02(개발자)가 파일 접근 시도
   → 시스템이 user02의 역할(개발자) 확인
   → 개발자 역할의 권한 확인
   → 권한 있으면 접근 허용

장점:

1. 권한 관리 효율성
   예: 100명의 영업팀원에게 권한 부여
   DAC: 각 사용자마다 100번 권한 설정
   RBAC: "영업팀" 역할 1개만 설정 → 사용자 할당

2. 직무 분리 (Separation of Duties)
   - 회계 승인 역할 ≠ 회계 집행 역할
   - 한 사람이 두 역할 동시 불가 (내부 통제)

3. 유지보수 용이
   - 신입 사원: "인턴" 역할 할당만 하면 됨
   - 퇴사자: 역할 제거만 하면 모든 권한 회수

4. 감사 및 모니터링
   - 역할별 접근 로그 추적 용이
   - "누가 관리자 권한으로 접근했나?" 쉽게 확인

실무 예시:

회사 시스템:
┌──────────┬─────────────────────────────┐
│   역할   │          권한               │
├──────────┼─────────────────────────────┤
│  CEO     │ 모든 시스템 접근            │
│  CFO     │ 재무 시스템 전체 권한       │
│ 영업팀장 │ 영업DB 읽기/쓰기, CRM 접근 │
│ 영업사원 │ 영업DB 읽기, CRM 읽기      │
│  인턴    │ 공개 문서 읽기              │
└──────────┴─────────────────────────────┘

신입 영업사원 입사:
→ "영업사원" 역할만 할당하면 자동으로 모든 권한 부여
```

## 📝 기출 유형 4: Bell-LaPadula 모델 ★★

### 개념
```
Bell-LaPadula 모델
- 기밀성(Confidentiality) 중심 보안 모델
- 군사, 정부 기관용
- 정보 유출 방지

핵심 규칙:

1. No Read Up (단순 보안 속성, Simple Security Property)
   - 상위 레벨 문서 읽기 금지
   - Secret 레벨 사용자는 Top Secret 문서 읽기 불가

2. No Write Down (★-속성, Star Property)
   - 하위 레벨에 쓰기 금지
   - Top Secret 레벨 사용자는 Secret 문서에 쓰기 불가
   - 이유: 기밀 정보가 낮은 레벨로 유출 방지
```

### 문제 4-1 (2022년 실기)
```
Bell-LaPadula 모델의 "No Read Up"과 "No Write Down"
규칙을 예시와 함께 설명하시오.
```

**✅ 답안:**
```
보안 레벨 구조:
Top Secret (최상위)
    ↑
  Secret
    ↑
Confidential
    ↑
Unclassified (최하위)


규칙 1: No Read Up (단순 보안 속성)
"낮은 레벨 사용자는 높은 레벨 문서를 읽을 수 없다"

예시:
- 사용자: Alice (Secret 레벨)
- 문서 A: Secret 레벨
- 문서 B: Top Secret 레벨

결과:
✓ Alice가 문서 A 읽기: 허용 (같은 레벨)
✓ Alice가 문서 A 쓰기: 허용
✗ Alice가 문서 B 읽기: 차단 (상위 레벨)

이유: 기밀 정보 유출 방지


규칙 2: No Write Down (★-속성, Star Property)
"높은 레벨 사용자는 낮은 레벨 문서에 쓸 수 없다"

예시:
- 사용자: Bob (Top Secret 레벨)
- 문서 C: Top Secret 레벨
- 문서 D: Secret 레벨

결과:
✓ Bob이 문서 C 읽기: 허용
✓ Bob이 문서 C 쓰기: 허용
✗ Bob이 문서 D 쓰기: 차단 (하위 레벨)
✓ Bob이 문서 D 읽기: 허용 (읽기는 가능)

이유:
Top Secret 정보를 알고 있는 Bob이 Secret 문서에 쓰면,
Top Secret 정보가 Secret 레벨로 유출될 위험


실제 시나리오:
군사 기밀 시스템:
- 대령(Top Secret): 작전 계획 문서 작성 중
- 중위(Secret): 부대 일정 문서 관리

No Write Down 위반 예시:
✗ 대령이 부대 일정 문서에 "내일 OO 작전 실시"라고 쓰기
  → Top Secret 작전 정보가 Secret 문서로 유출
  → 차단해야 함!

Bell-LaPadula 모델은 "기밀성"을 최우선으로 보호
```

## 📝 기출 유형 5: Biba 모델 ★★

### 개념
```
Biba 모델
- 무결성(Integrity) 중심 보안 모델
- 데이터 변조 방지
- Bell-LaPadula의 반대 개념

핵심 규칙:

1. No Read Down (단순 무결성 속성)
   - 하위 레벨 문서 읽기 금지
   - 이유: 신뢰할 수 없는 하위 데이터로 인한 오염 방지

2. No Write Up (무결성 ★-속성)
   - 상위 레벨에 쓰기 금지
   - 이유: 낮은 무결성 데이터가 높은 무결성 데이터 오염 방지
```

### 문제 5-1 (2023년 실기)
```
Bell-LaPadula 모델과 Biba 모델의 차이점을 설명하시오.
```

**✅ 답안:**
```
┌──────────────┬──────────────────┬──────────────────┐
│    구분      │  Bell-LaPadula   │      Biba        │
├──────────────┼──────────────────┼──────────────────┤
│ 보호 대상    │ 기밀성           │ 무결성           │
│              │(Confidentiality) │ (Integrity)      │
├──────────────┼──────────────────┼──────────────────┤
│ 읽기 규칙    │ No Read Up       │ No Read Down     │
│              │(상위 읽기 금지)  │ (하위 읽기 금지) │
├──────────────┼──────────────────┼──────────────────┤
│ 쓰기 규칙    │ No Write Down    │ No Write Up      │
│              │(하위 쓰기 금지)  │ (상위 쓰기 금지) │
├──────────────┼──────────────────┼──────────────────┤
│ 사용 환경    │ 군사, 정부 기관  │ 상업 시스템      │
│              │ (기밀 정보 보호) │ (데이터 무결성)  │
└──────────────┴──────────────────┴──────────────────┘


[Bell-LaPadula 모델]
목적: 정보 유출 방지 (기밀성)

규칙:
1. No Read Up: 상위 레벨 읽기 금지
   Secret 사용자 → Top Secret 문서 읽기 ✗

2. No Write Down: 하위 레벨 쓰기 금지
   Top Secret 사용자 → Secret 문서 쓰기 ✗

시나리오:
군사 작전 계획(Top Secret)이 일반 병사(Secret)에게 유출되면 안 됨


[Biba 모델]
목적: 데이터 변조 방지 (무결성)

규칙:
1. No Read Down: 하위 레벨 읽기 금지
   High Integrity 프로그램 → Low Integrity 데이터 읽기 ✗

2. No Write Up: 상위 레벨 쓰기 금지
   Low Integrity 사용자 → High Integrity 데이터 쓰기 ✗

시나리오:
인터넷에서 다운받은 파일(Low Integrity)이
시스템 중요 설정 파일(High Integrity)을 변조하면 안 됨


비교 예시:

데이터 레벨: High > Medium > Low

Bell-LaPadula (기밀성):
Medium 사용자:
✓ Medium 문서 읽기/쓰기 가능
✗ High 문서 읽기 불가 (No Read Up)
✗ Low 문서 쓰기 불가 (No Write Down)

Biba (무결성):
Medium 사용자:
✓ Medium 문서 읽기/쓰기 가능
✗ Low 문서 읽기 불가 (No Read Down)
✗ High 문서 쓰기 불가 (No Write Up)


실무 적용:
- Bell-LaPadula: 정부 기밀문서 시스템
- Biba: 은행 거래 시스템 (데이터 무결성 중요)
```

## 🎯 접근 통제 모델 핵심 암기 카드

### 카드 1: 3대 접근 통제 모델
```
DAC (임의적):
- 소유자가 권한 결정
- 예: Linux chmod, Windows ACL

MAC (강제적):
- 시스템이 권한 결정
- 예: SELinux, 보안 등급

RBAC (역할 기반):
- 역할에 권한 부여
- 예: 관리자, 개발자, 사용자 역할
```

### 카드 2: Bell-LaPadula (기밀성) ★★
```
목적: 정보 유출 방지

No Read Up: 상위 레벨 읽기 금지
No Write Down: 하위 레벨 쓰기 금지

예: Secret 사용자는 Top Secret 문서 읽기 불가
```

### 카드 3: Biba (무결성) ★★
```
목적: 데이터 변조 방지

No Read Down: 하위 레벨 읽기 금지
No Write Up: 상위 레벨 쓰기 금지

예: Low Integrity 데이터는 High Integrity 파일 수정 불가
```

### 카드 4: 모델 비교 (시험 빈출!)

│  모델   │ 읽기규칙 │ 쓰기규칙 │

│Bell-La  │ No ↑     │ No ↓     │

## 📊 그림으로 이해하기

### DAC vs MAC vs RBAC
```
[DAC - 임의적 접근 통제]
user01 (소유자) → file.txt
        ↓
   chmod 644 file.txt (소유자가 직접 권한 변경)
        ↓
   rw-r--r-- (다른 사용자 읽기 가능)


[MAC - 강제적 접근 통제]
시스템 정책: Top Secret > Secret > Confidential

user01 (Secret 레벨)
        ↓
  file_A (Top Secret) → 접근 거부 ✗ (시스템 강제)
  file_B (Secret) → 접근 허용 ✓
  file_C (Confidential) → 읽기만 허용 ✓, 쓰기 거부 ✗


[RBAC - 역할 기반 접근 통제]
김철수 → 영업팀장 역할 → 영업DB 읽기/쓰기 권한
이영희 → 개발자 역할 → 소스코드 읽기/쓰기 권한
박민수 → 인턴 역할 → 공개문서 읽기 권한

역할 변경 시:
김철수가 개발팀으로 이동 → 역할만 "개발자"로 변경
→ 자동으로 권한 변경 (영업DB 접근 X, 소스코드 접근 O)
```

### Bell-LaPadula 모델 동작
```
보안 레벨:
┌─────────────────┐
│  Top Secret (4) │ ← 최상위
├─────────────────┤
│   Secret (3)    │
├─────────────────┤
│ Confidential(2) │
├─────────────────┤
│ Unclassified(1) │ ← 최하위
└─────────────────┘

Alice (Secret 레벨, 3)의 접근:
┌──────────────┬────────┬────────┐
│   문서       │  읽기  │  쓰기  │
├──────────────┼────────┼────────┤
│Top Secret(4) │   ✗    │   ✗    │ No Read Up
│Secret (3)    │   ✓    │   ✓    │ 같은 레벨
│Confidential  │   ✓    │   ✗    │ No Write Down
│(2)           │        │        │
│Unclassified  │   ✓    │   ✗    │ No Write Down
│(1)           │        │        │
└──────────────┴────────┴────────┘

읽기: 자신 레벨 이하만 가능 (↓ 방향)
쓰기: 자신 레벨만 가능 (→ 방향)
```

### Biba 모델 동작
```
무결성 레벨:
┌─────────────────┐
│ High Integrity  │ ← 최상위 (신뢰)
├─────────────────┤
│Medium Integrity │
├─────────────────┤
│ Low Integrity   │ ← 최하위 (의심)
└─────────────────┘

Medium Integrity 프로세스의 접근:
┌─────────────┬────────┬────────┐
│   데이터    │  읽기  │  쓰기  │
├─────────────┼────────┼────────┤
│High (3)     │   ✓    │   ✗    │ No Write Up
│Medium (2)   │   ✓    │   ✓    │ 같은 레벨
│Low (1)      │   ✗    │   ✓    │ No Read Down
└─────────────┴────────┴────────┘

읽기: 자신 레벨 이상만 가능 (↑ 방향)
쓰기: 자신 레벨 이하만 가능 (↓ 방향)

Bell-LaPadula와 정반대!
```

## 💡 실기 답안 작성 팁

### Tip 1: 모델 약자 정확히
```
✅ DAC (Discretionary Access Control)
✅ MAC (Mandatory Access Control)
✅ RBAC (Role-Based Access Control)

❌ DCA, MCA (순서 틀림)
```

### Tip 2: Bell-LaPadula vs Biba 구별
```
Bell-LaPadula: 기밀성 (군사)
- No Read Up (상위 읽기 X)
- No Write Down (하위 쓰기 X)

Biba: 무결성 (상업)
- No Read Down (하위 읽기 X)
- No Write Up (상위 쓰기 X)

★ 암기법:
Bell은 "위로" 못 읽고, "아래로" 못 씀
Biba는 "아래로" 못 읽고, "위로" 못 씀
```

### Tip 3: 예시와 함께 설명
```
문제: "RBAC 모델을 설명하시오"

✅ RBAC는 역할 기반 접근 통제로,
   사용자에게 역할을 할당하고 역할에 권한을 부여함.
   예: 영업팀장 역할에 영업DB 읽기/쓰기 권한 부여

❌ RBAC는 역할 기반입니다. (예시 없음)
```

### Tip 4: 장단점 함께 작성
```
DAC:
장점: 유연함, 소유자가 직접 관리
단점: 트로이목마 공격 취약, 권한 전파 위험
```
