## 1. DAC vs MAC vs RBAC

### 문제 1-1: DAC, MAC, RBAC 접근통제 모델의 차이점을 비교하고, 각각의 장단점과 적용 사례를 설명하시오 (15점) ★★★

#### ✅ 모범 답안:

**[접근 통제 (Access Control) 정의]**

```
접근 통제:
주체(Subject)가 객체(Object)에 접근하는 것을 제어

주체: 사용자, 프로세스, 프로그램
객체: 파일, 디렉토리, 데이터베이스, 네트워크 리소스
```

---

**[1. DAC (Discretionary Access Control) - 임의적 접근 통제] ★★★**

**정의:**
```
소유자가 임의로 권한을 결정
"내 파일, 내 마음대로"
```

**특징:**

**소유자 중심:**
```
- 리소스 소유자가 권한 결정
- 다른 사용자에게 권한 부여/회수
- 유연한 권한 관리
```

**구현 방법:**

**1. ACL (Access Control List)**
```
각 객체마다 접근 가능한 주체 목록

예시:
file.txt의 ACL:
- alice: read, write
- bob: read
- charlie: denied

Windows:
파일 우클릭 → 속성 → 보안 → 권한 편집

Linux:
```bash
# ACL 설정
setfacl -m u:alice:rw file.txt
setfacl -m u:bob:r file.txt

# ACL 확인
getfacl file.txt
# file: file.txt
# owner: root
# group: root
user::rw-
user:alice:rw-
user:bob:r--
```
```

**2. Capability List (능력 목록)**
```
각 주체마다 접근 가능한 객체 목록

예시:
alice의 Capability:
- file1.txt: read, write
- file2.txt: read
- dir1/: read, execute
```

**3. Protection Matrix (보호 행렬)**
```
       file1  file2  dir1
alice   rw     r      rx
bob     r      rw     -
charlie -      r      rx

행: 주체
열: 객체
셀: 권한
```

**Unix/Linux 파일 권한:**
```bash
-rw-r--r-- 1 alice users 1024 Jan 10 10:00 file.txt
│││ │ │ │
│││ │ │ └─ 기타 (others)
│││ │ └─── 그룹 (group)
│││ └───── 소유자 (owner)
││└─────── 실행 (execute)
│└──────── 쓰기 (write)
└───────── 읽기 (read)

# 권한 변경 (소유자만 가능)
chmod 644 file.txt  # rw-r--r--
chmod 755 script.sh # rwxr-xr-x

# 소유자 변경
chown bob file.txt
chgrp developers file.txt
```

**장점:**

1. **유연성 ★★★**
```
- 소유자가 자유롭게 권한 설정
- 빠른 권한 변경
- 협업 용이
```

2. **사용자 친화적**
```
- 이해하기 쉬움
- 구현 간단
- 관리 편리
```

3. **세밀한 제어**
```
- 개별 사용자에게 각기 다른 권한
- 파일별 권한 설정
```

**단점:**

1. **보안 취약 ★★★**
```
트로이목마 공격:
1. 악성 프로그램이 사용자로 실행
2. 사용자 권한으로 파일 접근
3. 데이터 유출/변조

예시:
alice가 악성 프로그램 실행
→ 프로그램이 alice 권한 획득
→ alice 소유 파일 모두 접근 가능
```

2. **권한 전파 (Permission Propagation)**
```
alice가 bob에게 read 권한 부여
→ bob이 파일 복사
→ bob이 charlie에게 권한 부여
→ alice 의도와 무관하게 확산
```

3. **관리 부담**
```
- 사용자 증가 시 관리 복잡
- 일관성 유지 어려움
- 퇴사자 권한 회수 누락 위험
```

**적용 사례:**
```
- Windows 파일 시스템 (NTFS)
- Linux/Unix 파일 시스템
- 클라우드 스토리지 (개인 파일)
- 대부분의 상업용 OS
```

---

**[2. MAC (Mandatory Access Control) - 강제적 접근 통제] ★★★**

**정의:**
```
시스템이 강제적으로 권한을 결정
"시스템 정책에 따라 엄격히 제어"
소유자도 임의로 변경 불가
```

**특징:**

**보안 등급 기반:**
```
주체 (Subject):
- Top Secret (TS)
- Secret (S)
- Confidential (C)
- Unclassified (U)

객체 (Object):
- Top Secret 문서
- Secret 문서
- Confidential 문서
- Unclassified 문서
```

**보안 규칙:**

**1. No Read Up (상향 읽기 금지) ★★★**
```
낮은 등급 주체가 높은 등급 객체 읽기 불가

예시:
Secret 등급 사용자
→ Top Secret 문서 읽기 ✗
→ Secret 문서 읽기 ✓
→ Confidential 문서 읽기 ✓
```

**2. No Write Down (하향 쓰기 금지) ★★★**
```
높은 등급 주체가 낮은 등급 객체에 쓰기 불가
(정보 유출 방지)

예시:
Top Secret 등급 사용자
→ Top Secret 문서 쓰기 ✓
→ Secret 문서 쓰기 ✗
→ Confidential 문서 쓰기 ✗
```

**구현 예시:**

**SELinux (Security-Enhanced Linux)**
```
Type Enforcement (유형 강제):

컨텍스트:
user:role:type:level

예시:
system_u:object_r:httpd_sys_content_t:s0
│        │        │                    │
사용자    역할     타입                레벨

정책:
allow httpd_t httpd_sys_content_t:file { read open };
→ httpd 프로세스는 웹 콘텐츠 파일만 읽기 가능

확인:
```bash
# 파일 컨텍스트 확인
ls -Z /var/www/html/
-rw-r--r--. root root unconfined_u:object_r:httpd_sys_content_t:s0 index.html

# 프로세스 컨텍스트 확인
ps -eZ | grep httpd
system_u:system_r:httpd_t:s0    1234 ?    /usr/sbin/httpd
```

정책 위반 시:
httpd가 /etc/passwd 읽기 시도
→ SELinux 거부
→ /var/log/audit/audit.log 기록
```

**AppArmor**
```
프로파일 기반:

/usr/sbin/nginx {
  /var/www/html/** r,
  /var/log/nginx/* w,
  /etc/nginx/ r,
  deny /etc/passwd r,
}

nginx는:
- 웹 디렉토리 읽기만 가능
- 로그 쓰기 가능
- /etc/passwd 접근 불가
```

**장점:**

1. **높은 보안성 ★★★**
```
- 엄격한 정책
- 트로이목마 방어
  - 프로그램이 사용자 권한 획득해도
  - MAC 정책으로 제한
- 정보 유출 방지
```

2. **일관된 정책**
```
- 중앙 집중식 관리
- 모든 시스템에 동일 정책 적용
- 사용자 임의 변경 불가
```

3. **감사 추적**
```
- 모든 접근 시도 기록
- 정책 위반 탐지
```

**단점:**

1. **유연성 부족 ★★★**
```
- 정책 변경 어려움
- 관리자만 설정 가능
- 긴급 상황 대응 어려움
```

2. **복잡한 관리**
```
- 정책 설정 복잡
- 전문 지식 필요
- 오설정 시 서비스 중단
```

3. **사용자 불편**
```
- 정당한 작업도 차단 가능
- 워크플로우 제약
```

4. **높은 오버헤드**
```
- 모든 접근마다 정책 검사
- 성능 저하
```

**적용 사례:**
```
- 군사/정부 시스템
- 국가 기밀 문서 관리
- 고도의 보안이 필요한 환경
- SELinux (Red Hat, CentOS)
- AppArmor (Ubuntu, SUSE)
- TrustedBSD
```

**[3. RBAC (Role-Based Access Control) - 역할 기반 접근 통제] ★★★**

**정의:**
```
역할에 권한을 부여하고, 사용자를 역할에 할당
"역할로 권한 관리"
```

**구조:**
```
사용자 → 역할 → 권한 → 객체

예시:
John → 관리자 역할 → 시스템 설정 변경 권한 → 설정 파일
Jane → 일반 사용자 역할 → 읽기 권한 → 데이터 파일
```

**핵심 개념:**

**1. 역할 (Role)**
```
직무나 책임에 따른 그룹

예시:
- CEO
- 관리자
- 개발자
- 영업
- 고객 지원
- 일반 사용자
```

**2. 권한 (Permission)**
```
특정 작업 수행 능력

예시:
- 파일 읽기
- 파일 쓰기
- 사용자 생성
- 시스템 재시작
- 급여 조회
```

**3. 역할-권한 매핑**
```
관리자 역할:
- 사용자 생성/삭제
- 시스템 설정 변경
- 모든 로그 조회
- 백업 수행

개발자 역할:
- 코드 저장소 접근
- 개발 서버 접속
- 테스트 DB 접근

영업 역할:
- 고객 정보 조회
- 영업 실적 조회
- 견적서 작성
```

**4. 사용자-역할 할당**
```
John → 관리자 역할
Jane → 개발자 역할
Bob → 영업 역할

직무 변경 시:
Jane: 개발자 → 관리자 (역할만 변경)
→ 자동으로 관리자 권한 획득
```

**구현 예시:**

**Windows Active Directory**
```
그룹 = 역할

그룹: Domain Admins
권한:
- 도메인 컨트롤러 관리
- 모든 컴퓨터 관리
- 사용자 계정 관리

사용자 할당:
net localgroup "Domain Admins" john /add
```

**Linux sudo**
```
/etc/sudoers:

# 관리자 그룹
%admin ALL=(ALL) ALL

# 개발자 그룹 - 특정 명령만
%developers ALL=(ALL) /usr/bin/systemctl restart nginx, /usr/bin/git

# 백업 담당 - 백업 명령만
%backup ALL=(ALL) NOPASSWD: /usr/bin/rsync

사용자 할당:
usermod -aG admin john
usermod -aG developers jane
```

**Database**
```sql
-- 역할 생성
CREATE ROLE analyst;
CREATE ROLE developer;

-- 권한 부여
GRANT SELECT ON sales_data TO analyst;
GRANT SELECT, INSERT, UPDATE ON products TO developer;

-- 사용자에게 역할 할당
GRANT analyst TO john;
GRANT developer TO jane;

직무 변경:
REVOKE analyst FROM john;
GRANT developer TO john;
→ 자동으로 권한 변경
```

**AWS IAM**
```json
{
  "RoleName": "S3-ReadOnly",
  "AssumeRolePolicyDocument": {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {"Service": "ec2.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }]
  },
  "Policies": [{
    "PolicyName": "S3-Read",
    "PolicyDocument": {
      "Version": "2012-10-17",
      "Statement": [{
        "Effect": "Allow",
        "Action": ["s3:GetObject", "s3:ListBucket"],
        "Resource": "*"
      }]
    }
  }]
}

사용자/리소스에 역할 할당
```

**RBAC 제약 조건:**

**1. 상호 배타적 역할 (Mutually Exclusive Roles)**
```
동일 사용자가 충돌하는 역할 동시 보유 불가

예시:
- 회계 담당 + 감사 담당 ✗
- 개발자 + QA 테스터 ✗ (일부 조직)

이유: 직무 분리 원칙
```

**2. 선행 조건 (Prerequisite Roles)**
```
특정 역할을 위해 다른 역할 먼저 필요

예시:
시니어 개발자 역할
→ 먼저 일반 개발자 역할 필요
```

**3. 카디널리티 (Cardinality)**
```
역할에 할당 가능한 사용자 수 제한

예시:
CFO 역할: 최대 1명
관리자 역할: 최대 5명
```

**장점:**

1. **관리 편의성 ★★★**
```
- 역할 단위 권한 관리
- 사용자 수 증가해도 관리 간단
- 직무 변경 시 역할만 변경

예시:
1000명 회사, 10개 역할
→ 10개 역할만 관리
vs DAC: 1000명 각각 관리
```

2. **일관성**
```
- 동일 역할 = 동일 권한
- 정책 일관성 유지
- 오류 감소
```

3. **직무 분리**
```
- 중요 작업 분산
- 내부 통제 강화
- 부정 방지
```

4. **감사 용이**
```
- 역할별 활동 추적
- 책임 소재 명확
```

**단점:**

1. **역할 폭발 (Role Explosion)**
```
역할이 너무 많아지는 문제

예시:
- 서울 지점 관리자
- 부산 지점 관리자
- 대구 지점 관리자
...
→ 지점별 역할 생성
→ 관리 복잡도 증가
```

2. **유연성 부족**
```
- 개별 사용자 예외 처리 어려움
- 임시 권한 부여 복잡
```

3. **초기 설계 중요**
```
- 역할 설계 잘못 시 재설계 필요
- 조직 구조 변경 시 역할 재정의
```

**적용 사례:**
```
- 대부분의 기업 시스템
- ERP (SAP, Oracle)
- 클라우드 (AWS IAM, Azure RBAC)
- 데이터베이스 (Oracle, PostgreSQL)
- Active Directory
- Linux sudo
```

**[DAC vs MAC vs RBAC 비교표]**

| 구분 | DAC | MAC | RBAC |
|------|-----|-----|------|
| **권한 결정** | 소유자 | 시스템 | 역할 |
| **유연성** | 매우 높음 | 낮음 | 중간 |
| **보안성** | 낮음 | 매우 높음 | 높음 |
| **관리 복잡도** | 낮음 | 높음 | 중간 |
| **확장성** | 낮음 | 중간 | 높음 |
| **사용자 편의** | 높음 | 낮음 | 중간 |
| **적용 분야** | 일반 OS | 군사/정부 | 기업 |
| **예시** | Windows, Linux | SELinux | Active Directory |

**[4. ABAC (Attribute-Based Access Control) - 속성 기반 접근 통제] ★★**

**정의:**
```
주체, 객체, 환경의 속성 조합으로 권한 결정
"조건부 접근 통제"
```

**속성 종류:**

**주체 속성:**
```
- 부서: HR, IT, Sales
- 직급: 사원, 대리, 부장
- 위치: 서울, 부산
- 보안 등급: Top Secret
```

**객체 속성:**
```
- 분류: Public, Confidential
- 소유 부서: HR
- 생성 일자: 2024-01-01
```

**환경 속성:**
```
- 시간: 09:00-18:00
- 위치: 사무실 내부
- IP 범위: 192.168.1.0/24
- 요일: 평일
```

**정책 예시:**
```
IF (사용자.부서 == "HR") AND
   (문서.분류 == "인사") AND
   (시간 >= 09:00 AND 시간 <= 18:00) AND
   (위치 == "사무실")
THEN
   Allow READ/WRITE

IF (사용자.직급 == "부장") AND
   (문서.소유부서 == 사용자.부서)
THEN
   Allow READ
```

**장점:**
- 매우 세밀한 제어
- 동적 권한 결정
- 컨텍스트 고려

**단점:**
- 복잡한 정책
- 성능 오버헤드
- 관리 어려움

**[접근 통제 선택 가이드]**

**DAC 선택:**
```
- 소규모 조직
- 유연성 중요
- 협업 빈번
- 낮은 보안 요구
- 예: 개인 PC, 소규모 팀
```

**MAC 선택:**
```
- 국가 기밀
- 군사/정부
- 엄격한 보안 필요
- 정보 유출 방지 중요
- 예: 국방부, 정보기관
```

**RBAC 선택:**
```
- 중대규모 기업
- 명확한 직무 구분
- 다수 사용자
- 관리 효율 중요
- 예: 대부분의 기업
```

**ABAC 선택:**
```
- 복잡한 정책 필요
- 동적 권한 결정
- 클라우드 환경
- 예: AWS, Azure
```

**[채점 기준]**
- DAC, MAC, RBAC 정의 (6점, 각 2점)
- 장단점 비교 (6점)
- 적용 사례 (3점)

## 2. Bell-LaPadula 모델

### 문제 2-1: Bell-LaPadula 보안 모델의 두 가지 주요 원칙을 설명하고, 이 모델이 보호하는 보안 목표와 한계점을 제시하시오 (12점) ★★★

#### ✅ 모범 답안:

**[Bell-LaPadula 모델 개요]**

```
개발: 1973년, Bell과 LaPadula
목적: 기밀성(Confidentiality) 보호
기반: MAC (Mandatory Access Control)
용도: 군사 및 정부 시스템
```

**[보안 등급]**

```
주체 (Subject) 등급:
- Top Secret (TS)
- Secret (S)
- Confidential (C)
- Unclassified (U)

객체 (Object) 분류:
- Top Secret 문서
- Secret 문서
- Confidential 문서
- Unclassified 문서

관계: TS > S > C > U
```

---

**[주요 원칙 2가지] ★★★**

**1. Simple Security Property (단순 보안 속성)**
```
별칭: No Read Up (상향 읽기 금지)

규칙:
주체는 자신의 등급보다 높은 등급의 객체를 읽을 수 없다

S(주체) ≤ O(객체) 일 때만 Read 허용
```

**예시:**
```
Secret 등급 사용자 Alice:

읽기 가능:
✓ Unclassified 문서 (U < S)
✓ Confidential 문서 (C < S)
✓ Secret 문서 (S = S)

읽기 불가:
✗ Top Secret 문서 (TS > S)

이유: 높은 등급 정보 유출 방지
```

**구체적 시나리오:**
```
상황:
Bob (Confidential 등급)이
Top Secret 문서를 읽으려 시도

시스템:
Bob의 등급 (C) < 문서 등급 (TS)
→ Simple Security Property 위반
→ 접근 거부

로그:
Access Denied: Bob (C) attempted to read TS document
```

---

**2. *-Property (Star Property)**
```
별칭: No Write Down (하향 쓰기 금지)

규칙:
주체는 자신의 등급보다 낮은 등급의 객체에 쓸 수 없다

S(주체) ≥ O(객체) 일 때만 Write 허용
```

**예시:**
```
Top Secret 등급 사용자 Alice:

쓰기 가능:
✓ Top Secret 문서 (TS = TS)

쓰기 불가:
✗ Secret 문서 (S < TS)
✗ Confidential 문서 (C < TS)
✗ Unclassified 문서 (U < TS)

이유: 높은 등급 정보가 낮은 등급 문서로 유출 방지
```

**구체적 시나리오:**
```
상황:
Alice (Top Secret 등급)가
비밀 정보를 알게 됨
→ Unclassified 문서에 메모하려 시도

시스템:
Alice의 등급 (TS) > 문서 등급 (U)
→ *-Property 위반
→ 쓰기 거부

이유:
TS 정보가 U 문서에 기록되면
U 등급 사용자가 읽을 수 있음
→ 정보 유출
```

---

**[두 규칙의 조합]**

```
읽기와 쓰기:

Top Secret 사용자:
- Read: TS 이하 모두 읽기 ✓
- Write: TS만 쓰기 ✓
→ 높은 등급 정보를 낮은 등급으로 유출 불가

Unclassified 사용자:
- Read: U만 읽기 ✓
- Write: U 이상 모두 쓰기 ✓
→ 낮은 등급 사용자는 높은 정보 접근 불가
```

**매트릭스:**
```
        │ Read U │ Read C │ Read S │ Read TS
────────┼────────┼────────┼────────┼─────────
User U  │   ✓    │   ✗    │   ✗    │    ✗
User C  │   ✓    │   ✓    │   ✗    │    ✗
User S  │   ✓    │   ✓    │   ✓    │    ✗
User TS │   ✓    │   ✓    │   ✓    │    ✓

        │ Write U│ Write C│ Write S│ Write TS
────────┼────────┼────────┼────────┼─────────
User U  │   ✓    │   ✓    │   ✓    │    ✓
User C  │   ✗    │   ✓    │   ✓    │    ✓
User S  │   ✗    │   ✗    │   ✓    │    ✓
User TS │   ✗    │   ✗    │   ✗    │    ✓
```

---

**[보안 목표] ★★★**

**1. 기밀성 (Confidentiality) 보호**
```
목표: 비인가 정보 공개 방지

방법:
- 상향 읽기 금지 → 높은 등급 정보 보호
- 하향 쓰기 금지 → 정보 유출 경로 차단
```

**2. 정보 흐름 통제**
```
정보 흐름 방향:
낮음 → 높음 (허용)
높음 → 낮음 (차단)

예시:
Unclassified → Top Secret ✓
Top Secret → Unclassified ✗
```

**3. 트로이목마 공격 방어**
```
공격 시나리오:
1. Top Secret 사용자가 악성 프로그램 실행
2. 프로그램이 TS 문서 읽기 (허용)
3. 프로그램이 U 문서에 쓰기 시도 (차단!)

Bell-LaPadula:
TS 등급 프로세스가 U 문서 쓰기 불가
→ 정보 유출 차단
```

---

**[한계점] ★★★**

**1. 무결성 미보호**
```
Bell-LaPadula는 기밀성만 보호
→ 무결성(Integrity)은 보호 안 함

문제:
Unclassified 사용자가
Top Secret 문서에 쓰기 가능 (Write Up)
→ 낮은 등급 사용자가 높은 등급 문서 변조 가능

예시:
U 등급 사용자가 TS 문서에
잘못된 정보 작성 가능
```

**2. Covert Channel (은닉 채널)**
```
정책 우회 경로:

타이밍 채널:
TS 프로세스가 U 프로세스에게
시간 간격으로 정보 전달
- 1초 대기 = 비트 1
- 0.5초 대기 = 비트 0

저장 채널:
TS 프로세스가 공유 리소스 사용
→ U 프로세스가 리소스 상태 관찰
→ 간접적 정보 전달
```

**3. 실용성 문제**
```
하향 쓰기 금지로 인한 불편:

일일 보고서 작성:
TS 등급 직원이 일반 보고서 작성 불가
→ 모든 보고서가 TS 등급으로 생성
→ 등급 인플레이션

해결책:
- Trusted Subject (신뢰 주체) 도입
- 등급 강등 절차 (Declassification)
```

**4. 가용성 고려 안 됨**
```
DoS 공격:
U 등급 사용자가
TS 문서를 과도하게 쓰기
→ TS 문서 크기 폭증
→ 디스크 고갈

Bell-LaPadula는 이를 방지 안 함
```

**5. 동적 환경 부적합**
```
정적 보안 등급:
사용자와 문서 등급이 고정

현대 환경:
- 동적 권한 변경 필요
- 컨텍스트 기반 접근
- 협업 필요

Bell-LaPadula는 유연성 부족
```

---

**[보완 모델]**

**Biba 모델 (무결성):**
```
Bell-LaPadula의 반대
기밀성 대신 무결성 보호
- No Write Up
- No Read Down
```

**Clark-Wilson 모델:**
```
상업 환경에 적합
- 잘 정의된 트랜잭션
- 직무 분리
- 감사 추적
```

---

**[실제 적용]**

**SELinux MLS (Multi-Level Security):**
```
Bell-LaPadula 구현

보안 레벨:
s0 < s1 < s2 < s3

파일:
-rw-r--r--. root root s0:c0 public.txt
-rw-------. root root s3:c0 classified.txt

프로세스:
user_u:user_r:user_t:s0 (일반 사용자)
user_u:user_r:user_t:s3 (높은 등급 사용자)

정책:
s0 프로세스 → s3 파일 읽기 ✗
s3 프로세스 → s0 파일 쓰기 ✗
```

**[채점 기준]**
- 두 가지 원칙 설명 (6점, 각 3점)
- 보안 목표 (3점)
- 한계점 (3점)
