---

**[1단계: 준비 (Preparation)] ★★★**

```
평상시 사전 준비 활동
"예방이 최선의 대응"
```

**주요 활동:**

**A. 조직 구성**
```
CSIRT (Computer Security Incident Response Team) 구성:

역할 정의:
- 팀장: 의사결정, 대외 소통
- 기술팀: 분석, 포렌식
- 법무팀: 법적 대응
- 홍보팀: 미디어 대응
- 경영진: 자원 승인

연락망 구축:
- 24/7 비상 연락망
- 에스컬레이션 경로
- 외부 협력 기관
  - 경찰청 사이버수사대
  - KISA (한국인터넷진흥원)
  - 보안업체
```

**B. 정책 및 절차**
```
문서화:

사고 대응 계획 (IRP):
- 사고 정의 및 분류
- 대응 절차
- 역할 및 책임
- 보고 체계

대응 플레이북:
- 랜섬웨어 대응 플레이북
- DDoS 대응 플레이북
- 데이터 유출 대응 플레이북
- APT 대응 플레이북

커뮤니케이션 계획:
- 내부 공지 절차
- 고객 통지 절차
- 언론 대응 절차
```

**C. 도구 및 시스템**
```
기술적 준비:

포렌식 도구:
- FTK (Forensic Toolkit)
- EnCase
- Volatility (메모리 분석)
- Wireshark (네트워크 분석)
- SIFT Workstation

백업 시스템:
- 정기 백업 (일일/주간)
- 오프라인 백업
- 백업 테스트
- 복구 훈련

격리 환경:
- 샌드박스
- 격리 네트워크
- 분석용 VM
```

**D. 교육 및 훈련**
```
정기 훈련:

Table-top Exercise:
- 시나리오 기반 토론
- 분기별 실시
- 의사결정 연습

모의 훈련:
- 실제 환경 시뮬레이션
- 연 1~2회
- Red Team vs Blue Team

인식 제고:
- 전 직원 보안 교육
- 피싱 훈련
- 사고 신고 절차 교육
```

**E. 위협 인텔리전스**
```
정보 수집:

위협 동향:
- CVE 모니터링
- 보안 취약점 정보
- 신종 악성코드 정보

지표 수집:
- IOC (Indicators of Compromise)
- 악성 IP/도메인 목록
- 파일 해시
```

---

**[2단계: 식별 (Identification)] ★★★**

```
침해사고 발생 인지 및 확인
"정확한 진단이 절반"
```

**주요 활동:**

**A. 탐지**
```
사고 발견 경로:

자동 탐지:
- SIEM 경보
- IDS/IPS 알림
- EDR 탐지
- 백신 경보

수동 발견:
- 사용자 신고
- 관리자 발견
- 외부 통보 (KISA, FBI)
- 언론 보도
```

**B. 초기 평가**
```
사고 확인:

질문 사항:
□ 실제 침해사고인가? (오탐 여부)
□ 언제 발생했는가?
□ 어떤 시스템이 영향 받았는가?
□ 어떤 데이터가 관련되었는가?
□ 공격자는 누구인가? (추정)
□ 공격 목적은 무엇인가?

초기 증거 수집:
- 로그 백업
- 메모리 덤프
- 네트워크 트래픽 캡처
- 스크린샷
```

**C. 사고 분류**
```
심각도 평가:

Critical (긴급):
- 핵심 시스템 침해
- 대규모 데이터 유출
- 서비스 완전 중단
- 랜섬웨어 전파
→ 즉시 대응

High (높음):
- 중요 시스템 침해
- 민감 정보 노출 가능
- 부분 서비스 장애
→ 1시간 내 대응

Medium (중간):
- 일반 시스템 침해
- 제한적 영향
→ 4시간 내 대응

Low (낮음):
- 경미한 침해 시도
- 차단됨
→ 일과 시간 내 대응
```

**D. 범위 파악**
```
영향 분석:

침해 범위:
- 감염된 호스트 수
- 네트워크 세그먼트
- 사용자 계정
- 데이터베이스

시간 범위:
- 최초 침입 시점 (Initial Compromise)
- 탐지 시점
- 잠복 기간 (Dwell Time)
```

**E. 통보**
```
이해관계자 통지:

내부:
- 경영진
- 법무팀
- 홍보팀
- IT 부서

외부 (필요시):
- KISA
- 경찰청
- 고객
- 규제 기관

보고서 작성:
- 초기 사고 보고서
- 상황 요약
- 현재 조치
- 예상 영향
```

---

**[3단계: 억제 (Containment)] ★★★**

```
확산 방지 및 피해 최소화
"불을 끄기 전에 퍼지는 것을 막아라"
```

**주요 활동:**

**A. 단기 억제 (Short-term)**
```
즉각 조치 (분~시간 내):

네트워크 차단:
- 감염 시스템 네트워크 격리
- 악성 IP/도메인 차단
- 방화벽 규칙 추가
- VLAN 분리

계정 조치:
- 침해 계정 비활성화
- 의심 계정 패스워드 재설정
- 권한 회수

서비스 조치:
- 불필요한 서비스 중지
- 원격 접속 차단
- 공유 폴더 접근 차단

백업 보호:
- 백업 서버 격리
- 백업 무결성 확인
- 추가 백업 생성
```

**예시 - 랜섬웨어:**
```
1. 감염 PC 즉시 네트워크 케이블 제거
2. 동일 네트워크 세그먼트 격리
3. 공유 폴더 모두 오프라인
4. 백업 서버 네트워크 분리
5. VPN 접속 일시 차단
```

**B. 장기 억제 (Long-term)**
```
지속 가능한 조치 (일~주 단위):

임시 시스템:
- 클린 시스템으로 서비스 이전
- 임시 네트워크 구성
- 우회 경로 설정

모니터링 강화:
- 추가 감시 포인트
- 로그 수집 증가
- 실시간 알림 설정

정책 강화:
- 임시 보안 정책
- 접근 제한
- 다중 인증 강제
```

**C. 증거 보존**
```
포렌식 준비:

휘발성 데이터:
- 메모리 덤프 (우선)
- 네트워크 연결 상태
- 실행 중 프로세스

비휘발성 데이터:
- 하드디스크 이미징
- 로그 파일 백업
- 설정 파일 복사

Chain of Custody:
- 증거 보관 기록
- 접근 이력 관리
- 해시 값 기록
```

---

**[4단계: 근절 (Eradication)] ★★★**

```
위협 완전 제거
"뿌리까지 뽑아라"
```

**주요 활동:**

**A. 악성 요소 제거**
```
삭제 작업:

악성코드:
- 악성 파일 삭제
- 레지스트리 정리
  - HKLM\Software\Microsoft\Windows\CurrentVersion\Run
  - HKCU\Software\Microsoft\Windows\CurrentVersion\Run
- 스케줄 작업 제거
- 서비스 삭제

백도어:
- 생성된 계정 삭제
- 변조된 파일 복원
- 웹쉘 제거
- 루트킷 제거

Persistence 제거:
- Startup 폴더
- WMI 이벤트
- DLL 인젝션
```

**B. 취약점 제거**
```
보안 강화:

패치 적용:
- OS 보안 패치
- 애플리케이션 업데이트
- 펌웨어 업데이트

설정 강화:
- 불필요한 서비스 비활성화
- 포트 차단
- 기본 계정 삭제
- 패스워드 정책 강화

권한 재설정:
- 최소 권한 원칙
- 관리자 계정 제한
- 공유 폴더 권한 검토
```

**C. 침해 흔적 정리**
```
시스템 정리:

로그 보존:
- 공격 로그 별도 백업
- 포렌식 분석용

로그 아카이빙 후:
- 로그 파일 정리 (용량 확보)
- 임시 파일 삭제
```

**D. 검증**
```
제거 확인:

스캔:
- 백신 전체 스캔
- 루트킷 스캔
- 포트 스캔

IOC 검색:
- 파일 해시 검색
- 레지스트리 키 검색
- 네트워크 연결 확인

모니터링:
- 24~72시간 집중 관찰
- 재감염 징후 확인
- 이상 행동 감시
```

---

**[5단계: 복구 (Recovery)] ★★★**

```
정상 운영 재개
"안전한 복귀"
```

**주요 활동:**

**A. 시스템 복구**
```
복구 방법 선택:

Option 1: 백업 복원
- 감염 이전 백업 확인
- 무결성 검증
- 단계적 복원

Option 2: 재설치
- 클린 OS 설치
- 애플리케이션 설치
- 데이터 복원
- 더 안전하지만 시간 소요

Option 3: 하이브리드
- 시스템: 재설치
- 데이터: 백업 복원
```

**B. 서비스 재개**
```
단계적 복구:

1단계: 내부 테스트
- 격리 환경에서 테스트
- 기능 검증
- 보안 스캔

2단계: 제한적 운영
- 일부 사용자만
- 주요 기능만
- 집중 모니터링

3단계: 전면 복구
- 전체 서비스
- 정상 모니터링
```

**C. 모니터링**
```
복구 후 감시:

집중 모니터링 기간 (1~2주):
- 로그 실시간 검토
- 네트워크 트래픽 분석
- 사용자 행동 모니터링
- 시스템 성능 확인

경보 임계값 조정:
- 더 민감하게 설정
- 재발 징후 즉시 탐지
```

**D. 검증**
```
복구 확인:

기능 테스트:
- 모든 서비스 정상 작동
- 데이터 무결성 확인
- 성능 검증

보안 테스트:
- 취약점 스캔
- 침투 테스트
- 설정 검토

사용자 확인:
- 사용자 피드백 수집
- 문제 즉시 대응
```

---

**[6단계: 교훈 (Lessons Learned)] ★★★**

```
사후 분석 및 개선
"같은 실수를 반복하지 않기 위해"
```

**주요 활동:**

**A. 사후 검토 회의**
```
Post-Incident Review:

참석자:
- CSIRT 전원
- 경영진
- 관련 부서장
- 외부 전문가 (필요시)

논의 사항:
□ 무엇이 발생했는가?
□ 왜 발생했는가?
□ 무엇이 잘 되었는가?
□ 무엇이 잘못되었는가?
□ 무엇을 개선할 것인가?

타임라인 검토:
- 최초 침입 시점
- 탐지 시점
- 대응 시작 시점
- 억제 완료 시점
- 복구 완료 시점
```

**B. 최종 보고서**
```
상세 문서화:

보고서 구성:

1. 개요 (Executive Summary)
   - 사고 요약
   - 영향 범위
   - 주요 조치
   - 결과

2. 사고 상세
   - 타임라인
   - 공격 벡터
   - 공격자 TTP
   - 피해 내역

3. 대응 활동
   - 각 단계별 조치
   - 의사결정 근거
   - 사용된 도구

4. 근본 원인 분석 (RCA)
   - 기술적 원인
   - 관리적 원인
   - 인적 원인

5. 교훈 및 권고사항
   - 정책 개선
   - 기술 강화
   - 프로세스 개선
   - 교육 필요

6. 비용 산정
   - 직접 피해액
   - 복구 비용
   - 기회 비용
   - 명성 손실
```

**C. 개선 조치**
```
실행 계획:

정책 업데이트:
- 사고 대응 계획 수정
- 보안 정책 강화
- 백업 정책 개선

기술적 통제:
- 탐지 규칙 추가
- 방화벽 정책 업데이트
- 모니터링 강화
- 추가 보안 솔루션 도입

프로세스 개선:
- 대응 절차 보완
- 에스컬레이션 경로 개선
- 의사소통 프로세스

교육 강화:
- 직원 보안 인식 교육
- 대응 팀 기술 교육
- 모의 훈련 계획
```

**D. 지식 공유**
```
조직 학습:

내부 공유:
- 전 직원 대상 공지
- 부서별 맞춤 교육
- 사례 연구

외부 공유:
- 보안 커뮤니티
- KISA 정보 공유
- 컨퍼런스 발표
  (민감 정보 제외)
```

**E. 지속적 개선**
```
순환 구조:

개선 사항 → [1. 준비] 단계 반영
      ↓
다음 사고 대응 시 적용
      ↓
더 나은 대응
      ↓
교훈 축적
```

---

**[침해사고 대응 성공 요인]**

```
1. 사전 준비 ★★★
   - "계획된 대응은 성공의 80%"
   - 평상시 훈련과 도구 준비

2. 빠른 탐지

## 3. 디지털 포렌식

### 문제 3-1: 디지털 포렌식의 4가지 원칙을 설명하고, 증거 수집 순서를 휘발성에 따라 나열하시오 (12점) ★★★

#### ✅ 모범 답안:

**[디지털 포렌식 정의]**

```
Digital Forensics:
디지털 증거를 수집, 보존, 분석하여
법정에서 사용 가능한 형태로 제시하는 과학적 절차

목적:
- 사고 원인 규명
- 범인 특정
- 법적 증거 확보
- 재발 방지
```

**[디지털 포렌식 4대 원칙] ★★★**

**1. 정당성 원칙 (Legitimacy) ★★★**

```
정의:
적법한 절차를 거쳐 증거를 수집해야 함

요구사항:

법적 근거:
- 수사 영장
- 압수 수색 영장
- 동의서
- 긴급 상황 예외

권한:
- 증거 수집 권한 확보
- 접근 권한 확인
- 관할권 확인

절차:
- 법정 절차 준수
- 규정 준수 (개인정보보호법 등)
- 문서화

위반 시:
- 증거 능력 상실
- 법정 채택 불가
- "독나무 열매" 원칙
  (Fruit of the Poisonous Tree)
```

**예시:**
```
적법:
- 경찰이 영장으로 압수
- 회사가 자사 시스템 조사 (동의서)
- 긴급 상황 (테러, 인명)

위법:
- 영장 없이 타인 PC 조사
- 동의 없이 개인 이메일 수집
- 권한 없는 네트워크 침투
```

---

**2. 무결성 원칙 (Integrity) ★★★**

```
정의:
원본 증거가 변조되지 않았음을 보장

위협:
- 고의적 변조
- 실수로 인한 수정
- 시스템 자동 변경

보장 방법:

A. 원본 보호 ★★★
   - 원본은 절대 직접 조사 금지
   - Write Blocker 사용
   - 읽기 전용 마운트

B. 이미징 (복제)
   ```
   원본 디스크 → [Write Blocker] → 이미징 → 분석용 복사본

   도구:
   - dd (Linux)
   - FTK Imager
   - EnCase
   ```

C. 해시 값 계산 ★★★
   ```bash
   # 원본 해시 계산
   md5sum /dev/sda > original.md5
   sha256sum /dev/sda > original.sha256

   # 복사본 해시 계산
   md5sum image.dd > copy.md5

   # 비교
   diff original.md5 copy.md5
   → 일치하면 무결성 보장
   ```

D. 보관
   - 물리적 보안 (잠금 장치)
   - 접근 통제
   - 봉인 (Seal)
```

**검증:**
```
법정에서:
"이 증거가 수집 당시와 동일함을 어떻게 증명하는가?"

답변:
"수집 시 SHA-256 해시: A1B2C3...
 현재 해시: A1B2C3...
 일치하므로 변조되지 않았습니다."
```

---

**3. 연계 보관성 원칙 (Chain of Custody) ★★★**

```
정의:
증거의 모든 이동 경로와 처리 과정을 문서화

목적:
- 증거 추적 가능
- 책임 소재 명확
- 법정 신뢰성 확보

기록 사항:

□ 누가 (Who)
  - 수집자
  - 인계자
  - 인수자
  - 분석자

□ 무엇을 (What)
  - 증거물 설명
  - 시리얼 번호
  - 해시 값

□ 언제 (When)
  - 수집 일시
  - 인계 일시
  - 분석 일시

□ 어디서 (Where)
  - 수집 장소
  - 보관 장소
  - 분석 장소

□ 왜 (Why)
  - 수집 목적
  - 이동 사유

□ 어떻게 (How)
  - 수집 방법
  - 포장 방법
  - 운송 방법
```

**CoC 양식 예시:**
```
┌────────────────────────────────────┐
│  증거물 관리 대장                   │
├────────────────────────────────────┤
│ 사건번호: 2024-001                 │
│ 증거번호: E-001                    │
│ 증거물: Dell Latitude E7470        │
│ S/N: ABCD1234                      │
│ 해시: sha256:A1B2C3...             │
├────────────────────────────────────┤
│ 일시        │ 담당자  │ 행위  │ 서명│
├────────────────────────────────────┤
│ 2024-01-10  │ 홍길동  │ 수집  │ ✓ │
│ 10:00       │         │       │   │
├────────────────────────────────────┤
│ 2024-01-10  │ 김철수  │ 인수  │ ✓ │
│ 14:00       │         │       │   │
├────────────────────────────────────┤
│ 2024-01-11  │ 이영희  │ 분석  │ ✓ │
│ 09:00       │         │       │   │
└────────────────────────────────────┘
```

**중요성:**
```
CoC가 끊어지면:
- 증거 신뢰성 의심
- "증거가 바뀌었을 수 있다"
- 법정 채택 거부 가능
```

---

**4. 재현 가능성 원칙 (Reproducibility) ★★★**

```
정의:
동일한 절차로 동일한 결과를 얻을 수 있어야 함

요구사항:

A. 상세한 문서화
   ```
   분석 보고서에 포함:
   - 사용한 도구 (버전 포함)
   - 실행 명령어
   - 설정 값
   - 분석 과정
   - 중간 결과
   - 최종 결과
   ```

B. 표준 도구 사용
   - 검증된 도구
   - 법정 인정 도구
   - 오픈 소스 (검증 가능)

C. 과학적 방법
   - 가설 수립
   - 테스트
   - 검증
   - 반복

검증:
```
다른 전문가가 동일 절차로:
→ 동일한 결과 도출
→ 재현 성공
→ 증거 신뢰성 확보
```

**예시:**
```
보고서:
"악성코드 sample.exe 분석

도구: IDA Pro 7.5
명령어: ida64 -A sample.exe
설정: Default
결과: 0x401000 주소에 악성 행동 확인

재현:
다른 분석가가 동일 도구, 동일 설정으로
→ 동일한 0x401000 주소에서 악성 행동 확인"
```

---

**[증거 수집 순서 - 휘발성 순서] ★★★**

```
RFC 3227: Guidelines for Evidence Collection and Archiving

원칙:
"휘발성이 높은 것부터 수집"
(Most Volatile First)

이유:
- 시스템 종료 시 손실
- 시간 경과 시 변경
- 덮어쓰기 위험
```

**휘발성 순서 (높음 → 낮음):**

**1. CPU 레지스터, 캐시 ★★★**
```
위치: CPU 내부
수명: 나노초~마이크로초
수집: 거의 불가능 (특수 장비 필요)
참고: 일반 포렌식에서는 생략
```

**2. 메모리 (RAM) ★★★**
```
위치: 물리 메모리
수명: 전원 off 시 즉시 손실
