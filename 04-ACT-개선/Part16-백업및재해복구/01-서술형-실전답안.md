## 1. 재해복구 목표

### 문제 1. RPO와 RTO 개념 (15점) ★★★

**문제**:
재해복구 계획 수립 시 고려해야 하는 RPO와 RTO의 개념과 차이점을 설명하시오. (15점)

**✅ 모범 답안**:

#### RPO (Recovery Point Objective) - 7점 ★★★

**정의**:
```
복구 목표 시점
재해 발생 시 데이터 손실을 허용할 수 있는 최대 시간
```

**상세 설명**:
```
RPO = 재해 발생 시점 - 복구 가능한 데이터 시점
```

**예시**:
```
RPO = 1시간인 경우:
- 재해 발생: 오후 3시
- 복구 가능한 데이터: 오후 2시까지의 데이터
- 데이터 손실: 최대 1시간분
```

**RPO에 따른 백업 전략**:

**RPO = 0 (데이터 손실 불가)**: ★★★
```
- 실시간 동기화 (Synchronous Replication)
- 미러링 (Mirroring)
- 핫 사이트 (Hot Site)
- RAID 구성

예: 금융권 거래 시스템, 의료 기록
```

**RPO = 1시간**:
```
- 시간 단위 백업
- 증분 백업 (Incremental Backup)
- 웜 사이트 (Warm Site)

예: 전자상거래, 온라인 서비스
```

**RPO = 24시간**:
```
- 일 단위 백업
- 전체 백업 (Full Backup)
- 콜드 사이트 (Cold Site)

예: 일반 업무 데이터, 보고서
```

**비용과의 관계**:
```
RPO ↓ (짧을수록) → 비용 ↑
RPO ↑ (길수록) → 비용 ↓
```

#### RTO (Recovery Time Objective) - 7점 ★★★

**정의**:
```
복구 목표 시간
재해 발생 후 시스템을 복구하여 정상 운영까지 걸리는 최대 허용 시간
```

**상세 설명**:
```
RTO = 서비스 재개 시점 - 재해 발생 시점
```

**예시**:
```
RTO = 4시간인 경우:
- 재해 발생: 오후 3시
- 서비스 재개: 오후 7시까지
- 최대 중단 허용 시간: 4시간
```

**RTO에 따른 복구 전략**:

**RTO = 즉시 (거의 0에 가까움)**: ★★★
```
- 핫 사이트 (Hot Site)
- 실시간 페일오버 (Failover)
- 이중화 (Redundancy)
- Active-Active 구성

예: 은행 시스템, 911 긴급 서비스
비용: 매우 높음
```

**RTO = 수 시간**:
```
- 웜 사이트 (Warm Site)
- Active-Standby 구성
- 자동 복구 시스템

예: 기업 이메일, ERP 시스템
비용: 중간
```

**RTO = 수일 ~ 수주**: ★★
```
- 콜드 사이트 (Cold Site)
- 수동 복구
- 테이프 백업 복원

예: 보관용 데이터, 비중요 시스템
비용: 낮음
```

**비용과의 관계**:
```
RTO ↓ (짧을수록) → 비용 ↑
RTO ↑ (길수록) → 비용 ↓
```

#### RPO vs RTO 비교 - 1점

| 구분 | RPO | RTO |
|-----|-----|-----|
| 정의 | 복구 목표 시점 | 복구 목표 시간 |
| 의미 | 데이터 손실 허용 범위 | 시스템 중단 허용 시간 |
| 측정 | 시간 단위 (데이터 손실) | 시간 단위 (서비스 중단) |
| 초점 | 데이터 ★★★ | 시스템 가용성 ★★★ |
| 영향 요소 | 백업 주기 | 복구 절차, 인프라 |

**관계**:
```
일반적으로 RPO ≤ RTO
(데이터 복구 후 시스템 복구)
```

---

**채점 기준**:
- RPO 정의 및 의미 (4점)
- RTO 정의 및 의미 (4점)
- 각각의 예시 또는 전략 (4점)
- RPO와 RTO 비교 (3점)

**핵심 요약**:
```
RPO (Recovery Point Objective): ★★★
- 복구 목표 시점
- 데이터 손실 허용 범위
- RPO 짧을수록 비용 ↑

RTO (Recovery Time Objective): ★★★
- 복구 목표 시간
- 시스템 중단 허용 시간
- RTO 짧을수록 비용 ↑

관계: RPO ≤ RTO (일반적)
```

**암기 팁**:
```
"RPO = Point (시점, 데이터)"
"RTO = Time (시간, 시스템)"
```

## 2. 백업 사이트

### 문제 2. 백업 사이트 유형 (18점) ★★★

**문제**:
재해복구를 위한 백업 사이트의 3가지 유형(핫 사이트, 웜 사이트, 콜드 사이트)을 비교하여 설명하시오. (18점)

**✅ 모범 답안**:

#### 1. 핫 사이트 (Hot Site) - 6점 ★★★

**정의**:
```
주 시스템과 동일한 환경으로 구축되어
실시간으로 데이터를 동기화하는 백업 사이트
```

**특징**:
```
1. 실시간 동기화 ★★★
   - 주 시스템과 백업 시스템 동시 운영
   - Synchronous Replication
   - 미러링 (Mirroring)

2. 즉시 전환 가능
   - 재해 발생 시 즉시 페일오버
   - 자동 전환 (Automatic Failover)
   - 사용자 인지 불가

3. 완전한 복제
   - 하드웨어, 소프트웨어, 네트워크 동일
   - 데이터, 애플리케이션 모두 복제
   - 최신 상태 유지
```

**RPO/RTO**:
```
RPO: 거의 0 (실시간 동기화) ★★★
RTO: 즉시 ~ 수분 ★★★
```

**비용**:
```
매우 높음 (주 시스템 비용의 80~100%) ★★
```

**적용 사례**:
```
- 은행 거래 시스템
- 증권 거래소
- 통신사 핵심 인프라
- 119/112 긴급 서비스
- 항공 관제 시스템
```

**장점**:
```
✅ 데이터 손실 최소 (RPO ≈ 0)
✅ 서비스 중단 최소 (RTO ≈ 0)
✅ 높은 가용성
```

**단점**:
```
❌ 매우 높은 비용
❌ 복잡한 관리
❌ 높은 운영 비용
```

#### 2. 웜 사이트 (Warm Site) - 6점 ★★★

**정의**:
```
주요 시스템과 장비는 구축되어 있으나
데이터 동기화가 주기적으로 이루어지는 백업 사이트
```

**특징**:
```
1. 주기적 동기화 ★★★
   - 시간/일 단위 백업
   - Asynchronous Replication
   - 증분 백업 (Incremental Backup)

2. 수 시간 내 전환
   - 재해 발생 시 설정 및 데이터 복원 필요
   - 반자동 전환 (Semi-Automatic)
   - 일부 수동 작업 필요

3. 부분 복제
   - 주요 하드웨어 구축
   - 소프트웨어 사전 설치
   - 데이터는 주기적 백업
```

**RPO/RTO**:
```
RPO: 수 시간 ~ 24시간 ★★★
RTO: 수 시간 ~ 1일 ★★★
```

**비용**:
```
중간 (주 시스템 비용의 30~50%) ★★
```

**적용 사례**:
```
- 기업 ERP 시스템
- 이메일 서버
- 전자상거래 사이트
- 온라인 게임 서버
- 일반 웹 서비스
```

**장점**:
```
✅ 적절한 비용 대비 효과
✅ 합리적인 복구 시간
✅ 중요 업무 대부분 커버
```

**단점**:
```
❌ 일부 데이터 손실 가능
❌ 복구에 수 시간 소요
❌ 수동 작업 필요
```

#### 3. 콜드 사이트 (Cold Site) - 6점 ★★

**정의**:
```
기본 인프라(전력, 공조, 네트워크)만 갖춘 빈 공간
재해 발생 시 장비 설치 및 데이터 복원 필요
```

**특징**:
```
1. 기본 인프라만 제공 ★★★
   - 전력, 냉방, 공간
   - 네트워크 회선
   - 장비는 미설치

2. 장기 복구 시간
   - 재해 발생 시 장비 구매/설치
   - 데이터 복원 (테이프 백업 등)
   - 전체 수동 복구

3. 최소 투자
   - 공간 임대 비용만 발생
   - 필요 시 장비 구매
   - 평상시 유지비 낮음
```

**RPO/RTO**:
```
RPO: 24시간 ~ 수일 ★★
RTO: 수일 ~ 수주 ★★★
```

**비용**:
```
낮음 (주 시스템 비용의 5~15%) ★★★
```

**적용 사례**:
```
- 보관용 데이터
- 비중요 업무 시스템
- 개발/테스트 환경
- 장기 보관 데이터
```

**장점**:
```
✅ 낮은 비용
✅ 공간 확보 (재해 대응 가능)
```

**단점**:
```
❌ 긴 복구 시간
❌ 상당한 데이터 손실
❌ 장비 구매/설치 시간 소요
❌ 중요 업무에 부적합
```

#### 비교 요약표

| 구분 | 핫 사이트 | 웜 사이트 | 콜드 사이트 |
|-----|----------|----------|------------|
| **준비 상태** | 완전 가동 ★★★ | 부분 가동 | 빈 공간 |
| **데이터 동기화** | 실시간 ★★★ | 주기적 | 없음 |
| **RPO** | 거의 0 | 수 시간 | 수일 |
| **RTO** | 즉시 ~ 수분 ★★★ | 수 시간 | 수일 ~ 수주 ★★★ |
| **비용** | 매우 높음 (80~100%) | 중간 (30~50%) | 낮음 (5~15%) ★★ |
| **장비** | 모두 설치 | 주요 장비 설치 | 미설치 |
| **전환** | 자동 | 반자동 | 수동 |
| **적합 업무** | 핵심 업무 | 중요 업무 | 비중요 업무 |

---

**채점 기준**:
- 3가지 사이트 유형별 정의 (6점)
- 각 사이트의 RPO/RTO (6점)
- 비용 및 특징 비교 (6점)

**핵심 요약**:
```
핫 사이트 (Hot Site): ★★★
- 실시간 동기화
- RPO ≈ 0, RTO ≈ 즉시
- 비용 매우 높음 (80~100%)
- 금융, 통신 핵심 시스템

웜 사이트 (Warm Site): ★★★
- 주기적 동기화
- RPO = 수시간, RTO = 수시간
- 비용 중간 (30~50%)
- 기업 ERP, 이메일

콜드 사이트 (Cold Site): ★★
- 기본 인프라만
- RPO = 수일, RTO = 수일~수주
- 비용 낮음 (5~15%)
- 비중요 업무
```

**암기 팁**:
```
"핫(Hot) = 뜨거움 = 즉시 = 비용 높음"
"웜(Warm) = 따뜻함 = 수시간 = 비용 중간"
"콜드(Cold) = 차가움 = 수일 = 비용 낮음"

비용: Hot(100) > Warm(50) > Cold(10)
속도: Hot(즉시) > Warm(시간) > Cold(일)
```

## 3. 비즈니스 연속성

### 문제 3. BCP와 DRP 개념 (15점) ★★★

**문제**:
BCP(Business Continuity Plan)와 DRP(Disaster Recovery Plan)의 개념과 차이점을 설명하시오. (15점)

**✅ 모범 답안**:

#### BCP (Business Continuity Plan) - 7점 ★★★

**정의**:
```
비즈니스 연속성 계획
재해나 중대한 사고 발생 시에도
핵심 업무를 지속적으로 수행하기 위한 전사적 계획
```

**목적**:
```
비즈니스 중단 최소화
기업의 생존 보장
```

**범위**: ★★★
```
전사적 관점 (Organization-wide)

포함 영역:
1. 인력 (People)
   - 핵심 인력 식별
   - 대체 인력 확보
   - 비상 연락망
   - 역할 및 책임

2. 프로세스 (Process)
   - 핵심 업무 프로세스
   - 대체 프로세스
   - 업무 우선순위

3. 기술 (Technology)
   - IT 시스템
   - 데이터
   - 통신

4. 시설 (Facility)
   - 대체 사무실
   - 원격 근무

5. 협력사 (Vendor)
   - 공급망 관리
   - 대체 협력사
```

**주요 활동**:
```
1. 업무영향분석 (BIA: Business Impact Analysis) ★★★
   - 핵심 업무 식별
   - 업무 중단 영향 분석
   - 최대 허용 중단 시간 (MTD: Maximum Tolerable Downtime)
   - RPO/RTO 설정

2. 리스크 평가
   - 재해 시나리오 분석
   - 취약점 식별

3. 연속성 전략 수립
   - 핵심 업무 우선순위
   - 복구 전략
   - 대체 방안

4. 계획 수립 및 문서화
   - BCP 문서 작성
   - 비상 연락망
   - 복구 절차

5. 훈련 및 테스트 ★★★
   - 정기 훈련 (연 1~2회)
   - 시뮬레이션
   - 계획 개선

6. 유지 보수
   - 정기 검토 및 업데이트
   - 변경 사항 반영
```

#### DRP (Disaster Recovery Plan) - 7점 ★★★

**정의**:
```
재해복구 계획
재해 발생 시 IT 시스템과 데이터를 복구하여
정상 운영 상태로 복원하기 위한 기술적 계획
```

**목적**:
```
IT 시스템 복구
데이터 복원
```

**범위**: ★★★
```
IT 중심 (IT-focused)

포함 영역:
1. 시스템 복구
   - 서버 복구
   - 네트워크 복구
   - 스토리지 복구

2. 데이터 복구 ★★★
   - 백업 데이터 복원
   - 데이터 무결성 검증

3. 애플리케이션 복구
   - 운영 시스템 복구
   - 설정 복원

4. 인프라 복구
   - 백업 사이트 전환
   - 네트워크 전환
```

**주요 활동**:
```
1. 백업 전략 수립 ★★★
   - 백업 방법 (전체/증분/차등)
   - 백업 주기
   - 백업 매체
   - 오프사이트 백업

2. 복구 사이트 구축
   - 핫/웜/콜드 사이트 선택
   - 백업 센터 구축

3. RPO/RTO 설정 ★★★
   - 복구 목표 시점 (RPO)
   - 복구 목표 시간 (RTO)

4. 복구 절차 문서화
   - 시스템별 복구 절차
   - 체크리스트
   - 우선순위

5. 복구 훈련 ★★★
   - 정기 복구 테스트 (연 2회 이상)
   - 백업 복원 테스트
   - 페일오버 테스트

6. 모니터링 및 유지보수
   - 백업 성공 여부 확인
   - 백업 매체 관리
   - 계획 업데이트
```

#### BCP vs DRP 비교 - 1점

| 구분 | BCP | DRP |
|-----|-----|-----|
| **정의** | 비즈니스 연속성 계획 | 재해복구 계획 |
| **범위** | 전사적 (조직 전체) ★★★ | IT 시스템 중심 ★★★ |
| **목적** | 업무 지속 | 시스템 복구 |
| **초점** | 비즈니스 프로세스 | IT 인프라, 데이터 |
| **포함** | 인력, 프로세스, 시설, 기술 | 시스템, 데이터, 네트워크 |
| **책임자** | 경영진, 부서장 | IT 부서, 보안 담당자 |
| **관계** | 상위 개념 ★★★ | 하위 개념 (BCP의 일부) |

**관계**: ★★★
```
BCP ⊃ DRP

BCP (전사적 계획)
 ├── 인력 계획
 ├── 시설 계획
 ├── 프로세스 계획
 └── DRP (IT 복구 계획) ★★★
      ├── 시스템 복구
      ├── 데이터 복구
      └── 네트워크 복구
```

---

**채점 기준**:
- BCP 정의 및 범위 (4점)
- DRP 정의 및 범위 (4점)
- BCP와 DRP의 차이점 (4점)
- BCP와 DRP의 관계 (3점)

**핵심 요약**:
```
BCP (Business Continuity Plan): ★★★
- 비즈니스 연속성 계획
- 전사적 관점 (인력, 프로세스, 시설, 기술)
- 업무 지속이 목적
- 상위 개념

DRP (Disaster Recovery Plan): ★★★
- 재해복구 계획
- IT 중심 (시스템, 데이터, 네트워크)
- 시스템 복구가 목적
- BCP의 일부 (하위 개념)

관계: BCP ⊃ DRP
```

**암기 팁**:
```
"BCP = Business (비즈니스 전체)"
"DRP = Disaster (재해, IT 복구)"

"BCP가 큰 그림, DRP는 IT 부분"
```

## 4. 백업 전략

### 문제 4. 백업 방법 (18점) ★★★

**문제**:
데이터 백업의 3가지 주요 방법(전체 백업, 증분 백업, 차등 백업)을 비교하여 설명하시오. (18점)

**✅ 모범 답안**:

#### 1. 전체 백업 (Full Backup) - 6점 ★★★

**정의**:
```
모든 데이터를 백업하는 방식
매번 전체 데이터를 복사
```

**방법**:
```
전체 데이터 → 백업

일요일: 전체 A, B, C, D
월요일: 전체 A, B, C, D, E
화요일: 전체 A, B, C, D, E, F
```

**특징**:
```
1. 백업 시간: 가장 김 ★★★
2. 백업 용량: 가장 많음 ★★★
3. 복구 시간: 가장 빠름 ★★★
4. 복구 복잡도: 가장 단순 (1개 백업만 필요)
```

**Archive Bit (보관 비트)**:
```
- 백업 후: 모든 파일의 Archive Bit OFF
```

**복구 절차**:
```
1단계: 가장 최근 전체 백업 복원
끝!
```

**장점**:
```
✅ 복구가 간단하고 빠름
✅ 1개의 백업본만 필요
✅ 관리 용이
```

**단점**:
```
❌ 백업 시간이 오래 걸림
❌ 저장 공간 많이 필요
❌ 네트워크 대역폭 소모
```

**사용 시나리오**:
```
- 주 1회 전체 백업 (일요일)
- 데이터 양이 적은 경우
- 빠른 복구가 중요한 경우
```

#### 2. 증분 백업 (Incremental Backup) - 6점 ★★★

**정의**:
```
마지막 백업(전체 또는 증분) 이후 변경된 데이터만 백업
```

**방법**:
```
일요일: 전체 A, B, C, D
월요일: 증분 E (월요일 변경분만)
화요일: 증분 F (화요일 변경분만)
수요일: 증분 G, H (수요일 변경분만)
```

**특징**:
```
1. 백업 시간: 가장 빠름 ★★★
2. 백업 용량: 가장 적음 ★★★
3. 복구 시간: 중간
4. 복구 복잡도: 복잡 (여러 백업 필요)
```

**Archive Bit**:
```
- 백업 후: 백업된 파일의 Archive Bit OFF
```

**복구 절차**:
```
1단계: 마지막 전체 백업 복원
2단계: 첫 번째 증분 백업 복원
3단계: 두 번째 증분 백업 복원
...
N단계: 마지막 증분 백업 복원

예: 수요일 복구 시
→ 일요일 전체 + 월요일 증분 + 화요일 증분 + 수요일 증분
```

**장점**:
```
✅ 백업 시간이 빠름
✅ 저장 공간 절약
✅ 네트워크 부하 적음
```

**단점**:
```
❌ 복구가 복잡하고 시간 소요
❌ 여러 개의 백업본 필요
❌ 중간 백업 손상 시 복구 불가능
```

**사용 시나리오**:
```
- 일 단위 증분 백업
- 데이터 변경이 많은 경우
- 저장 공간이 부족한 경우
```

#### 3. 차등 백업 (Differential Backup) - 6점 ★★★

**정의**:
```
마지막 전체 백업 이후 변경된 모든 데이터를 백업
(증분과 달리 전체 백업 기준으로만 비교)
```

**방법**:
```
일요일: 전체 A, B, C, D
월요일: 차등 E (일요일 이후 변경분)
화요일: 차등 E, F (일요일 이후 모든 변경분)
수요일: 차등 E, F, G, H (일요일 이후 모든 변경분)
```

**특징**:
```
1. 백업 시간: 중간 ★★★
2. 백업 용량: 중간 (점점 증가)
3. 복구 시간: 빠름
4. 복구 복잡도: 단순 (전체 + 차등 1개)
```

**Archive Bit**:
```
- 백업 후: Archive Bit OFF 하지 않음 (계속 ON)
- 전체 백업만 Archive Bit OFF
```

**복구 절차**:
```
1단계: 마지막 전체 백업 복원
2단계: 가장 최근 차등 백업 복원
끝!

예: 수요일 복구 시
→ 일요일 전체 + 수요일 차등
```

**장점**:
```
✅ 복구가 비교적 간단 (2개 백업만)
✅ 증분보다 복구 빠름
✅ 전체 백업보다 백업 빠름
```

**단점**:
```
❌ 시간이 지날수록 백업 용량 증가
❌ 전체 백업보다 복구 느림
❌ 저장 공간이 증분보다 많이 필요
```

**사용 시나리오**:
```
- 주 1회 전체 + 일 단위 차등
- 중간 수준의 데이터 변경
- 복구 편의성과 백업 속도의 균형
```

#### 비교 요약표

| 구분 | 전체 백업 | 증분 백업 | 차등 백업 |
|-----|----------|----------|----------|
| **백업 시간** | 가장 김 ★ | 가장 빠름 ★★★ | 중간 ★★ |
| **백업 용량** | 가장 많음 ★ | 가장 적음 ★★★ | 중간 (증가) ★★ |
| **복구 시간** | 가장 빠름 ★★★ | 중간 ★ | 빠름 ★★ |
| **복구 복잡도** | 단순 (1개) ★★★ | 복잡 (N개) ★ | 단순 (2개) ★★ |
| **Archive Bit** | 모두 OFF | 백업분 OFF | ON 유지 |
| **복구 필요 백업** | 전체 1개 | 전체 + 모든 증분 | 전체 + 최신 차등 |
| **사용 빈도** | 주 1회 | 일 1회 | 일 1회 |

#### 백업 전략 예시

**전략 1: 전체 백업만** ★
```
일요일: 전체
월요일: 전체
화요일: 전체
...

장점: 복구 간단
단점: 시간/공간 많이 소요
```

**전략 2: 전체 + 증분** ★★★ (가장 일반적)
```
일요일: 전체
월요일: 증분
화요일: 증분
수요일: 증분
목요일: 증분
금요일: 증분
토요일: 증분

장점: 저장 공간 절약
단점: 복구 복잡
```

**전략 3: 전체 + 차등** ★★
```
일요일: 전체
월요일: 차등
화요일: 차등
수요일: 차등
목요일: 차등
금요일: 차등
토요일: 차등

장점: 복구와 백업의 균형
단점: 주말로 갈수록 백업 용량 증가
```

**전략 4: 전체 + 차등 + 증분** ★★
```
일요일: 전체
월요일: 차등
화요일: 증분 (월요일 차등 기준)
수요일: 차등
목요일: 증분 (수요일 차등 기준)
금요일: 차등
토요일: 증분 (금요일 차등 기준)

장점: 유연성
단점: 관리 복잡
```

---

**채점 기준**:
- 3가지 백업 방법 각각의 정의 (6점)
- 각 방법의 백업 시간, 용량, 복구 특성 (6점)
- 복구 절차 또는 사용 시나리오 (6점)

**핵심 요약**:
```
전체 백업 (Full): ★★★
- 모든 데이터 백업
- 백업: 김, 복구: 빠름
- 복구: 전체 1개만 필요

증분 백업 (Incremental): ★★★
- 마지막 백업 이후 변경분만
- 백업: 빠름, 복구: 복잡
- 복구: 전체 + 모든 증분 필요

차등 백업 (Differential): ★★★
- 마지막 전체 이후 모든 변경분
- 백업: 중간, 복구: 비교적 빠름
- 복구: 전체 + 최신 차등 필요

일반적 전략: 주 1회 전체 + 일 단위 증분/차등
```

**암기 팁**:
```
"전체 = 복구 1개 (간단)"
"증분 = 변경분만 (저장 효율)"
"차등 = 전체 기준 누적 (중간)"

복구 개수: 전체(1) < 차등(2) < 증분(N)
백업 속도: 증분 > 차등 > 전체
```

### 문제 5. 3-2-1-1 백업 규칙 (12점) ★★

**문제**:
데이터 보호를 위한 3-2-1-1 백업 규칙을 설명하시오. (12점)

**✅ 모범 답안**:

#### 3-2-1-1 백업 규칙 - 12점 ★★★

**정의**:
```
안전한 데이터 백업을 위한 모범 사례 규칙
```

#### 1. 3 - 3개의 복사본 - 3점 ★★★

**의미**:
```
최소 3개의 데이터 복사본 유지
```

**구성**:
```
1. 원본 (Original)
   - 운영 시스템의 원본 데이터

2. 백업본 1 (Backup Copy 1)
   - 로컬 백업

3. 백업본 2 (Backup Copy 2)
   - 원격 백업 또는 오프사이트 백업
```

**이유**:
```
- 단일 장애 지점 제거
- 원본 손상 시 백업 2개 보유
- 백업 1개 손상 시에도 다른 백업 가용
```

**예시**:
```
1. 원본: 운영 서버 하드디스크
2. 백업 1: 사내 NAS 백업
3. 백업 2: 클라우드 백업
```

#### 2. 2 - 2가지 다른 매체 - 3점 ★★★

**의미**:
```
최소 2가지 다른 유형의 저장 매체 사용
```

**매체 유형**:
```
1. HDD (Hard Disk Drive)
2. SSD (Solid State Drive)
3. 테이프 (Tape)
4. 광학 디스크 (DVD, Blu-ray)
5. 클라우드 스토리지
```

**이유**:
```
- 특정 매체 유형의 결함 대비
- 다양한 매체의 장점 활용
- 동일 매체 결함 시 데이터 손실 방지
```

**예시**:
```
1. 매체 1: HDD (로컬 백업)
2. 매체 2: 클라우드 (원격 백업)

또는

1. 매체 1: SSD (빠른 복구용)
2. 매체 2: 테이프 (장기 보관용)
```

**잘못된 예**:
```
❌ 모두 HDD (같은 매체)
❌ 모두 SSD (같은 매체)
```

#### 3. 1 - 1개는 오프사이트 - 3점 ★★★

**의미**:
```
최소 1개의 백업은 물리적으로 떨어진 장소에 보관
```

**오프사이트 옵션**:
```
1. 원격 데이터센터
2. 클라우드 스토리지 (AWS S3, Azure Blob, Google Cloud Storage)
3. 다른 지사/사무소
4. 전문 백업 보관 업체
```

**이유**:
```
- 재해 발생 시 데이터 보호 (화재, 홍수, 지진)
- 물리적 도난/파손 대비
- 지역적 재난 대응
```

**거리 권장사항**:
```
- 최소 100km 이상 떨어진 곳
- 다른 재해 영향권 밖
```

**예시**:
```
본사: 서울
- 원본: 서울 본사
- 백업 1: 서울 본사 백업실
- 백업 2: 부산 데이터센터 ★★★

또는

- 원본: 사내 서버
- 백업 1: 사내 NAS
- 백업 2: AWS S3 (해외 리전) ★★★
```

#### 4. 1 - 1개는 오프라인 (Air-Gap) - 3점 ★★★

**의미**:
```
최소 1개의 백업은 네트워크에서 완전히 분리 (Air-Gap)
```

**오프라인 백업 방법**:
```
1. 테이프 백업 후 금고 보관
2. 외장 하드디스크 분리 보관
3. 불변 스토리지 (Immutable Storage)
4. WORM (Write Once Read Many) 매체
```

**이유**:
```
- 랜섬웨어 공격 대응 ★★★
  (네트워크 연결 백업은 암호화 대상)
- 해킹/악성코드로부터 보호
- 논리적 오류 대응
```

**Air-Gap 백업 특징**:
```
✓ 네트워크 미연결
✓ 물리적으로 분리
✓ 수동 연결 시에만 접근 가능
✓ 자동 업데이트 불가 (보안 장점)
```

**예시**:
```
1. 일일 백업: 클라우드 (온라인)
2. 주간 백업: 테이프 → 금고 보관 (오프라인) ★★★
3. 월간 백업: 외장 HDD → 원격지 보관 (오프라인)
```

**랜섬웨어 시나리오**:
```
공격 발생:
❌ 원본: 암호화됨
❌ 백업 1 (NAS, 네트워크 연결): 암호화됨
✅ 백업 2 (테이프, 오프라인): 안전 ★★★
→ 백업 2로 복구 가능!
```

## 💡 파트 전체 핵심 요약

### RPO / RTO ★★★
```
RPO (Recovery Point Objective):
- 복구 목표 시점
- 데이터 손실 허용 범위
- RPO 짧을수록 비용 ↑

RTO (Recovery Time Objective):
- 복구 목표 시간
- 시스템 중단 허용 시간
- RTO 짧을수록 비용 ↑
```

### 백업 사이트 ★★★
```
핫 사이트 (Hot Site):
- 실시간 동기화, RPO≈0, RTO≈즉시
- 비용 높음 (80~100%)

웜 사이트 (Warm Site):
- 주기적 동기화, RPO=시간, RTO=시간
- 비용 중간 (30~50%)

콜드 사이트 (Cold Site):
- 기본 인프라만, RPO=일, RTO=일~주
- 비용 낮음 (5~15%)
```

### BCP / DRP ★★★
```
BCP (Business Continuity Plan):
- 비즈니스 연속성 계획
- 전사적 (인력, 프로세스, 시설, 기술)
- 상위 개념

DRP (Disaster Recovery Plan):
- 재해복구 계획
- IT 중심 (시스템, 데이터, 네트워크)
- BCP의 일부
```

### 백업 방법 ★★★
```
전체 백업: 모든 데이터, 복구 빠름
증분 백업: 변경분만, 백업 빠름, 복구 복잡
차등 백업: 전체 이후 모든 변경, 중간

복구 필요 백업 개수:
- 전체: 1개
- 차등: 2개 (전체 + 최신 차등)
- 증분: N개 (전체 + 모든 증분)
```

### 3-2-1-1 규칙 ★★★
```
3: 3개 복사본 (원본 + 백업 2)
2: 2가지 다른 매체
1: 1개는 오프사이트 (물리적 분리)
1: 1개는 오프라인 (Air-Gap, 랜섬웨어 대비)
```
