# 인증서 고정 (Certificate Pinning) - 모바일 보안

## 🔴 인증서 고정 (Certificate Pinning) 핵심 개념

### 정의
```
모바일 앱에 특정 인증서 또는 공개키를 하드코딩하여,
해당 인증서로만 서버와 통신하도록 제한하는 보안 기법

목적: MITM (중간자 공격) 방지
```

### 제거 가능한 위협
```
1. MITM (Man-In-The-Middle) 공격
   - 공격자가 가짜 인증서로 통신 가로채기 시도
   - 인증서 고정으로 신뢰된 인증서만 허용

2. 가짜 CA 인증서 공격
   - 사용자 기기에 악의적 루트 CA 설치
   - 정상 도메인에 대한 가짜 인증서 발급
   - 인증서 고정으로 특정 인증서만 신뢰

3. SSL Strip 공격 (일부 방어)
   - HTTPS → HTTP 다운그레이드 시도
   - 앱이 HTTPS 필수 + 인증서 고정으로 방어
```

## 📝 기출 유형 1: 인증서 고정 기본 개념 ★★★

### 문제 1-1 (2024년 실기)
```
모바일 인증서 고정에 대해 다음을 설명하시오.

ㄱ. 이 기법의 정의 및 제거할 수 있는 위협
ㄴ. 고정 대상 3가지
ㄷ. 우회 기법 2가지
```

**✅ 정답:**

**ㄱ. 정의 및 제거 위협**
```
정의:
모바일 앱에 특정 인증서 또는 공개키를 하드코딩하여,
해당 인증서로만 서버 통신을 허용하는 보안 기법.
시스템의 CA 저장소를 신뢰하지 않고 앱 자체적으로 인증서 검증.

제거 가능한 위협:
1. MITM (Man-In-The-Middle) 공격
   - 공격자가 중간에서 통신 가로채기 시도
   - 가짜 인증서 사용 차단

2. 가짜 CA 인증서 공격
   - 루트 CA 인증서 위조/설치 공격 방어
   - 시스템 CA 저장소 신뢰 X

3. SSL/TLS 다운그레이드 공격
   - HTTPS 강제 및 특정 인증서 검증
```

**ㄴ. 고정 대상 3가지**
```
1. 인증서 전체 (Certificate Pinning)
   - X.509 인증서 전체를 앱에 포함
   - 가장 엄격한 방법
   - 인증서 갱신 시 앱 업데이트 필요

2. 공개키 (Public Key Pinning)
   - 인증서의 공개키만 고정
   - 인증서 갱신 시에도 같은 키 사용 가능
   - 유연성 높음 (권장 방식)

3. 인증서 해시값 (Hash/Fingerprint Pinning)
   - SHA-256 해시값 고정
   - 저장 공간 효율적
   - 빠른 비교 가능

예시 (Android):
String pin = "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=";
```

**ㄷ. 우회 기법 2가지**
```
1. 리패키징 (Repackaging)
   공격 방법:
   - APK/IPA 파일 디컴파일
   - 인증서 검증 코드 제거 또는 수정
   - 재서명 후 재배포

   방어:
   - 코드 난독화 (ProGuard, R8)
   - 무결성 검사 (앱 서명 검증)
   - Root/Jailbreak 탐지

2. 런타임 후킹 (Runtime Hooking)
   공격 방법:
   - Frida, Xposed Framework 사용
   - 런타임에서 인증서 검증 함수 후킹
   - 검증 결과를 강제로 true 반환

   방어:
   - Anti-Frida 탐지
   - Root/Jailbreak 탐지
   - 동적 무결성 검사
   - 난독화 및 암호화

추가 우회 기법:
3. 프록시 도구 (Burp Suite, Charles Proxy)
   - 사용자가 직접 프록시 설정
   - 프록시 인증서를 신뢰된 CA로 설치
   - 방어: 프록시 탐지, VPN 탐지
```

## 📝 기출 유형 2: 인증서 고정 구현 ★★

### Android 구현 예시 (Network Security Configuration)

**res/xml/network_security_config.xml**
```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <domain-config>
        <domain includeSubdomains="true">example.com</domain>
        <pin-set expiration="2025-12-31">
            <!-- SHA-256 공개키 해시 -->
            <pin digest="SHA-256">7HIpactkIAq2Y49orFOOQKurWxmmSFZhBCoQYcRhJ3Y=</pin>
            <!-- 백업 핀 (인증서 갱신 대비) -->
            <pin digest="SHA-256">fwza0LRMXouZHRC8Ei+4PyuldPDcf3UKgO/04cDM1oE=</pin>
        </pin-set>
    </domain-config>
</network-security-config>
```

**AndroidManifest.xml**
```xml
<application
    android:networkSecurityConfig="@xml/network_security_config"
    ...>
</application>
```

---

### iOS 구현 예시 (Swift)

```swift
class PinningDelegate: NSObject, URLSessionDelegate {
    func urlSession(_ session: URLSession,
                    didReceive challenge: URLAuthenticationChallenge,
                    completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void) {

        // 서버 인증서 가져오기
        guard let serverTrust = challenge.protectionSpace.serverTrust,
              let certificate = SecTrustGetCertificateAtIndex(serverTrust, 0) else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }

        // 인증서 데이터 추출
        let serverCertificateData = SecCertificateCopyData(certificate) as Data

        // 앱에 포함된 인증서와 비교
        let pinnedCertificateData = loadPinnedCertificate()

        if serverCertificateData == pinnedCertificateData {
            let credential = URLCredential(trust: serverTrust)
            completionHandler(.useCredential, credential)
        } else {
            completionHandler(.cancelAuthenticationChallenge, nil)
        }
    }
}
```

## 📝 기출 유형 3: MITM 공격과 인증서 고정 ★★

### 문제 3-1
```
다음 시나리오에서 인증서 고정이 공격을 방어하는 원리를 설명하시오.

시나리오:
1. 공격자가 공용 Wi-Fi에 가짜 AP 설치
2. 사용자가 뱅킹 앱 실행
3. 공격자가 Burp Suite로 HTTPS 통신 가로채기 시도
4. 공격자의 가짜 인증서 제시
```

**✅ 답안:**
```
일반 앱 (인증서 고정 없음):
1. 앱이 서버 연결 시도
2. 공격자가 가짜 인증서 제시
3. 시스템 CA 저장소에서 검증
   → 공격자가 루트 CA 설치했다면 검증 성공
4. 앱이 가짜 인증서 신뢰
5. MITM 공격 성공 (통신 내용 노출)

인증서 고정 적용 앱:
1. 앱이 서버 연결 시도
2. 공격자가 가짜 인증서 제시
3. 앱이 인증서를 하드코딩된 핀(Pin)과 비교
   → 불일치 발견
4. 연결 거부, 사용자에게 경고
5. MITM 공격 차단

방어 원리:
- 시스템 CA 저장소를 신뢰하지 않음
- 앱에 포함된 특정 인증서/공개키만 신뢰
- 가짜 인증서는 핀과 불일치하여 즉시 탐지
```

## 🎯 인증서 고정 핵심 암기 카드

### 카드 1: 정의 및 목적
```
인증서 고정 (Certificate Pinning):
앱에 인증서/공개키 하드코딩 → 특정 인증서만 신뢰

목적: MITM 공격 방어

일반 앱: 시스템 CA 신뢰 (취약)
고정 앱: 특정 인증서만 신뢰 (안전)
```

### 카드 2: 고정 대상 3가지
```
1. Certificate (인증서 전체)
   - 엄격, 갱신 시 앱 업데이트 필요

2. Public Key (공개키) ★ 권장
   - 유연, 인증서 갱신해도 키 유지 가능

3. Hash (해시값)
   - 효율적, 빠른 비교
```

### 카드 3: 우회 기법
```
1. 리패키징 (Repackaging)
   - APK 디컴파일 → 핀 제거 → 재배포

2. 후킹 (Hooking)
   - Frida로 검증 함수 우회

방어:
- 난독화 (ProGuard)
- Root/Jailbreak 탐지
- Anti-Frida
```

### 카드 4: 장단점
```
장점:
+ MITM 공격 방어
+ 가짜 CA 인증서 무효화
+ 추가 보안 계층

단점:
- 인증서 갱신 복잡 (앱 업데이트 필요)
- 구현 복잡도 증가
- 우회 가능성 존재 (후킹)
```

## 📊 그림으로 이해하기

### MITM 공격 vs 인증서 고정
```
[일반 앱 - 인증서 고정 없음]

사용자 앱 ←→ 공격자 (가짜 인증서) ←→ 실제 서버
    │              ↑
    └─ 시스템 CA 검증
       → 가짜 CA 신뢰
       → 공격 성공!


[인증서 고정 적용 앱]

사용자 앱 ←X→ 공격자 (가짜 인증서)
    │
    └─ 앱 내장 핀과 비교
       → 불일치!
       → 연결 거부
       → 공격 차단!

사용자 앱 ←→ 실제 서버 (정상 인증서)
    │
    └─ 앱 내장 핀과 비교
       → 일치!
       → 연결 허용
```

### 인증서 고정 검증 흐름
```
[HTTPS 연결 시도]
        ↓
   서버 인증서 수신
        ↓
    ┌────────────────┐
    │ 인증서 고정     │
    │ 검증 시작      │
    └────────────────┘
        ↓
    ┌─────────┬─────────┐
    │ 핀 일치?│         │
    └─────────┴─────────┘
       ✓          ✗
       │          │
   연결 허용   연결 거부
       │          │
   [통신 진행] [에러 표시]
```

### 고정 대상별 비교
```
┌──────────────┬──────────┬──────────┬──────────┐
│   고정 대상  │   엄격성 │  유연성  │  권장도  │
├──────────────┼──────────┼──────────┼──────────┤
│ Certificate  │   높음   │   낮음   │    △     │
│ (전체)       │ 갱신불편 │          │          │
├──────────────┼──────────┼──────────┼──────────┤
│ Public Key   │   중간   │   높음   │    ◎     │
│ (공개키)     │ 갱신용이 │          │  권장!   │
├──────────────┼──────────┼──────────┼──────────┤
│ Hash         │   높음   │   중간   │    ○     │
│ (해시값)     │ 빠름효율 │          │          │
└──────────────┴──────────┴──────────┴──────────┘
```

## 💡 실기 답안 작성 팁

### Tip 1: 정의 명확히
```
✅ "앱에 인증서/공개키를 하드코딩하여 특정 인증서만 신뢰"

❌ "인증서를 고정한다" (정의 부족)
```

### Tip 2: MITM 설명 시
```
✅ MITM (Man-In-The-Middle) 공격
   중간자가 통신 가로채기, 가짜 인증서 사용

❌ MITM (설명 없이 약자만)
```

### Tip 3: 고정 대상
```
✅ 1. Certificate (인증서 전체)
   2. Public Key (공개키)
   3. Hash (해시값)

❌ 1. SSL 인증서
   2. 인증기관 (RA, CA) ← 틀림!
   3. 식별자 번호 ← 틀림!
```

### Tip 4: 우회 기법
```
✅ 1. 리패키징 (APK 디컴파일, 핀 제거)
   2. 런타임 후킹 (Frida, 함수 우회)

❌ 1. 세션 탈취 ← 관련 없음
   2. 재전송 공격 ← 관련 없음
```

## 📝 종합 문제: 인증서 고정 시나리오

### 종합 문제 1
```
모바일 뱅킹 앱에 인증서 고정을 적용하려고 한다.

1. 어떤 고정 방식을 사용할지 선택하고 이유를 설명하시오.
2. 인증서 갱신 시 고려 사항을 설명하시오.
3. 공격자가 우회를 시도할 경우 추가 방어 방법을 제시하시오.
```

**✅ 답안:**
```
1. 고정 방식 선택

선택: Public Key Pinning (공개키 고정)

이유:
- 인증서 갱신 시에도 같은 공개키 사용 가능
- 앱 업데이트 없이 인증서 갱신 가능
- Certificate Pinning보다 유연
- Hash보다 직관적이고 안전

구현:
- 주 공개키 + 백업 공개키 2개 이상 설정
- 백업 키로 인증서 갱신 대비


2. 인증서 갱신 시 고려 사항

ㄱ. 백업 핀 (Backup Pin) 사전 설정
   - 최소 2개 이상의 공개키 핀 설정
   - 갱신용 키를 미리 앱에 포함

   예시:
   <pin digest="SHA-256">현재키해시...</pin>
   <pin digest="SHA-256">백업키해시...</pin>

ㄴ. 만료 기한 (Expiration) 설정
   - 긴급 상황 대비 핀 만료 날짜 설정
   - 만료 후 일반 CA 검증으로 폴백

   <pin-set expiration="2025-12-31">

ㄷ. 점진적 배포 (Gradual Rollout)
   - 새 인증서 배포 전 백업 핀으로 테스트
   - 문제 발생 시 롤백 가능

ㄹ. 모니터링
   - 핀 불일치 에러 모니터링
   - 갱신 시점 전 충분한 여유 확보


3. 추가 방어 방법

ㄱ. Root/Jailbreak 탐지
   - 루팅 탐지 시 앱 실행 차단 또는 경고
   - SafetyNet (Android), DeviceCheck (iOS) 사용

ㄴ. 코드 난독화
   - ProGuard, R8 (Android)
   - 인증서 검증 로직 난독화
   - 핀 값 암호화 저장

ㄷ. Anti-Hooking
   - Frida 탐지 코드 추가
   - 동적 무결성 검사
   - 함수 호출 체크섬 검증

ㄹ. SSL/TLS 버전 강제
   - TLS 1.2 이상만 허용
   - 약한 Cipher Suite 차단

ㅁ. 네트워크 환경 검증
   - 프록시 탐지 (Proxy Detection)
   - VPN 탐지 (의심스러운 네트워크)
   - 공용 Wi-Fi 경고
```
