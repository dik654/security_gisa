## 1. OSI 7 Layer

### 문제 1-1: OSI 7계층을 순서대로 나열하고, 각 계층의 역할과 대표 프로토콜을 설명하시오 (15점) ★★★

#### ✅ 모범 답안:

**[OSI 7 Layer 구조]**

| 계층 | 이름 | 역할 | 프로토콜/장비 | PDU |
|------|------|------|---------------|-----|
| 7 | Application (응용) | 사용자 인터페이스 제공 | HTTP, FTP, SMTP, DNS | Data |
| 6 | Presentation (표현) | 데이터 형식 변환, 암호화 | JPEG, MPEG, SSL/TLS | Data |
| 5 | Session (세션) | 세션 연결/유지/종료 | NetBIOS, RPC | Data |
| 4 | Transport (전송) | 종단간 신뢰성 있는 전송 | TCP, UDP | Segment |
| 3 | Network (네트워크) | 논리적 주소 지정, 라우팅 | IP, ICMP, Router | Packet |
| 2 | Data Link (데이터링크) | 물리적 주소 지정, 에러 검출 | Ethernet, Switch, MAC | Frame |
| 1 | Physical (물리) | 비트 전송 | Cable, Hub, Repeater | Bit |

**[계층별 상세 설명]**

**7계층 - Application Layer (응용 계층) ★★★**
- 역할: 사용자와 직접 상호작용하는 응용 프로그램
- 프로토콜:
  - HTTP/HTTPS: 웹 (80/443)
  - FTP: 파일 전송 (21)
  - SMTP: 메일 전송 (25)
  - DNS: 도메인 이름 해석 (53)
  - Telnet/SSH: 원격 접속 (23/22)

**6계층 - Presentation Layer (표현 계층) ★★**
- 역할: 데이터 표현 방식 변환
- 기능:
  - 인코딩/디코딩 (ASCII, EBCDIC)
  - 암호화/복호화 (SSL/TLS)
  - 압축/압축 해제
  - 데이터 형식 변환 (JPEG, MPEG)

**5계층 - Session Layer (세션 계층) ★★**
- 역할: 응용 프로그램 간 연결(세션) 관리
- 기능:
  - 세션 설정/유지/종료
  - 동기화 (Synchronization)
  - 대화 제어 (Dialog Control)

**4계층 - Transport Layer (전송 계층) ★★★**
- 역할: 종단 간(End-to-End) 신뢰성 있는 데이터 전송
- 프로토콜:
  - **TCP**: 연결 지향, 신뢰성, 흐름 제어
  - **UDP**: 비연결, 빠른 속도, 실시간 전송
- 기능:
  - 포트 번호로 프로세스 식별
  - 오류 제어, 흐름 제어, 혼잡 제어

**3계층 - Network Layer (네트워크 계층) ★★★**
- 역할: 논리적 주소(IP) 지정 및 라우팅
- 프로토콜:
  - IP: 패킷 전달
  - ICMP: 에러 보고 (ping)
  - ARP: IP → MAC 주소 변환
  - OSPF, BGP: 라우팅 프로토콜
- 장비: Router (라우터)

**2계층 - Data Link Layer (데이터링크 계층) ★★★**
- 역할: 물리적 주소(MAC) 지정, 에러 검출
- 하위 계층:
  - LLC: 논리적 링크 제어
  - MAC: 매체 접근 제어
- 프로토콜: Ethernet, PPP
- 장비: Switch (스위치), Bridge (브리지)
- 기능: 프레임 단위 전송, CRC 에러 검출

**1계층 - Physical Layer (물리 계층) ★★**
- 역할: 전기적 신호로 비트 전송
- 장비: Hub, Repeater, Cable
- 전송 매체: UTP, 광섬유, 무선

**[암기 팁]**
```
하향식 (Application → Physical): 모든 프시네데피
- 모(응용) 든(표현) 프(세션) 시(전송) 네(네트워크) 데(데이터링크) 피(물리)

상향식 (Physical → Application): 피데네전세표응
```

**[채점 기준]**
- 7계층 순서대로 나열 (7점, 각 1점)
- 각 계층의 역할 (4점)
- 대표 프로토콜 3개 이상 (4점)

### 문제 1-2: TCP와 UDP의 차이점을 비교하고, 각각의 사용 예시를 3가지씩 쓰시오 (12점) ★★★

#### ✅ 모범 답안:

**[TCP vs UDP 비교]**

| 구분 | TCP | UDP |
|------|-----|-----|
| **연결 방식** | 연결 지향 (Connection-Oriented) | 비연결 (Connectionless) |
| **신뢰성** | 높음 (재전송, 순서 보장) | 낮음 (재전송 없음) |
| **속도** | 느림 (오버헤드 큼) | 빠름 (오버헤드 작음) |
| **순서 보장** | ✓ 순서 보장 | ✗ 순서 미보장 |
| **오류 제어** | ✓ 있음 (ACK, Checksum) | 제한적 (Checksum만) |
| **흐름 제어** | ✓ 있음 (Sliding Window) | ✗ 없음 |
| **혼잡 제어** | ✓ 있음 (Slow Start) | ✗ 없음 |
| **헤더 크기** | 20~60 bytes | 8 bytes |
| **브로드캐스트** | ✗ 불가능 | ✓ 가능 |

**[TCP 특징] ★★★**
```
전화 통화와 유사:
1. 연결 수립 (3-Way Handshake)
2. 데이터 전송
3. 연결 종료 (4-Way Handshake)
```

**TCP 사용 예시 (신뢰성 중요):**
1. **HTTP/HTTPS (웹 브라우징)**
   - 웹 페이지 전체가 정확히 전송되어야 함
   - 이미지, HTML 파일 손실 불가

2. **FTP (파일 전송)**
   - 파일이 손상 없이 완전히 전송되어야 함
   - 순서가 바뀌면 파일 깨짐

3. **SMTP/POP3/IMAP (이메일)**
   - 메일 내용 손실 방지
   - 첨부 파일 정확한 전송

4. **SSH/Telnet (원격 접속)**
   - 명령어가 정확히 전달되어야 함

5. **데이터베이스 연결**
   - 트랜잭션 무결성 보장

**[UDP 특징] ★★★**
```
편지 발송과 유사:
1. 주소 적고 발송
2. 도착 여부 확인 안 함
3. 빠르지만 손실 가능
```

**UDP 사용 예시 (속도 중요):**
1. **DNS (도메인 이름 조회)**
   - 빠른 응답 필요
   - 실패 시 재요청하면 됨
   - 포트: 53

2. **스트리밍 (음성/영상)**
   - YouTube, Netflix, Zoom
   - 일부 패킷 손실 허용 (화질/음질 저하)
   - 실시간성이 더 중요

3. **온라인 게임**
   - 캐릭터 위치 정보 실시간 전송
   - 약간의 손실은 다음 패킷으로 보정

4. **SNMP (네트워크 관리)**
   - 주기적인 상태 정보 전송
   - 손실되어도 다음 주기에 전송

5. **TFTP (간단한 파일 전송)**
   - 라우터 설정 파일 전송
   - 작은 파일, 빠른 전송

6. **VoIP (인터넷 전화)**
   - 실시간 음성 통신
   - 지연이 치명적

**[선택 기준]**
```
TCP 사용:
- 데이터 손실이 치명적인 경우
- 순서가 중요한 경우
- 신뢰성 > 속도

UDP 사용:
- 실시간성이 중요한 경우
- 약간의 손실 허용 가능
- 속도 > 신뢰성
```

**[채점 기준]**
- TCP와 UDP 차이점 비교 (6점)
- TCP 사용 예시 3가지 (3점)
- UDP 사용 예시 3가지 (3점)

## 2. TCP/IP 3-Way Handshake

### 문제 2-1: TCP 3-Way Handshake 과정을 상세히 설명하고, 각 단계에서 주고받는 플래그를 명시하시오 (12점) ★★★

#### ✅ 모범 답안:

**[3-Way Handshake 과정]**

```
Client                          Server

  |                                |
  |  ①SYN (seq=100)                |
  |------------------------------>|  (LISTEN 상태)
  |                                |
  |                                |  포트 열림 확인
  |                                |
  |  ②SYN+ACK (seq=200, ack=101)   |
  |<------------------------------|
  |                                |
  |  ③ACK (seq=101, ack=201)       |
  |------------------------------>|
  |                                |
  |  ====== 연결 수립 완료 ======    |
  |                                |
  |  데이터 전송 시작                |
  |<----------------------------->|
```

**[단계별 상세 설명]**

**1단계: SYN (Synchronize) ★★★**
```
Client → Server
- 플래그: SYN = 1
- Sequence Number: 100 (초기 순서 번호, 랜덤)
- 의미: "연결하고 싶습니다. 내 초기 순서 번호는 100입니다."
- 클라이언트 상태: SYN_SENT
```

**2단계: SYN+ACK (Synchronize + Acknowledgement) ★★★**
```
Server → Client
- 플래그: SYN = 1, ACK = 1
- Sequence Number: 200 (서버의 초기 순서 번호)
- Acknowledgement Number: 101 (클라이언트 seq + 1)
- 의미: "연결 요청 받았습니다. 내 초기 순서 번호는 200입니다."
- 서버 상태: SYN_RECEIVED
```

**3단계: ACK (Acknowledgement) ★★★**
```
Client → Server
- 플래그: ACK = 1
- Sequence Number: 101
- Acknowledgement Number: 201 (서버 seq + 1)
- 의미: "확인했습니다. 이제 데이터 전송 시작합니다."
- 양쪽 상태: ESTABLISHED (연결 수립 완료)
```

**[TCP 헤더 플래그 6가지]**
```
URG (Urgent): 긴급 데이터
ACK (Acknowledgement): 확인 응답
PSH (Push): 버퍼링 없이 즉시 전달
RST (Reset): 연결 강제 종료
SYN (Synchronize): 연결 수립
FIN (Finish): 연결 종료
```

**[ISN (Initial Sequence Number)]**
- 초기 순서 번호는 랜덤하게 생성
- 이유: 세션 하이재킹 방지
- 예측 가능하면 공격자가 패킷 위조 가능

**[3-Way Handshake의 목적]**
1. **양방향 통신 확인**
   - 클라이언트 → 서버 경로 확인 (1, 2단계)
   - 서버 → 클라이언트 경로 확인 (2, 3단계)

2. **초기 순서 번호 동기화**
   - 양쪽의 ISN 교환
   - 이후 데이터 순서 보장 기반

3. **연결 수립 확인**
   - 양쪽 모두 ESTABLISHED 상태
   - 데이터 전송 준비 완료

**[채점 기준]**
- 3단계 과정 설명 (6점, 각 2점)
- 각 단계의 플래그 명시 (3점)
- Sequence/Acknowledgement 번호 (3점)

### 문제 2-2: TCP 4-Way Handshake (연결 종료) 과정을 설명하시오 (10점) ★★

#### ✅ 모범 답안:

**[4-Way Handshake 과정]**

```
Client                          Server

  |                                |
  |  ①FIN (seq=1000)               |
  |------------------------------>|
  |                                |  (CLOSE_WAIT)
  |  ②ACK (ack=1001)               |
  |<------------------------------|
  |                                |
  | (FIN_WAIT 상태)                 |  (남은 데이터 전송)
  |                                |
  |  ③FIN (seq=2000)               |
  |<------------------------------|
  |                                |
  |  ④ACK (ack=2001)               |
  |------------------------------>|
  |                                |
  | (TIME_WAIT → CLOSED)           |  (CLOSED)
```

**[단계별 설명]**

**1단계: FIN (Finish)**
```
Client → Server
- 플래그: FIN = 1
- "나는 더 이상 보낼 데이터가 없습니다."
- 클라이언트 상태: FIN_WAIT_1
```

**2단계: ACK**
```
Server → Client
- 플래그: ACK = 1
- "종료 요청 받았습니다. 잠시만 기다려주세요."
- 서버 상태: CLOSE_WAIT
- 클라이언트 상태: FIN_WAIT_2
- 서버는 아직 보낼 데이터가 있을 수 있음
```

**3단계: FIN**
```
Server → Client
- 플래그: FIN = 1
- "나도 모든 데이터 전송 완료했습니다."
- 서버 상태: LAST_ACK
```

**4단계: ACK**
```
Client → Server
- 플래그: ACK = 1
- "확인했습니다."
- 클라이언트 상태: TIME_WAIT → CLOSED
- 서버 상태: CLOSED
```

**[TIME_WAIT 상태] ★★**
- 기간: 2MSL (Maximum Segment Lifetime, 보통 1~4분)
- 이유:
  1. 마지막 ACK 패킷이 손실될 경우 재전송 대비
  2. 이전 연결의 지연된 패킷이 새 연결에 영향 방지

**[3-Way vs 4-Way 차이]**
- 연결 수립: 3-Way (SYN+ACK 통합)
- 연결 종료: 4-Way (ACK와 FIN 분리)
- 이유: 서버가 남은 데이터를 전송할 시간 필요

**[채점 기준]**
- 4단계 과정 설명 (8점, 각 2점)
- TIME_WAIT 설명 (2점)

## 3. 방화벽

### 문제 3-1: Stateful 방화벽과 Stateless 방화벽의 차이점을 설명하고, 각각의 장단점을 비교하시오 (15점) ★★★

#### ✅ 모범 답안:

**[Stateless vs Stateful 방화벽 비교]**

| 구분 | Stateless (무상태) | Stateful (상태 기반) |
|------|-------------------|---------------------|
| **연결 상태 추적** | ✗ 추적 안 함 | ✓ 추적함 |
| **패킷 단위** | 개별 패킷만 검사 | 세션 전체 추적 |
| **메모리 사용** | 적음 | 많음 (세션 테이블) |
| **속도** | 빠름 | 느림 (상태 확인) |
| **보안성** | 낮음 | 높음 |
| **규칙 복잡도** | 복잡 (양방향 규칙 필요) | 단순 (단방향 규칙) |
| **대표 기술** | Packet Filtering | Dynamic Packet Filtering |

**[Stateless 방화벽 (1세대)] ★★**

**동작 원리:**
```
각 패킷을 독립적으로 검사
이전 패킷 정보 사용 안 함
규칙(ACL)과만 비교
```

**장점:**
1. **빠른 처리 속도**
   - 단순 비교만 수행
   - 상태 테이블 조회 불필요

2. **적은 리소스 사용**
   - 메모리 사용량 낮음
   - 세션 정보 저장 안 함

3. **단순한 구조**
   - 구현이 간단
   - 유지보수 용이

**단점:**
1. **양방향 규칙 필요**
```
# 웹 서버 허용 예시 (Stateless)
# 클라이언트 → 서버 (요청)
allow tcp any any 80

# 서버 → 클라이언트 (응답)
allow tcp 80 any any  # 모든 high port 허용 (보안 취약!)
```

2. **보안 취약점**
   - 응답 패킷 허용을 위해 넓은 범위 오픈
   - 스푸핑 공격에 취약

3. **세션 제어 불가**
   - 비정상 세션 탐지 어려움

**[Stateful 방화벽 (2세대)] ★★★**

**동작 원리:**
```
연결 상태 테이블 유지
- 송신지 IP, 포트
- 목적지 IP, 포트
- 연결 상태 (NEW, ESTABLISHED, RELATED)
```

**세션 상태:**
```
NEW: 새로운 연결 시도
ESTABLISHED: 기존 연결의 패킷
RELATED: 기존 연결과 관련된 새 연결 (FTP 데이터 채널)
INVALID: 알 수 없는 패킷
```

**장점:**
1. **단방향 규칙만 필요 ★★★**
```
# 웹 서버 허용 예시 (Stateful)
# 아웃바운드 규칙만 작성
allow tcp any any 80

# 인바운드 응답은 자동 허용
# 세션 테이블에 연결 기록되어 있음
```

2. **높은 보안성**
   - 정상 세션의 응답만 허용
   - 비정상 패킷 자동 차단
   - 스푸핑 공격 방어

3. **세션 기반 제어**
```
# 연결 상태별 정책
allow ESTABLISHED  # 기존 연결 허용
allow RELATED      # 관련 연결 허용
drop INVALID       # 비정상 패킷 차단
```

4. **애플리케이션 인식**
   - FTP, SIP 등 다중 채널 프로토콜 지원
   - 동적 포트 할당 처리

**단점:**
1. **높은 리소스 사용**
   - 세션 테이블 메모리 필요
   - CPU 사용량 증가

2. **느린 처리 속도**
   - 상태 테이블 조회 오버헤드
   - 첫 패킷은 상태 생성 필요

3. **DoS 공격 취약**
   - SYN Flooding으로 세션 테이블 고갈
   - 대량 연결 시 성능 저하

**[실무 비유]**
```
Stateless:
- 신분증만 확인하는 경비원
- 들어올 때, 나갈 때 매번 확인
- 빠르지만 비효율적

Stateful:
- 방문 기록을 관리하는 경비원
- 들어온 사람은 나갈 때 자동 통과
- 느리지만 안전하고 효율적
```

**[iptables 예시]**

**Stateless 규칙:**
```bash
# 양방향 규칙 모두 작성
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A OUTPUT -p tcp --sport 80 -j ACCEPT
```

**Stateful 규칙:**
```bash
# 단방향 규칙만 작성
iptables -A INPUT -p tcp --dport 80 -m state --state NEW,ESTABLISHED -j ACCEPT
iptables -A OUTPUT -m state --state ESTABLISHED -j ACCEPT
```

**[현대 방화벽]**
- 대부분 Stateful 방화벽 사용
- 차세대 방화벽(NGFW): Stateful + 애플리케이션 인식 + IPS

**[채점 기준]**
- Stateless vs Stateful 차이 (5점)
- 각각의 장단점 (8점)
- 규칙 예시 (2점)

### 문제 3-2: 방화벽 아키텍처 종류를 설명하고, 베스천 호스트(Bastion Host)의 역할을 서술하시오 (12점) ★★

#### ✅ 모범 답안:

**[방화벽 아키텍처 3가지]**

**1. 단일 홈 게이트웨이 (Single-Homed Gateway) = 베스천 호스트 ★★★**

```
인터넷 ←→ [방화벽] ←→ [베스천 호스트] ←→ 내부망
                        (Bastion Host)

구조:
- 베스천 호스트가 내부망 앞에 배치
- NIC 1개 (단일 네트워크 인터페이스)
- 모든 외부 접속이 베스천 호스트를 거침
```

**베스천 호스트 (Bastion Host)**: ★★★
```
정의:
외부 공격에 노출되도록 특별히 설계된 호스트
요새(Bastion)처럼 방어 최전선에 배치

역할:
1. 외부 접속 집중 지점
   - 모든 외부 접속이 이 서버를 거침
   - 게이트웨이 역할

   - 애플리케이션 게이트웨이

특징:
- 내부망 IP 주소 은닉
- 집중적인 보안 모니터링 가능
- SPOF (Single Point of Failure) 위험
```

**시험 출제 포인트**: ★★★
```
문제: "베스천 호스트라고도 부르는 것은?"
정답: 단일 홈 게이트웨이

주의:
- 베스천 호스트 = 단일 홈 게이트웨이
- 외부에 노출된 강화된 호스트
- 방화벽과 내부망 사이에 배치
```

**장점:**

**단점:**
- 베스천 호스트 침해 시 내부망 노출

**2. 듀얼 홈 게이트웨이 (Dual-Homed Gateway) ★★**

```
                 [듀얼 홈 게이트웨이]
                 /              \
인터넷 ←→ NIC 1 (외부)    NIC 2 (내부) ←→ 내부망

- IP 포워딩 비활성화
- 모든 트래픽이 게이트웨이 통과
```

**특징:**
- NIC 2개 (외부/내부)
- 라우팅 기능 차단
- 프록시로만 통신
- 완전한 트래픽 제어

**장점:**
- 강력한 보안 (물리적 분리)
- 완전한 로깅 가능
- IP 포워딩 차단으로 직접 접속 불가

**단점:**
- 성능 병목
- 복잡한 설정
- 애플리케이션별 프록시 필요

**3. 스크린 서브넷 (Screened Subnet) = DMZ ★★★**

```
                     [외부 방화벽]
                           |
인터넷 ←→ 외부 방화벽 ←→ [DMZ] ←→ 내부 방화벽 ←→ 내부망
                      (비무장지대)
                      - 웹 서버
                      - 메일 서버
                      - DNS 서버
```

**DMZ (DeMilitarized Zone)**: ★★★
```
정의:
내부망과 외부 네트워크 사이의 중립 지역
비무장지대 (완충 지역)

배치 서버:
- 공개 웹 서버
- 메일 서버 (MX)
- DNS 서버 (외부용)
- FTP 서버

보안 규칙:
1. 외부 → DMZ: 제한적 허용 (HTTP, SMTP, DNS)
2. DMZ → 내부: 최소한 허용 (DB 접속만)
3. 외부 → 내부: 차단
4. 내부 → DMZ: 관리 접속만
5. 내부 → 외부: 허용 (프록시 경유)
```

**장점:**
- 최고 수준 보안 (2중 방화벽)
- 내부망 완전 보호
- DMZ 침해 시에도 내부망 안전

**단점:**
- 높은 비용 (방화벽 2대)
- 복잡한 관리
- 성능 오버헤드

**[방화벽 아키텍처 비교표]**

| 아키텍처 | NIC 개수 | 방화벽 개수 | 보안성 | 비용 | 복잡도 |
|---------|----------|-------------|--------|------|--------|
| 단일 홈 (베스천) | 1 | 1 | 낮음 | 낮음 | 낮음 |
| 듀얼 홈 | 2 | 1 | 중간 | 중간 | 중간 |
| 스크린 서브넷 (DMZ) | N/A | 2 | 높음 | 높음 | 높음 |

**[베스천 호스트 보안 강화 방법] ★★**

## 4. VPN과 IPSec

### 문제 4-1: VPN의 종류 3가지를 설명하고, IPSec의 두 가지 모드를 비교하시오 (15점) ★★★

#### ✅ 모범 답안:

**[VPN 종류 3가지]**

**1. Site-to-Site VPN (사이트 간 VPN) ★★★**
```
본사 (VPN Gateway) ←→ 지사 (VPN Gateway)
     |                      |
   내부망                  내부망
```
- 목적: 두 네트워크를 안전하게 연결
- 사용자: 투명하게 사용 (VPN 인식 불필요)
- 예시: 본사-지사 간 내부망 연결
- 구현: IPSec, MPLS VPN

**2. Remote Access VPN (원격 접속 VPN) ★★★**
```
재택근무자 (VPN Client) ←→ 회사 (VPN Server)
```
- 목적: 개인이 원격에서 회사 네트워크 접속
- 사용자: VPN 클라이언트 프로그램 설치 필요
- 예시: 재택근무, 출장 중 사내 시스템 접속
- 구현: SSL VPN, IPSec VPN, L2TP

**3. Client-to-Client VPN (P2P VPN) ★**
```
사용자 A ←→ 사용자 B
```
- 목적: 두 사용자 간 직접 암호화 통신
- 예시: 파일 공유, 게임

**[VPN 프로토콜 비교]**

| 프로토콜 | 계층 | 포트 | 특징 |
|---------|------|------|------|
| IPSec | 3계층 (Network) | UDP 500, 4500 | 강력한 보안, 복잡한 설정 |
| SSL VPN | 7계층 (Application) | TCP 443 | 웹 브라우저 사용, 쉬운 접속 |
| L2TP/IPSec | 2계층 + IPSec | UDP 1701, 500 | Windows 기본 지원 |
| PPTP | 2계층 | TCP 1723 | 빠르지만 취약 (사용 비권장) |

**[IPSec 두 가지 모드] ★★★**

**1. Transport Mode (전송 모드) ★★**

```
[원본]
+----------+----------+
| IP Header | Data    |
+----------+----------+

[Transport Mode]
+----------+------------+----------+
| IP Header | IPSec Header | Data  |
+----------+------------+----------+
  (원본)        (추가)       (암호화)

- IP 헤더: 변경 없음 (원본 유지)
- 페이로드만 암호화
```

**특징:**
- IP 헤더는 암호화 안 함
- 송신지/목적지 IP 주소 노출
- 오버헤드 작음
- 종단 간(End-to-End) 암호화

**사용 예시:**
- Host-to-Host 통신
- 두 서버 간 직접 통신
- 같은 네트워크 내 통신

**장점:**
- 적은 오버헤드
- 빠른 처리

**단점:**
- IP 주소 노출
- NAT 통과 어려움

**2. Tunnel Mode (터널 모드) ★★★**

```
[원본]
+----------+----------+
| IP Header | Data    |
+----------+----------+

[Tunnel Mode]
+----------+------------+----------+----------+
| 새 IP   | IPSec Header | 원본 IP | Data   |
| Header  |             | Header  |        |
+----------+------------+----------+----------+
  (추가)       (추가)       (암호화)  (암호화)

- 전체 원본 패킷 암호화
- 새로운 IP 헤더 추가
```

**특징:**
- 전체 원본 패킷 암호화 (IP 헤더 포함)
- 새 IP 헤더: VPN Gateway 주소
- 내부 IP 주소 완전 은닉
- 오버헤드 큼

**사용 예시:**
- Site-to-Site VPN
- Remote Access VPN
- Gateway-to-Gateway 통신

**장점:**
- 완전한 암호화 (IP 주소 포함)
- NAT 통과 가능
- 네트워크 토폴로지 은닉

**단점:**
- 큰 오버헤드 (20 bytes 추가)
- 느린 처리 속도

**[Transport vs Tunnel 비교표]**

| 구분 | Transport Mode | Tunnel Mode |
|------|----------------|-------------|
| **암호화 범위** | 페이로드만 | 전체 패킷 |
| **IP 헤더** | 원본 유지 | 새 헤더 추가 |
| **IP 주소 노출** | ✓ 노출 | ✗ 은닉 |
| **오버헤드** | 작음 | 큼 (+20 bytes) |
| **속도** | 빠름 | 느림 |
| **NAT 통과** | 어려움 | 가능 |
| **주요 용도** | Host-to-Host | Site-to-Site |

**[IPSec 프로토콜 2가지]**

**AH (Authentication Header) ★★**
- 기능: 인증 + 무결성
- 암호화: ✗ 없음
- 보호: IP 헤더 + 페이로드
- 포트: IP Protocol 51
- 단점: NAT 통과 불가 (IP 헤더 보호)

**ESP (Encapsulating Security Payload) ★★★**
- 기능: 인증 + 무결성 + 암호화
- 암호화: ✓ 있음
- 보호: 페이로드 (IP 헤더 제외)
- 포트: IP Protocol 50
- 장점: NAT 통과 가능
- 실무: 대부분 ESP 사용

**[IPSec 연결 과정]**

**1단계: IKE Phase 1 (ISAKMP SA 수립)**
```
목적: 안전한 제어 채널 수립
방식: Main Mode (6개 메시지) 또는 Aggressive Mode (3개 메시지)
결과: IKE SA (제어용)
```

**2단계: IKE Phase 2 (IPSec SA 수립)**
```
목적: 실제 데이터 암호화 채널 수립
방식: Quick Mode
결과: IPSec SA (데이터용)
```

**[채점 기준]**
- VPN 종류 3가지 (6점)
- Transport Mode 설명 (4점)
- Tunnel Mode 설명 (4점)
- 비교 (1점)

## 5. SSL/TLS

### 문제 5-1: SSL/TLS Handshake 과정을 설명하시오 (12점) ★★★

#### ✅ 모범 답안:

**[SSL/TLS Handshake 과정]**

```
Client                          Server

①Client Hello
  - 지원 암호화 알고리즘
  - 랜덤 데이터 (Client Random)
  - TLS 버전
------------------------------>

                              ②Server Hello
                                - 선택한 암호화 알고리즘
                                - 랜덤 데이터 (Server Random)
                              ③Certificate
                                - 서버 인증서 (공개키 포함)
                              ④Server Hello Done
<------------------------------

⑤Client Key Exchange
  - Pre-Master Secret (서버 공개키로 암호화)
⑥Change Cipher Spec
  - 이제부터 암호화 통신
⑦Finished (암호화됨)
------------------------------>

                              ⑧Change Cipher Spec
                              ⑨Finished (암호화됨)
<------------------------------

========= SSL/TLS 연결 수립 완료 =========

암호화된 데이터 전송
<------------------------------>
```

**[단계별 상세 설명]**

**1단계: Client Hello ★★★**
```
클라이언트 → 서버

전송 내용:
- TLS 버전 (TLS 1.2, 1.3)
- Cipher Suite 목록 (지원하는 암호화 알고리즘)
  예: TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
- Client Random (28 bytes, 세션 키 생성용)
- Session ID (재연결용)
- 압축 방법
```

**2단계: Server Hello ★★★**
```
서버 → 클라이언트

전송 내용:
- 선택한 TLS 버전
- 선택한 Cipher Suite (1개)
- Server Random (28 bytes)
- Session ID
```

**3단계: Certificate ★★★**
```
서버 → 클라이언트

전송 내용:
- 서버의 디지털 인증서
  - 서버 공개키
  - 도메인 정보
  - 발급 기관(CA) 정보
  - 유효기간

클라이언트 검증:
1. 인증서가 신뢰된 CA에서 발급되었는지 확인
2. 인증서가 만료되지 않았는지 확인
3. 인증서의 도메인이 접속한 도메인과 일치하는지 확인
4. 인증서가 폐기되지 않았는지 확인 (CRL, OCSP)
```

**4단계: Server Hello Done**
```
서버 → 클라이언트
"서버의 Hello 단계 완료"
```

**5단계: Client Key Exchange ★★★**
```
클라이언트 → 서버

전송 내용:
- Pre-Master Secret (48 bytes)
  - 클라이언트가 생성한 랜덤 값
  - 서버의 공개키로 암호화하여 전송
  - 서버만 개인키로 복호화 가능

세션 키 생성:
Master Secret = PRF(Pre-Master Secret,
                    Client Random,
                    Server Random)

세션 키 = PRF(Master Secret, ...)
```

**6단계: Change Cipher Spec ★★**
```
클라이언트 → 서버
"이제부터 협상한 암호화 알고리즘으로 통신합니다"
```

**7단계: Finished ★★**
```
클라이언트 → 서버

- 지금까지 주고받은 모든 메시지의 해시값
- 세션 키로 암호화하여 전송
- 서버가 복호화 성공하면 키 교환 성공 확인
```

**8~9단계: 서버도 동일하게 전송**
```
서버 → 클라이언트
- Change Cipher Spec
- Finished (암호화)
```

**[세션 키 생성 과정] ★★★**

```
재료:
- Pre-Master Secret (클라이언트 생성)
- Client Random
- Server Random

1단계: Master Secret 생성
Master Secret = PRF(Pre-Master Secret,
                   "master secret",
                   Client Random + Server Random)

2단계: 세션 키 생성
- 클라이언트 암호화 키
- 서버 암호화 키
- 클라이언트 MAC 키
- 서버 MAC 키
- 클라이언트 IV
- 서버 IV

총 6개 키 생성
```

**[대칭키 vs 비대칭키 사용] ★★★**

**Handshake 단계 (비대칭키):**
- Pre-Master Secret 암호화
- 느리지만 안전한 키 교환

**데이터 전송 단계 (대칭키):**
- 실제 데이터 암호화
- 빠른 암호화/복호화
- AES, ChaCha20 등 사용

**[TLS 1.3 개선사항] ★★**

**TLS 1.2:**
- Handshake: 2-RTT (왕복 2번)
- 느림

**TLS 1.3:**
- Handshake: 1-RTT (왕복 1번)
- 취약한 암호화 알고리즘 제거
- Forward Secrecy 필수
- 빠르고 안전

**[채점 기준]**
- Handshake 단계 설명 (8점)
- 세션 키 생성 과정 (2점)
- 비대칭/대칭키 사용 구분 (2점)

## 6. 네트워크 공격

### 문제 6-1: SYN Flooding 공격의 원리와 방어 방법을 5가지 이상 설명하시오 (15점) ★★★

#### ✅ 모범 답안:

**[SYN Flooding 공격 원리]**

```
정상 연결:
Client                Server
  |----SYN------------>|  ① 세션 테이블에 기록
  |<---SYN+ACK---------|  ② 대기 (SYN_RECEIVED)
  |----ACK------------>|  ③ ESTABLISHED

SYN Flooding 공격:
Attacker              Server
  |----SYN (위조 IP)-->|  ① 세션 테이블에 기록
  |<---SYN+ACK---------|  ② 대기 (SYN_RECEIVED)
  |  (응답 없음)        |  ③ 타임아웃까지 대기 (75초)
  |                    |
  |----SYN (위조 IP)-->|  대량 반복
  |----SYN (위조 IP)-->|  → 세션 테이블 고갈
  |----SYN (위조 IP)-->|  → 정상 연결 불가 (DoS)
```

**[공격 단계]**

1. **SYN 패킷 대량 전송**
   - 공격자가 위조된 송신지 IP로 SYN 패킷 전송
   - 초당 수천~수만 개 전송

2. **서버 자원 소진**
   - 서버는 각 SYN에 대해 세션 테이블 생성
   - SYN+ACK 전송 후 ACK 대기 (Half-Open 상태)
   - 타임아웃: 보통 75초

3. **정상 연결 거부**
   - 세션 테이블(Backlog Queue) 가득 참
   - 정상 사용자 연결 불가
   - 서비스 거부(DoS) 상태

**[피해]**
- CPU, 메모리 고갈
- 네트워크 대역폭 소진
- 서비스 중단

**[방어 방법 8가지]**

**1. SYN Cookie ★★★**
```
원리:
- 세션 테이블에 저장하지 않음
- SYN+ACK의 Sequence Number에 연결 정보 인코딩
- ACK 수신 시 Sequence Number 검증으로 연결 복원

장점:
- 세션 테이블 무한대
- 메모리 소진 없음

단점:
- TCP 옵션 일부 손실 가능

Linux 설정:
sysctl -w net.ipv4.tcp_syncookies=1
```

**2. Backlog Queue 크기 증가 ★★**
```bash
# 대기 큐 크기 확대
sysctl -w net.ipv4.tcp_max_syn_backlog=4096

# 기본값: 512~1024
# 증가: 2048~8192
```
- 임시 방편 (근본적 해결 아님)
- 대량 공격 시 여전히 고갈 가능

**3. SYN-ACK 재전송 횟수 감소 ★★**
```bash
# 재전송 횟수 줄이기
sysctl -w net.ipv4.tcp_synack_retries=1

# 기본값: 5회 (약 63초)
# 감소: 1~2회 (약 3~7초)
```
- Half-Open 연결 빠르게 정리
- 타임아웃 시간 단축

**4. 방화벽 Rate Limiting ★★★**
```bash
# iptables: 초당 SYN 패킷 제한
iptables -A INPUT -p tcp --syn -m limit \
  --limit 10/sec --limit-burst 20 -j ACCEPT
iptables -A INPUT -p tcp --syn -j DROP

# 의미: 초당 10개, 버스트 20개까지 허용
```

**5. 동일 IP에서의 연결 수 제한 ★★**
```bash
# iptables: 동일 IP 최대 연결 수 제한
iptables -A INPUT -p tcp --syn -m connlimit \
  --connlimit-above 10 -j REJECT

# 의미: IP당 최대 10개 동시 연결
```

**6. SYN Proxy ★★★**
```
Client → SYN Proxy → Server

동작:
1. SYN Proxy가 클라이언트와 3-Way Handshake 완료
2. 정상 연결 확인 후 서버에 전달
3. 서버는 검증된 연결만 처리

장점:
- 서버 완전 보호
- 위조 IP 차단

구현:
- F5, Cloudflare 등 전문 장비
- iptables CT target
```

**7. 소스 IP 검증 ★★**
```
- Reverse Path Filtering (RPF)
- 송신지 IP가 라우팅 테이블에 있는지 확인
- IP Spoofing 차단

Linux 설정:
sysctl -w net.ipv4.conf.all.rp_filter=1
```

**8. 방화벽/IPS 시그니처 탐지 ★★**
```
탐지 규칙:
- 초당 일정 개수 이상 SYN 패킷
- Half-Open 연결 비정상적 증가
- 동일 IP에서 과다 SYN

대응:
- 공격 IP 자동 차단
- 관리자 알림
```

**[추가 방어 기법]**

**9. CDN/DDoS 방어 서비스 ★★★**
- Cloudflare, Akamai, AWS Shield
- 트래픽 필터링
- 분산 방어

**10. TCP Timeout 설정 최적화**
```bash
# FIN_WAIT 타임아웃 줄이기
sysctl -w net.ipv4.tcp_fin_timeout=15

# TIME_WAIT 재사용
sysctl -w net.ipv4.tcp_tw_reuse=1
```

**[종합 방어 전략]**
```
1차 방어: CDN/DDoS 방어 서비스
2차 방어: 방화벽 Rate Limiting
3차 방어: SYN Cookie 활성화
4차 방어: IPS 시그니처 탐지
```

**[채점 기준]**
- SYN Flooding 원리 (5점)
- 방어 방법 5가지 이상 (8점)
- SYN Cookie 설명 (2점)

### 문제 6-2: DDoS 공격의 종류 5가지를 설명하고, 각각의 방어 방법을 제시하시오 (15점) ★★★

#### ✅ 모범 답안:

**[DDoS 공격 분류]**

```
Layer별 분류:
- L3/L4 DDoS: 네트워크/전송 계층 (대역폭/연결 고갈)
- L7 DDoS: 응용 계층 (애플리케이션 자원 고갈)
```

**[DDoS 공격 종류 8가지]**

**1. Volumetric Attack (대역폭 소진 공격) ★★★**

**UDP Flood**
```
공격 원리:
- 대량의 UDP 패킷 전송
- 목적지 포트 무작위 또는 특정 포트
- 서버는 매 패킷마다 포트 확인 후 ICMP Port Unreachable 응답

피해:
- 네트워크 대역폭 포화
- 초당 수십 Gbps ~ 수백 Gbps

방어:
- Rate Limiting
- UDP 포트 필터링
- Scrubbing Center (트래픽 정화)
```

**ICMP Flood (Ping Flood)**
```
공격 원리:
- 대량의 ICMP Echo Request 전송
- 서버는 Echo Reply 응답

방어:
- ICMP 패킷 Rate Limiting
- ICMP 차단 (업무 영향 없으면)
iptables -A INPUT -p icmp --icmp-type echo-request -j DROP
```

**2. Amplification Attack (증폭 공격) = DRDoS ★★★**

**DRDoS (Distributed Reflection Denial of Service)** ★★★
```
정의:
분산 반사 서비스 거부 공격

공격 원리:
1. 공격자가 송신지 IP를 피해자 IP로 위조 (IP Spoofing)
2. 다수의 반사 서버(Reflector)에게 요청 전송
3. 반사 서버들이 피해자에게 대량 응답 전송

특징:
- 증폭 효과 (Amplification): 작은 요청 → 큰 응답
- 반사 효과 (Reflection): 공격자 IP 은닉
- 분산 효과 (Distributed): 다수의 반사 서버 이용

공격 흐름:
공격자 (위조 IP: 피해자)
  → 반사 서버 1, 2, 3, ... N (DNS, NTP 등)
  → 피해자 (대량 응답 트래픽)

장점 (공격자 입장):
- 공격자 IP 추적 어려움 (반사 서버 IP만 보임)
- 적은 트래픽으로 큰 피해 (증폭률 최대 200배)
- 정상 서버 악용 (차단 어려움)
```

**DRDoS 대응 방법**: ★★★
```
1. BCP 38 (Best Current Practice 38) ★★★
   - Ingress 필터링: 송신지 IP 검증
   - 위조된 IP 패킷 차단
   - ISP 레벨에서 적용

2. Egress 필터링
   - 내부에서 나가는 패킷의 송신지 IP 검증
   - 자신의 네트워크 대역이 아니면 차단

3. 반사 서버 보안 강화
   - Open Resolver 폐쇄 (DNS)
   - 불필요한 명령 비활성화 (NTP monlist)
   - Rate Limiting 적용

4. 피해자 측 대응
   - Scrubbing Center (DDoS 방어 서비스)
   - 트래픽 필터링
   - Blackhole Routing (극단적)
```

**주요 DRDoS 공격 유형**:

**DNS Amplification** ★★★
```
공격 원리:
1. 공격자가 송신지 IP를 피해자 IP로 위조
2. DNS 서버에 큰 응답을 생성하는 쿼리 전송
   (예: ANY 쿼리 - 모든 레코드 요청)
3. DNS 서버가 피해자에게 대량 응답 전송

증폭률: 최대 50~100배
요청: 60 bytes → 응답: 3000 bytes

방어:
- Open Resolver 폐쇄 (외부 쿼리 거부)
- ANY 쿼리 차단
- Response Rate Limiting (RRL)
```

**NTP Amplification**
```
공격 원리:
- NTP monlist 명령 악용
- 최근 접속한 600개 IP 목록 요청

증폭률: 최대 200배
요청: 8 bytes → 응답: 1600 bytes

방어:
- monlist 명령 비활성화
restrict default kod nomodify notrap nopeer noquery
restrict -6 default kod nomodify notrap nopeer noquery
```

**Memcached Amplification** ★★★
```
정의:
Memcached 서버를 이용한 증폭 공격
UDP 포트 11211을 악용

공격 원리:
1. 공격자가 송신지 IP를 피해자 IP로 위조
2. Memcached 서버(UDP 11211)에 대용량 데이터 저장
3. 피해자 IP로 GET 요청 전송
4. Memcached가 피해자에게 대용량 응답 전송

증폭률: 최대 51,000배 ★★★
요청: 15 bytes → 응답: 750 KB
(역대 최대 증폭률!)

실제 사례:
- 2018년 GitHub DDoS 공격
- 1.35 Tbps 규모 (역대 최대)
- Memcached 서버 수천 대 악용

방어:
1. UDP 포트 차단
   - Memcached는 TCP만 사용하도록 설정
   - UDP 11211 포트 비활성화
   iptables -A INPUT -p udp --dport 11211 -j DROP

2. 바인딩 제한
   - 로컬호스트에만 바인딩
   memcached -l 127.0.0.1

3. 인증 활성화
   - SASL 인증 사용

4. 방화벽 설정
   - 외부에서 11211 접근 차단
```

**시험 출제 포인트**: ★★★
```
문제: "애플리케이션에서 가능한 공격이 아닌 것은?"
보기: Memcached, 멜트다운, 하트블리드, 기타

주의:
- Memcached 증폭 공격은 네트워크 계층 DRDoS 공격
- 애플리케이션 취약점이 아님 (서버 설정 문제)
- 멜트다운은 CPU 하드웨어 취약점 (애플리케이션 아님)
- 하트블리드는 OpenSSL 라이브러리 취약점 (애플리케이션)
```

**3. Protocol Attack (프로토콜 공격) ★★★**

**SYN Flood** (문제 6-1 참조)
```
방어:
- SYN Cookie
- Rate Limiting
- SYN Proxy
```

**ACK Flood**
```
공격 원리:
- 대량의 ACK 패킷 전송
- 서버는 매 패킷마다 세션 테이블 조회

방어:
- Stateful 방화벽 (세션 없는 ACK 차단)
- Connection Tracking
```

**Fragmented Packet Attack**
```
공격 원리:
- IP 패킷을 조각내어 전송
- 서버는 조각 재조합에 리소스 소비

방어:
- 조각화된 패킷 차단
iptables -A INPUT -f -j DROP
```

**4. Application Layer Attack (L7 DDoS) ★★★**

**HTTP GET Flood (Slowloris)**
```
공격 원리:
- 정상적인 HTTP GET 요청 대량 전송
- 복잡한 페이지 요청 (DB 쿼리 많은 페이지)
- 서버 CPU/메모리/DB 연결 고갈

특징:
- 적은 트래픽으로 효과적
- 정상 트래픽과 구분 어려움

방어:
- Rate Limiting (IP당 요청 수 제한)
- CAPTCHA (의심스러운 접속)
- WAF (Web Application Firewall)
- 캐싱 (CDN, Varnish)
```

**HTTP POST Flood**
```
공격 원리:
- 대용량 POST 요청 전송
- 업로드 기능 악용

방어:
- POST 크기 제한
client_max_body_size 10M;
- Rate Limiting
```

**Slowloris Attack**
```
공격 원리:
- HTTP 요청을 천천히 전송
- 헤더를 한 줄씩 느리게 전송
- 서버 연결 고갈 (TimeOut 전까지 유지)

예시:
GET / HTTP/1.1\r\n
Host: example.com\r\n
(10초 대기)
User-Agent: Mozilla\r\n
(10초 대기)
... 반복

방어:
- 요청 타임아웃 짧게 설정
Timeout 10
- Connection 수 제한
- mod_reqtimeout (Apache)
```

**5. Reflection Attack (반사 공격) ★★**

```
공격 원리:
1. 송신지 IP를 피해자 IP로 위조
2. 다수의 서버에 요청 전송
3. 서버들이 피해자에게 응답

활용 프로토콜:
- DNS (53/UDP)
- NTP (123/UDP)
- SNMP (161/UDP)
- SSDP (1900/UDP)
- CharGEN (19/UDP)

방어:
- BCP38 구현 (ISP 레벨)
- 송신지 IP 검증
- 불필요한 UDP 서비스 비활성화
```

**6. PDoS (Permanent Denial of Service) ★★**

```
정의:
영구적 서비스 거부 공격
하드웨어를 물리적으로 파괴하여 복구 불가능하게 만드는 공격
```

**PDoS 공격 특징**: ★★★
```
1. 영구적 손상
   - 하드웨어 물리적 파괴
   - 펌웨어 손상
   - 복구 불가능 (재부팅으로 해결 안 됨)

2. 대상 장비
   - IoT 디바이스 (IP 카메라, 공유기, 스마트 기기)
   - 네트워크 장비 (라우터, 스위치)
   - 산업 제어 시스템 (ICS/SCADA)
   - 모든 펌웨어 기반 장비

3. 일반 DoS와의 차이
   - DoS: 일시적 서비스 중단 → 재부팅으로 복구
   - PDoS: 영구적 파괴 → 장비 교체 필요
```

**PDoS 공격 유형**: ★★★

**1. 플래싱 (Flashing) 공격** ★★★
```
공격 원리:
1. 장비의 펌웨어 업데이트 기능 악용
2. 악의적인 펌웨어 or 손상된 펌웨어 설치
3. 부팅 불가능 상태로 만듦 (Bricking)

공격 시나리오:
- IoT 장비 기본 비밀번호 사용
- 공격자가 관리자 권한 획득
- 펌웨어 업데이트 명령 전송
  flash write 0x00000000 <악성 이미지>
- 장비 부팅 실패 (Brick 상태)

피해:
- 장비 완전 무력화
- 공장 초기화 불가
- 장비 교체 필요
```

**2. 하드웨어 파괴** ★★
```
공격 원리:
- 과부하 유발로 물리적 손상
- 예: CPU 과열, 메모리 소진, 디스크 과다 쓰기

공격 예시:
1. 펌웨어 명령으로 팬 중지
2. CPU 100% 사용으로 과열
3. 열 손상으로 하드웨어 파괴

SSD/Flash 메모리:
- 과다 쓰기로 수명 단축
- wear leveling 알고리즘 우회
```

**3. 논리 폭탄 (Logic Bomb)** ★★
```
공격 원리:
- 펌웨어 내 악성 코드 삽입
- 특정 시간/조건에 자동 실행
- 펌웨어 삭제 또는 손상

트리거 예시:
- 특정 날짜/시간 (2024-12-31 23:59)
- 특정 이벤트 (재부팅 10회 후)
- 원격 명령 (킬 스위치)
```

**시험 출제 포인트**: ★★★
```
문제: "PDoS 특징으로 맞는 것을 고르시오"
보기:
ㄱ. 플래싱 공격
ㄴ. 하드웨어 파괴
ㄷ. PC부터 펌웨어를 사용하는 모든 기기 대상
ㄹ. 논리폭탄
ㅁ. 일시적 서비스 중단

정답: ㄱ, ㄴ, ㄷ, ㄹ

주의:
- PDoS는 영구적 파괴 (ㅁ은 일반 DoS 특징)
- 펌웨어 기반 모든 장비가 대상
- 복구 불가능 (장비 교체 필요)
```

**실제 사례**: ★★★

**1. BrickerBot (2017)**
```
공격 대상: IoT 장비
공격 방법:
- 기본 비밀번호 사용 장비 탐색
- Telnet/SSH 접속
- 펌웨어 삭제 명령 실행
  rm -rf /* --no-preserve-root

피해:
```

## 7. 포트 스캔

### 문제 7-1: Nmap 포트 스캔의 종류 5가지를 설명하고, 각각의 특징을 비교하시오 (15점) ★★★

#### ✅ 모범 답안:

**[Nmap 스캔 종류]**

**1. TCP Connect Scan (-sT) ★★**

```bash
nmap -sT target.com

동작 과정:
Client → Server: SYN
Server → Client: SYN+ACK (포트 열림)
Client → Server: ACK
Client → Server: RST (연결 종료)

결과:
- 포트 열림: SYN+ACK 수신
- 포트 닫힘: RST 수신
```

**특징:**
- 장점:
  - 완전한 3-Way Handshake
  - 권한 불필요 (일반 사용자)
  - 가장 정확한 결과
  - 모든 시스템에서 동작

- 단점:
  - 느림 (완전 연결)
  - 로그에 기록됨 (연결 완료)
  - 쉽게 탐지됨

**2. SYN Scan (-sS, Stealth Scan) ★★★**

```bash
nmap -sS target.com  # root 권한 필요

동작 과정:
Client → Server: SYN
Server → Client: SYN+ACK (포트 열림) → RST 전송
Server → Client: RST (포트 닫힘)

- 3-Way Handshake 미완성 (Half-Open Scan)
```

**특징:**
- 장점:
  - 빠름 (연결 완료 안 함)
  - 은밀함 (로그 미기록 가능)
  - 기본 스캔 방식

- 단점:
  - root 권한 필요 (Raw Socket)
  - IDS/IPS 탐지 가능

**3. UDP Scan (-sU) ★★★**

```bash
nmap -sU target.com

동작 과정:
Client → Server: UDP 패킷
Server → Client: ICMP Port Unreachable (포트 닫힘)
응답 없음: 포트 열림 또는 필터링

결과:
- 포트 열림: 응답 또는 무응답
- 포트 닫힘: ICMP Port Unreachable
```

**특징:**
- 장점:
  - UDP 서비스 탐지 (DNS, SNMP, TFTP)
  - TCP 스캔으로 발견 안 되는 서비스

- 단점:
  - 매우 느림 (타임아웃 대기)
  - ICMP Rate Limiting 영향
  - 결과 불확실 (응답 없음 = 열림/필터링)

**가속화:**
```bash
nmap -sU --top-ports 100 target.com
# 상위 100개 포트만 스캔
```

**4. FIN Scan (-sF) ★★**

```bash
nmap -sF target.com

동작 과정:
Client → Server: FIN 패킷 (비정상)

RFC 793 표준:
- 포트 닫힘: RST 응답
- 포트 열림: 무응답 (비정상 패킷 무시)

결과:
- 포트 열림/필터링: 무응답
- 포트 닫힘: RST 수신
```

**특징:**
- 장점:
  - 일부 방화벽 우회
  - SYN 필터링하는 방화벽 통과
  - Stateless 방화벽 우회

- 단점:
  - Windows는 동작 안 함 (RFC 미준수)
  - 결과 불확실

**5. NULL Scan (-sN) ★★**

```bash
nmap -sN target.com

동작 과정:
Client → Server: 플래그 없는 패킷 (NULL)

- 모든 플래그 비트 0
- URG=0, ACK=0, PSH=0, RST=0, SYN=0, FIN=0

결과:
- 포트 열림/필터링: 무응답
- 포트 닫힘: RST
```

**특징:**
- FIN Scan과 유사
- 일부 방화벽 우회
- Windows 동작 안 함

**6. XMAS Scan (-sX) ★★**

```bash
nmap -sX target.com

동작 과정:
Client → Server: FIN + PSH + URG 플래그 설정

- 크리스마스 트리처럼 모든 플래그 켜짐
- FIN=1, PSH=1, URG=1

결과:
- 포트 열림/필터링: 무응답
- 포트 닫힘: RST
```

**특징:**
- FIN Scan과 동일한 원리
- 시그니처 우회 시도

**7. ACK Scan (-sA) ★★**

```bash
nmap -sA target.com

목적: 방화벽 규칙 파악 (포트 상태 X)

동작 과정:
Client → Server: ACK 패킷

결과:
- RST 수신: 필터링 안 됨 (Unfiltered)
- 무응답/ICMP 에러: 필터링됨 (Filtered)
```

**특징:**
- 포트 개방 여부는 판단 불가
- 방화벽 존재 여부 확인
- Stateful vs Stateless 방화벽 구분

**8. Window Scan (-sW) ★**

```bash
nmap -sW target.com

- ACK Scan과 유사
- RST 패킷의 TCP Window 크기 분석
- 일부 시스템에서 포트 상태 구분 가능
```

**[스캔 비교표]**

| 스캔 종류 | 플래그 | 은밀성 | 속도 | 정확도 | 권한 |
|----------|--------|--------|------|--------|------|
| TCP Connect | SYN | 낮음 | 느림 | 높음 | 불필요 |
| SYN Scan | SYN | 중간 | 빠름 | 높음 | root |
| UDP Scan | - | 중간 | 매우 느림 | 중간 | root |
| FIN Scan | FIN | 높음 | 빠름 | 낮음 | root |
| NULL Scan | (없음) | 높음 | 빠름 | 낮음 | root |
| XMAS Scan | FIN+PSH+URG | 높음 | 빠름 | 낮음 | root |
| ACK Scan | ACK | 높음 | 빠름 | N/A | root |

**[방어 방법] ★★★**

**1. 방화벽 설정**
```bash
# 불필요한 포트 차단
iptables -A INPUT -p tcp --dport 23 -j DROP  # Telnet
iptables -A INPUT -p tcp --dport 21 -j DROP  # FTP

# 특정 IP만 접속 허용
iptables -A INPUT -p tcp --dport 22 -s 1.2.3.4 -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j DROP
```

**2. IDS/IPS 탐지**
```
Snort 규칙:
alert tcp any any -> $HOME_NET any (flags: S; \
  msg: "Possible SYN scan"; \
  detection_filter: track by_src, count 20, seconds 60;)
```

**3. Port Knocking**
```
- 특정 포트 시퀀스 입력 시에만 포트 오픈
- 예: 100, 200, 300 순서로 접속 시도 → SSH 포트 오픈
```

**4. Rate Limiting**
```bash
# 동일 IP 연결 속도 제한
iptables -A INPUT -p tcp --syn -m recent --name portscan \
  --rcheck --seconds 60 --hitcount 20 -j DROP
```

**5. 서비스 최소화**
```bash
# 불필요한 서비스 중지
systemctl stop telnet
systemctl disable telnet
```

**[채점 기준]**
- 스캔 종류 5가지 이상 (10점)
- 각 스캔의 특징 (3점)
- 방어 방법 (2점)
